# crosskit

Минимальная структура проекта на Rust в стиле Onion Architecture.

Как всё это работает и почему устроено именно так — в [docs/how-it-works.md](docs/how-it-works.md):
схемы, объяснение терминов и история принятых решений.

## Слои архитектуры

- `domain` — сущности и бизнес-модель
- `application` — use cases / сервисы
- `infrastructure` — внешние зависимости, I/O, вывод в консоль
- `presentation` — точка входа для пользовательского взаимодействия

Подробный проект локальной базы знаний, двухуровневого графа, переиндексации и
организации файлов описан в
[docs/knowledge-graph-architecture.md](docs/knowledge-graph-architecture.md).

## Установка

Примеры ниже написаны в двух видах — через `crosskit` и через `cargo run`. Это одна и та же
программа; разница в том, откуда берётся исполняемый файл. Этот раздел — про первый вид.

**Сначала о том, чем за него платят.** Собранный бинарь застаревает молча. Он не знает, что
исходники ушли вперёд, и ничего об этом не говорит: `crosskit --version` печатает версию
пакета, а она между сборками не меняется. Владелец на этом уже споткнулся — запустил
`migrate` бинарём, который был на одиннадцать минут старше самой команды, и получил отказ
«нет такой команды» про команду, которая в исходниках есть. Отказ был честный, и понять из
него, что дело в возрасте файла, было нельзя.

### Рекомендуемый способ: обёртка, которая пересобирает

Поэтому рекомендуемый способ — не копия бинаря, а обёртка, которая каждый запуск спрашивает
cargo, не устарела ли сборка:

```sh
#!/bin/sh
# ~/bin/crosskit, положить в PATH и сделать исполняемым
exec cargo run --quiet --release --manifest-path "$HOME/Projects/crosscode/Cargo.toml" -- "$@"
```

`--quiet` убирает служебные строки cargo, чтобы вывод принадлежал программе; `exec` отдаёт
её код возврата как есть, поэтому таблица кодов выше остаётся верной. Когда ничего не
менялось, cargo только проверяет актуальность — это доли секунды; когда менялось,
пересобирает, и запуск ждёт сборку.

Чем платят за это:

- нужен сам чекаут — обёртка ссылается на `Cargo.toml` по пути, и переезд каталога её
  ломает;
- cargo берёт блокировку на `target/`, поэтому второй запуск во время сборки **ждёт**. Для
  `index watch`, который живёт часами, это заметно: пока watcher запущен через обёртку,
  пересборка из-за другой команды не начнётся, а команда, начавшая пересборку, задержит
  остальные;
- сборка `--release` — первая долгая, дальше инкрементальная.

**Куда программа смотрит за данными.** Каталог по умолчанию — `~/Library/Application
Support/Crosskit` на macOS и `$XDG_DATA_HOME/crosskit` (а без этой переменной
`~/.local/share/crosskit`) на Linux; там лежат `config.toml`, графы контекстов и поисковые
индексы. Переопределяет его целиком `CROSSKIT_DATA_DIR`, и читается она при **каждом**
запуске, а не однажды. Обёртка выше передаёт дальше то, что уже есть в окружении, — значит,
если ваши данные лежат не по умолчанию, переменную надо либо экспортировать в профиле, либо
назвать в самой обёртке. Иначе она тихо смотрит в умолчательный каталог, и `status` отвечает
про машину, на которой ничего нет:

```sh
#!/bin/sh
# ~/bin/crosskit, вариант для данных, лежащих не в умолчательном каталоге
CROSSKIT_DATA_DIR="$HOME/crosskit-trial"
export CROSSKIT_DATA_DIR
exec cargo run --quiet --release --manifest-path "$HOME/Projects/crosscode/Cargo.toml" -- "$@"
```

### Переезд с прежнего имени: `migrate --from-crosscode`

До 2026-10-02 программа называлась Crosscode, а её каталог — `…/Application Support/Crosscode`
(`~/.local/share/crosscode` на Linux). Сборка с новым именем, найдя только старый каталог,
**не начинает с пустого и не переносит его сама** — отказывает одной строкой с командой:

```sh
crosskit migrate --from-crosscode
```

Команда переименовывает каталог одним `rename(2)` — графы, индексы, кэш ответов и
`config.toml` остаются байт в байт, ничего не перестраивается, пути внутри конфигурации не
меняются. Отказывает, ничего не тронув, если оба каталога существуют, если граф держит на
запись другой процесс (называет его номер — обычно это `index watch`), если старый каталог
на другом томе (это была бы копия) и если каталог задан `CROSSKIT_DATA_DIR`. Читающих
процессов (панель, `search`) замок не показывает — их закрывают перед переездом.

Переменные тоже переименованы: `CROSSCODE_*` → `CROSSKIT_*`. Если задана только старая,
программа отказывает и называет новую; если заданы обе, читается новая, а про старую
печатается строка в stderr. Имена анализаторов поиска `crosscode-prefix` и
`crosscode-normalizing` остались прежними: они записаны в схеме каждого индекса (ADR 0047).

### `cargo install --path .`

```bash
cargo install --path .
```

Кладёт готовый бинарь в `~/.cargo/bin` и снимает и блокировку `target/`, и зависимость от
пути чекаута: запуск становится просто запуском. Платят за это ровно тем, с чего начался
раздел — это **снимок**. После каждого изменения исходников команду нужно выполнить снова,
и ничто об этом не напомнит: программа продолжит работать, просто это будет вчерашняя
программа. Отдельная release-сборка занимает своё место на диске.

Пока проект меняется этапами, обёртка честнее. `cargo install` разумен там, где чекаут
трогают редко.

## Запуск

Первый запуск на настоящей машине — одна команда, которая предлагает контексты, показывает
конфигурацию, спрашивает и индексирует (подробно — «С чего начать»):

```bash
crosskit setup ~
crosskit status
```

Что программа умеет и как её спрашивать:

```bash
crosskit --help              # все команды одним списком
crosskit <команда> --help    # грамматика одной команды
crosskit --version           # какая это сборка
```

`--help` печатает ту же строку `Usage:`, которой команда отказывает, — это один текст, а не
копия: справка и разборщик не могут разойтись. Слово, которое не является командой,
отвергается по имени и со списком настоящих, а не молча.

Проверить и создать локальное хранилище графа можно отдельно:

```bash
cargo run
cargo run -- doctor
```

### Чем заканчивается запуск

| запуск | код |
| --- | ---: |
| сделал то, о чём просили | 0 |
| ответил на вопрос о программе (`--help`, `--version`) | 0 |
| печатал в вывод, который уже никто не читал | 0 |
| не сделал того, о чём просили | 1 |
| упал сам — это дефект | 101 |

Третья строка — про `crosskit status | head`. `head` закрывает канал, как только набрал
свои строки; раньше следующий `println!` превращался в панику, и запуск, сделавший ровно то,
о чём просили, заканчивался отчётом о сломанной трубе с кодом 101. Теперь он заканчивается
тихо и нулём: команда своё сделала, а тот, кто просил, перестал слушать. Вопрос задаётся
операционной системе (`poll` на дескрипторе), а не угадывается по тексту паники.

Четвёртая строка покрывает три разные для человека и одинаковые для оболочки вещи: запрос,
который не разобрался, контекст, который не открылся, и проход, который не завершился.
Развести их по отдельным кодам значит завести типизированную ошибку в возврате **каждой**
команды; сегодня их различает предложение на stderr, и каждое такое предложение говорит, что
делать дальше.

Каждый контекст хранит свой граф отдельным файлом: на macOS по умолчанию
`~/Library/Application Support/Crosskit/graph-<контекст>.lbug`. Для изолированного
запуска или тестирования каталог задаётся через `CROSSKIT_DATA_DIR`; оригиналы файлов в
базе не сохраняются.

Индексация работает **над контекстом**: без каталога она обходит каждый корень, который
контекст объявляет в `include`, а каталог — сужение по явному требованию. Политика области
индексации применяется до чтения содержимого:

```bash
cargo run -- --context work index init              # каждый корень контекста
cargo run -- --context work index init ./docs       # только этот, если он лежит в контексте
cargo run -- --context work index reconcile         # то же для сверки
cargo run -- policy explain ./docs/notes.md
```

**Отказ одного корня не уносит остальные.** Каждый корень обходится сам по себе, и прогон
заканчивается перечнем: сколько корней обойдено, какие нет и что их остановило. База и
поисковый индекс открываются один раз до первого корня — если не открылись они, не обходится
ни один корень, и это единственный отказ, который говорит за весь контекст. Частичный проход
заканчивается кодом 1 и называет корни (ADR 0039).

`include`, который является маской, а не каталогом, обойти нельзя: он покрывает много
каталогов и не называет ни одного. Такой `include` **называют** в отчёте и в `status`, а не
пропускают молча.

Если настроен ровно один контекст, `--context` можно не писать — берётся он. Пока не
настроен ни один, индексировать нечего: путь, который не покрывает ни один контекст, не
индексируется.

## Контексты

На одной машине лежат файлы работодателя, личные проекты и файлы другого человека. Контекст
— граница конфиденциальности, а не фильтр: когда ИИ отвечает внутри рабочего контекста,
ничего из личного не может быть упомянуто или использовано.

Держит эту границу не проверка в каждом запросе, а хранение: **у каждого контекста своя
база**. Кросс-запрос между контекстами невозможен физически — в базе, против которой идёт
запрос, чужих файлов нет.

```toml
[workspace.work]
include = ["~/Work", "~/Projects/employer"]

[workspace.personal]
include = ["~/Documents", "~/Projects/mine"]
```

Правила те же, что у политики индексации: маска на любой глубине, покрытие распространяется
на потомков, выигрывает самое специфичное правило. Отличие одно и важное: **пересечение
покрытия двух контекстов — ошибка загрузки**, потому что путь принадлежит ровно одному
контексту, а граница, которую разрешает precedence, — не граница. Сообщение называет оба
контекста и оба правила так, как они написаны в конфиге. Из этого следует, что вырез
поддерева (рабочий контекст на весь домашний каталог и личный на папку внутри) пока не
выражается.

Один запуск команды работает **внутри одного контекста**: каталог, переданный в
`index init`, `reconcile` или `watch`, обязан лежать внутри покрытия названного контекста, а
когда контекст не назван и настроено несколько, команда отказывается до того, как
что-либо откроет. `index init` и `reconcile` без каталога обходят каждый корень названного
контекста — это по-прежнему один контекст, просто все его корни.

У этого есть названное исключение. Отчётные и обслуживающие команды проходят **по всем**
контекстам: `status` читает каждый, `migrate` приводит каждый к схеме этой сборки, `setup`
индексирует каждый, который только что записал. Они открывают контексты **по очереди**,
каждый — своей базой, и жёсткий инвариант изоляции этим не нарушается: ни одна функция не
получает двух контекстов сразу, и ни один запрос не пересекает границу между ними.

| команда | сколько контекстов открывает | сколько корней обходит |
| --- | --- | --- |
| `setup <каталог>` | все, которые только что записал, по очереди | все корни каждого |
| `status` | все настроенные, или один по `--context`; только на чтение | ни одного; называет все |
| `migrate` | все настроенные, или один по `--context`; на запись | ни одного |
| `index init`, `index reconcile` | ровно один | все корни контекста, или один названный |
| `index watch` | ровно один | все корни контекста, или один названный |
| `doctor`, `search`, `ask` | ровно один | ни одного; `doctor` называет пустые |
| `index …` — `init`, `reconcile`, `watch`, `review`, `rebuild`, `recover`, `runs`, `jobs`, `jobs run`, `jobs withdraw` | ровно один |
| `contexts propose`, `policy explain` | ни одного: база не открывается |

Имя контекста попадает в имя файла базы, поэтому разделители пути, обход вверх и пустое имя
отвергаются при загрузке, а не «очищаются»: то, во что санитайзер молча превратил бы имя, —
другой контекст, чем написал оператор. Буквы любого письма допустимы.

База по старому пути `graph.lbug`, написанная до появления контекстов, не принимается: в ней
не записано, какие файлы какому контексту принадлежат. Команда отказывается и просит убрать
файл и проиндексировать заново. Подробности и отложенные решения — общий контекст, тени,
смешанные папки — в ADR 0008.

### С чего начать: `setup`

Первый запуск на настоящей машине — одна команда и один разговор:

```bash
crosskit setup ~
```

Она обходит дерево, читает рядом папки бесед Claude Code (`~/.claude/projects`) и папки без
git в `Documents`, `Desktop`, `Downloads` и рядом с проектами, и **собирает найденное в
группы** — вещи, которые держатся вместе, с причиной, почему. Потом спрашивает. Ни ИИ, ни
сети.

| что | куда | причина |
| --- | --- | --- |
| проекты с одной группой `origin` на одном хосте | одна группа | одна группа `origin` |
| проект без такого признака | группа из одного | «признака нет» — и какого |
| репозиторий внутри проекта | с проектом, это печатается | два контекста не покрывают один путь |
| папка бесед проекта | с проектом | беседы этого проекта |
| папка без git, где работали беседы группы | с группой | там работали её беседы |
| папка без git, где не работал никто | остаток | показывается до первого вопроса |

Группа `origin` — первый сегмент пути: у `git@git.example.org:acme/platform/app.git` это
`acme`. Группа, названная доменом вашей почты из `~/.gitconfig`, помечается «looks like your
organization» — это пометка, а не решение.

```

  ~/.claude/projects/-private-tmp-probe (1 conversation): started in a temporary place: nobody's work
  ~/.claude/projects/-Users-alice-Projects (1 conversation): started in ~/Projects, which holds projects without being one: …
Codex: 1 session found; they are outside every context, because Crosskit has no reader for them.

Context 1: client-a
Context 2: client-b

  folder         ~/Documents/letters  (1 file)

  project        ~/Projects/alpha
  project        ~/Projects/beta
  conversations  ~/.claude/projects/-Users-alice-Projects-alpha  (1 conversation, started in ~/Projects/alpha)

…
```

Порядок вопросов:

1. **Контексты.** Имена вводите вы, по одному; пустая строка — конец, минимум один. Имён
   по умолчанию нет: система не знает, на что делится ваша жизнь, — «клиент А», «клиент Б»,
   «своё» или «работа» и «личное».
2. **Остаток** — до первой группы: куда идёт всё, что останется без ответа. Если выбран
   контекст, остаток записывается **явным списком каталогов**, а не правилом. Ответ `n`
   значит «спроси по одной»: после групп каждая папка остатка спрашивается так же, как
   группа, а пустой ответ — никуда.
3. **Группы**, по одной: номер контекста, `s` — никуда, пустая строка — в остаток.
4. **Файл целиком** и `[y/N]`. Показанное и записанное — одна строка.

Папка бесед сопоставляется с проектом не раскодированием имени, а наоборот: путь проекта
кодируется правилом Claude Code и сверяется с первым `cwd` каждой беседы внутри. Не сошлось
— папка не раскладывается и печатается с причиной. В папке бесед индексируются сами беседы
(`<id>.jsonl`) и **заметки инструмента о проекте в `memory/`**; каталог каждой сессии
(`<id>/` — транскрипты подагентов, сохранённый вывод инструментов, служебные дампы) в файле
исключён. Беседа идёт туда, где начата, а не по теме: беседа, начатая в личном проекте о
рабочих данных, лежит в личном контексте. Отдельного контекста `chats` новый `setup` не создаёт: беседы — в контекстах
своих проектов. Обоснование — ADR 0042.

После индексации — по строке на корень (файлы, фрагменты и, если были, непрочитанные пути)
и итог: что держит каждый контекст (проекты, папки без git, беседы) и что осталось вне всех
контекстов и почему. Полный отчёт по корню — `crosskit --context <имя> index init
<каталог>`. Каталоги, которые macOS не открывает терминалу без Full Disk Access (Корзина,
Фото, части `Library`), в файле — одной строкой со счётом: ни один из них для контекста не
нужен. Любая другая ошибка обхода по-прежнему названа поимённо.

Правила команды:

- **машина с объявленными контекстами — отказ**, не слияние и не перезапись. Чтобы разложить
  машину заново, отодвиньте `config.toml` (переименуйте и держите до конца индексации) и
  запустите снова;
- конфигурация **без** контекстов (только `[index]`, скажем) заменяется, но файл, который там
  был, копируется рядом под именем со временем — `config.toml.before-setup-20260923T101500Z`;
- **выход содержимого у всех новых контекстов выключен.** При записи одна строка говорит,
  сколько бесед в каждом контексте станут отправляемыми, если выход ему включить;
- закрытый вход на любом вопросе — не «да»: ничего не пишется. **`--yes` отказывается**:
  контексты называет человек, и догадки на случай, когда его нет, не существует;
- контекст, который не проиндексировался, не забирает остальные: итог называет упавший, код
  возврата 1.

Дальше — `crosskit status` (ниже), `crosskit search <слово>`, `crosskit ask "вопрос"`.

### Посмотреть черновик, ничего не трогая: `contexts propose`

Та же самая выкладка, без записи и без индексации: `crosskit contexts propose <каталог>`
обходит дерево и печатает **черновик** конфигурации контекстов по хосту remote, с уликой
под каждым предложением. В отличие от `setup`, он ничего не спрашивает и групп `origin` не
использует. Это то, что запускают на машине, где контексты уже есть, или когда хочется
собрать конфиг руками.

```bash
crosskit contexts propose ~
crosskit contexts propose ~/Projects > draft.toml
```

Команда только читает: ни конфигурации, ни базы, ни индекса она не создаёт, и работает до
того, как появился хоть какой-нибудь конфиг. Обход — тот же, что у скана и у `setup`:
относительно дескрипторов, без перехода по символическим ссылкам; нечитаемый каталог
считается и не роняет обход.

Улики только детерминированные — никакого ИИ и ни одной сетевой операции:

- каталог с записью `.git` и **хост** его remote — сильнейший сигнал «рабочее против
  личного»;
- маркеры проектов по точному имени файла: `Cargo.toml`, `package.json`, `go.mod`,
  `pyproject.toml` и ещё одиннадцать;
- верхнеуровневая раскладка домашнего каталога (`Documents`, `Downloads`, `Library`,
  `.cargo`, `go`…) — но только если обходят ровно `$HOME` и только для его прямых потомков;
- объём и глубина поддерева.

Содержимое файлов не читается. Единственное исключение — `.git/config`, и из него берётся
**только хост** remote и первая группа пути `origin` (последнюю читает только `setup`, ADR 0042):
ни URL целиком, ни аккаунт, ни имя репозитория никуда не печатаются и нигде не сохраняются. Сам каталог `.git` не обходится — впускается он сам и `config` в нём,
всё остальное отвергается до `stat`. Обоснование исключения — ADR 0019.

Вывод — валидный TOML целиком, объяснения комментариями, поэтому его можно вставить в файл
политики и править на месте:

```toml
# Draft contexts for /home/alice
#
# Walked: 8,410 files, 512.0 MB, deepest file 9 levels down.

[workspace.git-example-org]
# 2 repositories whose remote host is git.example.org
include = [
  "/home/alice/Projects/alpha",  # .git, remote host git.example.org; 412 files, 3.1 MB, deepest file 6 levels down
  "/home/alice/Projects/beta",   # .git, remote host git.example.org; 88 files, 412.0 KB, deepest file 4 levels down
]

# Not attributed to any context. These are yours to decide:
#
#   "/home/alice/Downloads"
#     1,204 files, 8.9 GB, deepest file 3 levels down
#     a standard home directory that everything arrives in, of every origin at once
```

Что команда **не** делает, и это намеренно:

- ничего не решает за человека. Репозиторий, у которого remote указывают на разные хосты и
  нет `origin`, не относится ни к какому контексту — он попадает в список нераспределённого
  с обоими хостами;
- не предлагает пересекающихся покрытий. Репозиторий внутри репозитория покрывается внешним
  (строка «covers N repositories inside it»), а `~/Documents` с проектом внутри не
  предлагается целиком: вырез поддерева пока не выражается;
- не предлагает сам корень обхода. `.git` в самом корне — это дотфайлы в `~`; один контекст
  на всё был бы решением, а не подготовкой решения, поэтому про него печатается строка;
- не учитывает существующую политику. Числа объёма — то, что лежит на диске; политика
  индексации читает меньше (`target`, `node_modules`, `.git`, `vendor`, `__pycache__`,
  `.pnpm-store` исключены по умолчанию, а каталоги с маркером кэша — целиком).

`--context` с обеими командами отвергается, а не игнорируется: они как раз предлагают,
какими контексты могли бы быть.

### Что сейчас в каждом контексте: `status`

`crosskit doctor` отвечает про один контекст. `crosskit status` отвечает про все сразу.
Обе, вместе с `search` и `ask`, **ничего не пишут**: это четыре команды одного класса, и с
ADR 0034 ни одна из них не открывает граф на запись — ни создать, ни мигрировать, ни
свернуть журнал:

```
Policy file: /home/alice/Library/Application Support/Crosskit/config.toml
Contexts: 4

git-example-org
  State: indexed
  Database: /home/alice/Library/Application Support/Crosskit/graph-git-example-org.lbug
  Schema version: 12
  Files: 412 (486 revisions kept)
  Insight jobs: queued 12, claimed 0, done 400, failed 0, dead 0
  Search index: 1,308 documents against 1,308 chunks of current versions (in step with the graph)
  Search index written by: the rules this build reads with

personal
  State: indexed, and held between passes by a writer (process 40152); the counts below are what that writer has folded into the database
  ...

archive
  State: not indexed yet
  Next: `crosskit --context archive index init <directory>` writes its graph from the files on disk.

books
  State: a pass was stopped without closing this context
  Its write-ahead log is still beside its graph, and the storage engine may refuse to replay it…
  Log: /home/alice/Library/Application Support/Crosskit/graph-books.lbug.wal
  Next: `crosskit --context books index recover --check` opens it and says whether it still opens; …
```

`--context <имя>` показывает один контекст. Контекст без базы — строка «ещё не
индексировался», а не ошибка; контекст, который держит писатель, — строка о том, что он
занят, а не отказ всей команды. Ни одно состояние контекста не роняет команду: это находка,
а не сбой отчёта, и код возврата остаётся нулевым — единица означает, что ответить не
удалось вообще.

Обе беды поиска названы в обе стороны: «in step with the graph» и «the one this build reads
with» — тоже ответы. Отчёт, который молчит, пока всё хорошо, не даёт отличить здоровый
контекст от того, который забыли проверить. Сам отпечаток анализатора печатает `doctor`.

**Почему эти команды не пишут — и как это устроено.** Открытие базы на запись создаёт базу
контекста, который никто не индексировал, мигрирует базу старой сборки и при закрытии
сворачивает журнал в базу. Все три — записи. Поэтому ни одна из четырёх его не делает, а
состояние контекста читается с файловой системы, до любого открытия, по двум фактам:

| состояние | журнал `*.lbug.wal` | блокировка записи на файле базы |
| --- | --- | --- |
| простаивает, закрыт чисто | нет | свободна |
| watcher между проходами | нет | держит watcher |
| проход пишет прямо сейчас | есть | держит этот проход |
| проход убит посреди записи | есть | свободна |

Блокировка — POSIX-овская, и спрашивается через `fcntl(F_GETLK)`, который сообщает, кто её
держит, и **не берёт никакой**. Отсюда: журнал, чей писатель мёртв, — это остановленный
проход, и он назван без открытия базы, которую движок в этом состоянии может не пережить
(на Linux он умирал по сигналу на трёх базах из шести — ADR 0015).

Открывается только то, у чего журнала нет, и только на чтение: открытие, которое не создаёт
и не мигрирует. Цена названа прямо — `status` не читает то, что писатель принял, но ещё не
сбросил контрольной точкой, и не чинит схему: база со схемой не этой сборки становится
строкой отчёта, а не миграцией. Поисковый индекс открывается тем же правилом: обычное
открытие создало бы пустой индекс там, где его нет, поэтому у `status` своя дверь, которая
открывает и не создаёт. Проверяется это поведением — снимок каталога данных до и после, в
тех же четырёх состояниях (ADR 0020).

### Схема после обновления: `migrate`

`status` говорит, что делать, и не делает сам. Делает — одна явная команда, и она проходит
по **всем** контекстам за один запуск:

```bash
crosskit migrate
```

```text
Policy file: /home/alice/Library/Application Support/Crosskit/config.toml
Contexts: 4

git-example-org
  Schema version: 13

personal
  Schema version: 13

archive
  Nothing to migrate: this context has no graph yet
  `crosskit --context archive index init <directory>` writes it from the files on disk.

books
  Not migrated: a pass was stopped without closing this context
  Log: /home/alice/Library/Application Support/Crosskit/graph-books.lbug.wal
  `crosskit --context books index recover` moves that log aside and keeps it; …
```

Миграция — это запись, и применяет её само открытие базы на запись. До этой команды не было
запуска, который делал бы только это: были команды, которые делают это попутно, и каждая —
про один контекст. После v13 две базы из четырёх владельца не открылись, и лечение было
четырьмя отдельными запусками. Сборка, обогнавшая схему одного контекста, почти наверняка
обогнала и остальные, поэтому починка просится один раз и применяется везде.

Перед открытием читаются те же два файла, что и в `status`, и по той же причине: контекст,
который никто не индексировал, не должен получить базу оттого, что попросили миграцию, а
граф после оборванного прохода вообще не открывается — движок на нём иногда умирает, а не
отказывает. Оба состояния названы, ни одно не тронуто. `--context <имя>` мигрирует один
контекст.

Отчёт печатается по всем контекстам и только потом решается код возврата: запуск, который
остановился бы на первом неоткрывшемся графе, спрятал бы остальные — ровно то состояние,
ради которого команда и появилась. Если хоть один граф остался не на схеме этой сборки,
запуск заканчивается единицей (ADR 0031).

## Область индексации и приватность

Для каждого пути политика принимает одно из трёх решений:

- `Include` — сохраняются метаданные и содержимое: `File`, `FileLocation`, `FileVersion`,
  `ContentChunk`, `FileObservation`;
- `Metadata` — сохраняются только имя, размер, тип и даты (`File` и `FileLocation`);
  файл не открывается;
- `Exclude` — путь не открывается, не читается через `stat`, не попадает в граф, а отчёт
  сканирования показывает только число исключённых путей без самих путей.

Precedence детерминирован:

1. `Exclude` сильнее `Metadata`, `Metadata` сильнее `Include`: побеждает самый
   ограничивающий класс среди всех подошедших правил.
2. Внутри одного класса побеждает более специфичное правило: больше буквальных
   сегментов, затем больше сегментов фиксированной глубины, затем больше буквальных
   символов; при равенстве — правило, объявленное раньше.
3. Путь, который не покрыло ни одно правило, исключается.
4. Явно переданный корень `index init` даёт `Include` своему поддереву на время
   запуска, но не отменяет `Metadata` и `Exclude` из конфигурации. Симлинк в самом
   корне разрешается до применения политики, ниже корня симлинки не traversятся: сам
   link сохраняется как metadata, его цель не читается.

Правило покрывает путь и всех его потомков. Шаблон начинается с `/`, `~/` или `**/`;
`*` и `?` действуют внутри одного сегмента, `**` покрывает любое число сегментов.

Кроме правил по путям действует правило по признаку: каталог, который несёт
`CACHEDIR.TAG` или `pyvenv.cfg`, пропускается целиком — вместе со всем поддеревом и не
попадая в граф. Оба имени оставляет тот инструмент, который сделал каталог
(`CACHEDIR.TAG` — общепринятый стандарт тегирования кэшей, его пишут cargo, ruff, mypy,
pytest; `pyvenv.cfg` — маркер корня питоновского окружения), поэтому правило работает и
для инструментов, о которых Crosskit ничего не знает. Отчёт показывает такие каталоги
отдельным счётчиком. Обоснование и измерения — ADR 0026.

Найденный маркер становится правилом `Exclude` на это поддерево **на время прогона**, и
дальше все шаги видят одно «сюда мы не смотрим», а не два. Это существенно: сверка хоронит
путь, которого не видела, только если политика его не исключает, — а пропуск по маркеру
защиты не имел и объявлял пропавшими файлы, лежащие на диске.

**Если ложные `missing` уже записаны.** Прогоны до этой правки могли пометить пропавшими
файлы внутри каталога, у которого появился маркер (в отчёте это видно как ненулевой
`Locations marked missing` при сверке, в которой ничего не удаляли). Обычная сверка это
**не лечит**: каталог теперь, и совершенно правильно, не обходится, а `present`
возвращается только наблюдением, которого больше не будет. В выдаче эти записи не всплывают
— поиск отбрасывает `missing`, — но история говорит неправду. Починить можно двумя
способами: убрать маркер, прогнать сверку (записи вернутся в `present`) и вернуть маркер на
место, либо проиндексировать контекст заново. Второе надёжнее: маркер пишет инструмент, и
он может восстановить его в любой момент.

Две защитные границы действуют независимо от правил. Запись, чьё имя не является
корректным UTF-8, нельзя точно представить строковой политике, поэтому она исключается
до любого системного вызова и попадает в отчёт только счётчиком. Файл, который изменился
между снятием метаданных и чтением или во время чтения, не публикуется вовсе: ни
`FileLocation`, ни evidence. Проверка сравнивает inode, размер и mtime с точностью до
наносекунды, так что перезапись того же размера внутри одной миллисекунды тоже
считается нестабильной; отчёт показывает такой файл как unstable source, а следующий
scan увидит уже стабильный файл.

### Чем отвечает: движок анализа

Кто отвечает на вопрос `ask` и кто размечает ревизию в очереди — один и тот же выбор,
названный один раз:

```toml
[analysis]
engine = "claude-code"        # умолчание — установленный инструмент подписки

[analysis.claude-code]
model = ""                    # пусто — модель решает подписка

# либо, вместо этого:
# [analysis]
# engine = "anthropic-api"
#
# [analysis.anthropic-api]
# model = "claude-haiku-4-5-20251001"
# effort = ""
```

Умолчание — `claude-code`: установленный инструмент подписки, токены которой уже оплачены.
Требуется только команда `claude` в `PATH`; ключ не нужен. Движок `anthropic-api` — тот же
HTTP-провайдер, что и раньше, он никуда не делся и выбирается именем; ему нужен
`ANTHROPIC_API_KEY` в окружении.

Неизвестное имя движка — отказ загрузки с перечислением известных. Настройки живут под своим
движком: `effort` принадлежит API и под `[analysis.claude-code]` его написать нельзя, а
секция движка, который не выбран, тоже отказ — настройка, молча не делающая ничего, здесь не
предусмотрена. Поля `model` и `effort` переехали из `[insight]`; старый файл не загрузится и
скажет, что именно в нём лишнее.

Если движок нельзя использовать — инструмента нет в `PATH`, ключа нет в окружении, — команда
говорит причину один раз и **не трогает очередь**: ни одно задание не захватывается, ни одна
попытка не тратится.

**Что нужно знать про подписку как канал.** Содержимое уходит наружу так же, как через API, —
подписка не делает его локальным, и `send_content_outside = true` требуется точно так же.
Сверх этого у инструмента есть своё свойство: по умолчанию он пишет транскрипт всего, что ему
передали, в `~/.claude/projects/<путь>/<session>.jsonl`. Crosskit всегда передаёт
`--no-session-persistence`, и тогда этот файл не пишется (проверено помеченной строкой).
Но `~/.claude/todos/` и `~/.claude/debug/` инструмент пишет при каждом вызове в любом случае —
это его журналы, вне управления Crosskit. Подробности и измерения — ADR 0028.

**Сколько это занимает.** Одно задание через подписку — 7–11 секунд, из них около 2.7
секунды уходит на запуск процесса. Важное: на длинном прогоне подписка не отказывает, а
**замедляется** — 7.25 с на задание на двенадцати подряд и 10.74 с на пятидесяти, без единого
отказа. Сообщения об исчерпании лимита ждать не нужно, его не будет. Считайте
`index jobs run --limit 50` примерно в девять минут, `--limit 100` — в восемнадцать. Очередь
на большом дереве разбирается порциями, и размер порции выбирается по тому, сколько вы готовы
ждать за один раз.

**В каком порядке.** Раньше берётся задание той ревизии, которая **раньше наблюдалась**, а
не то, чья строка в очереди раньше создана. Поэтому одобрение маски, поставившее задания
задним числом, не отодвигает и не обгоняет ничего случайно: старый файл, про который вы
только сегодня сказали «анализируй», законно старше документа, увиденного этим утром, и
идёт раньше него. Порядок описан в ADR 0030.

### Что разбирается, а что ждёт вашего решения

Разбор стоит времени подписки: на дереве владельца полный разбор — 77 часов. Поэтому
разбирается не всё.

```toml
[analysis]
automatic = ["**/*.md", "**/*.txt"]   # документы — сами
approved  = []                        # остальное — по вашему решению
```

Документы разбираются сами. Всё прочее **не получает задания вовсе** — не задание в особом
состоянии, а именно ни одного, — и ждёт вас в списке:

```
crosskit index review
```

Список сгруппирован по видам файлов и по каталогам, у каждой группы — число ревизий и оценка
времени по измеренной цене задания. Решение принимается пачкой:

```
crosskit index review approve '**/*.py'
```

Одобрение дописывает маску в `[analysis] approved`, спросив подтверждение и сохранив
предыдущую конфигурацию рядом — как это делает `setup`. Маска, а не список файлов: одобрив
каталог однажды, вы не одобряете каждую его новую ревизию. Уже проиндексированные ревизии
ставятся в очередь задним числом, постранично.

Если правило перестаёт покрывать ревизию, её задание уходит в `skipped` — тем же способом,
что и при смене политики путей. Покрытая снова — возвращается в очередь ближайшим проходом.

На дереве владельца умолчание покрывает 1 703 ревизии из 25 952 (6.6 %) — около пяти часов
вместо семидесяти семи; остальные 24 249 ждут решения. Обоснование умолчаний и все числа —
ADR 0029.

### Тема файла

У файла, который был разобран, поиск показывает строку `about:`:

```
1. [present] /Users/me/work/договор.md
   about: аренда складского помещения
   Настоящий договор регулирует аренду...
   matched: аренду
```

У файла, который не разбирали, этой строки просто нет — ни пустой метки, ни прочерка.
Большинство файлов такие, и заглушка на каждом была бы шумом.

Тема идёт и в `ask` — отдельным полем выдержки, рядом с текстом, а не внутри него.

Очередь на анализ спрашивает политику **при захвате задания, а не при постановке**:
очередь живёт дольше политики, которая её наполнила. Задание, чей файл больше не лежит ни
на одном пути, который контекст индексирует, уходит в своё терминальное состояние
`skipped` — это не ошибка и не «мертво», вопрос просто отозван, и модель не вызывается.
Если путь снова попадает под индексацию, ближайший обычный проход возвращает задание в
очередь: `skipped` — единственное состояние, которое повторная публикация ревизии
сбрасывает, потому что за ним не стоит никакой работы. `index jobs` показывает счётчик
`skipped`, `index jobs run` — строку «Skipped jobs (the policy no longer asks)».

Путь к файлу: `CROSSKIT_CONFIG`, иначе `config.toml` в каталоге данных
(`CROSSKIT_DATA_DIR`; на macOS по умолчанию `~/Library/Application Support/Crosskit`,
иначе `$XDG_DATA_HOME/crosskit`). Без файла действуют только встроенные исключения
`**/.git/**`, `**/node_modules/**`, `**/target/**`, `**/.env`, `**/*.key`,
`**/Library/Caches/**`, `**/.pnpm-store/**`, `**/vendor/**`, `**/__pycache__/**`, правило
по маркеру каталога (выше) и лимит содержимого 100 MB. Встроенные исключения применяются
всегда; конфигурация их только расширяет.

```toml
[index]
include = ["~/Documents", "~/Projects"]
metadata_only = ["~/Pictures"]
exclude = ["**/*.pem"]
max_content_size_mb = 100

[workspace.personal]
include = ["~/Documents"]

[workspace.work]
include = ["~/Projects"]

[watch]
analyze = true       # watcher разбирает очередь заданий после каждого удавшегося прохода
analyze_limit = 20   # не больше стольких заданий за проход
```

Неизвестный ключ, относительный шаблон или `~user` — ошибка загрузки. Секции
`[workspace.<имя>]` описаны в разделе «Контексты»; пересечение их покрытия — тоже ошибка
загрузки.

### Проверка решения

`crosskit policy explain <path>` печатает решение, контекст пути или его отсутствие,
сработавшее правило с его источником (`built-in default` или `configuration`), причину и
путь к файлу политики.
Команда не обращается к файловой системе: путь нормализуется лексически, поэтому
несуществующий путь объясняется так же, как существующий, а содержимое никогда не
читается.

### Физический слой

Каждый сохранённый файл получает `FileLocation`: нормализованный путь, отображаемое имя,
тип (`file`, `symlink`, `special`), размер, время изменения, `first_seen_at`,
`last_seen_at` и статус `present | missing`. Идентичность location — `file_id` плюс
нормализованный путь, поэтому повторный scan того же файла по тому же пути обновляет
одну запись, а новый файл на старом пути создаёт новую location и переводит прежнюю в
`missing`. Watcher, обнаружение rename и семантические извлечения последуют отдельными
этапами.

### Письменность чанка

У каждого `ContentChunk` есть поле `script`. **Это не язык.** Оно называет ровно то, что
вычислено по тексту самого чанка: какие из письменностей, которые Crosskit умеет
нормализовать, в нём встречаются.

| Значение | Что означает |
| --- | --- |
| `latin` | латинские буквы есть, кириллических нет |
| `cyrillic` | кириллические есть, латинских нет |
| `latin+cyrillic` | есть и те и другие — обычный случай для смешанного текста |
| `neither` | букв ни одной из двух письменностей нет |

Раньше на этом месте было поле `language` со значением `en`, если файл целиком ASCII, и
`und` иначе, причём решение принималось один раз на весь файл. Английский код оказывался
`en` по совпадению, русская проза — `und`, а файл с русским текстом и английскими
идентификаторами — `und` целиком. Определения языка в системе нет, и поле больше не
изображает его. Подробности и миграция — ADR 0012.

### Идентичность файла

Файл опознаётся парой «устройство и inode», которую даёт ядро. Эта пара — не идентичность во
времени: ext4 и overlayfs отдают освободившийся номер inode следующему созданному файлу
(в проверке — 20 из 20), APFS не отдаёт никогда. До Этапа 3 новый файл из-за этого наследовал
`File`-узел удалённого: его ревизии и наблюдения повисали на чужой идентичности, а ретайр
прежней location читался как relocated.

Теперь идентичность датируется. `File` хранит момент, когда граф впервые увидел файл с этой
парой, и файл, созданный позже этого момента, не может быть тем файлом: он публикуется под
собственной идентичностью. Время создания берётся у файловой системы (`st_birthtime` на
macOS, `statx`/`STATX_BTIME` на Linux) и служит дискриминатором, поэтому ветка детерминирована
и каждый следующий проход приходит к той же идентичности.

Правило действует в одну сторону: разделить историю одного файла на две поправимо, слить два
разных файла в один — нет. Поэтому при любой неуверенности идентичность считается новой.

Переименование и hard link ничего не меняют: у них та же пара и то же время создания, поэтому
это один `File` с несколькими locations, а переименование по-прежнему классифицируется как
relocated. Идентификаторы уже сохранённых файлов не переписывались: миграция v9 добавляет одно
поле и заполняет его из locations, которые в графе уже есть.

Что остаётся известным ограничением: файловая система без времени создания (не Linux и не
macOS) переиспользование не различает; столкновение, уложившееся в одну миллисекунду вместе с
первым наблюдением прежнего файла, не различается; `File` из базы схемы v1–v4 ничем не
датирован и потому не наследуется. Подробности и планы запросов — в ADR 0002 и 0003.

Защита не подразумевается молча. `doctor` говорит, читаются ли времена создания на этой
платформе вообще, а отчёт каждого скана считает источники, у которых файловая система времени
создания не записала: для них правило работать не может, и это видно числом, а не догадкой.
Имена таких файлов не печатаются, только счётчик.

### Сверка: `index reconcile`

`crosskit index reconcile <directory>` повторяет безопасный обход каталога с той же
политикой и тем же descriptor-relative walker, а после полного достоверного обхода
помечает `missing` те `FileLocation`, которые лежат внутри каталога (граница по
сегменту пути: `/data/docs` не касается `/data/docs-old`), разрешены текущей политикой и
не были увидены в этом запуске. Меняется только `FileLocation.status`: `File`,
`FileVersion`, `FileObservation`, `ContentChunk` и current-state остаются нетронутыми, а
обычный `index init` возвращает вновь появившийся файл в `present`.

Каждый запуск получает durable `ReconcileRun` с монотонным номером, который
одновременно является текущей эпохой наблюдений. Любая запись location, будь то `index
init` или reconcile, штампует эту эпоху в `FileLocation.seen_in_epoch` в той же
транзакции, поэтому финализация хоронит только то, что в последний раз было увидено до
старта run: параллельный `index init` и пересекающиеся reconcile не спорят друг с
другом, а wall-clock время критерием не служит. Кандидаты обрабатываются страницами по
500 в одной транзакции, объём служебных данных не растёт с числом запусков. Запуск
считается incomplete при любой ошибке обхода или записи, нестабильном файле или записи
с non-UTF-8 именем: тогда ни один статус не меняется, run сохраняется как `incomplete`,
а команда печатает причины и завершается с ненулевым кодом. Crash до финализации
оставляет run в `running` и тоже ничего не помечает; подменённый или уже закрытый run
хранилище отвергает.

Каждая location, которую run перевёл в `missing`, дополнительно классифицируется как
relocated, если у того же `File` (та же `file_id`, то есть тот же объект файловой
системы) осталась другая location со статусом `present`, подтверждённая в этом run или
позже и видимая этому run: внутри его каталога и не под `Exclude` его политики. Это
честная классификация по общей identity, а не доказанный OS rename event:
источником истины остаются две связи `LOCATED_AT` с разными статусами, никакого
`RENAMED_TO` не создаётся. Hard link даёт ту же картину и считается так же; удаление
файла с появлением другого файла на новом пути, перенос на другое устройство (другой
`file_id`) и перенос под путь, скрытый `Exclude`, relocation не считаются. Скрытые пути
в отчёте не раскрываются, выводится только счётчик.

Отчёт повторяет счётчики `index init` и добавляет:

```text
Reconciliation completed.
Run: reconcile-run:3
...
Locations marked missing: 1
Relocated locations (same file identity remains present): 1
```

или

```text
Reconciliation incomplete: missing statuses were not updated.
...
Incomplete because of: 1 failed path(s)
```

### Обслуживание истории запусков: `index runs prune`

Каждый `index reconcile` оставляет одну запись `ReconcileRun`, и сама сверка эти записи
никогда не удаляет: ни `index init`, ни `index reconcile` не чистят историю автоматически.

Запись остаётся и от прохода, который **не состоялся**: корень, отказавший до обхода, пишется
как `ReconcileRun` в статусе `failed` с категорией отказа в колонке `failure` (схема v15).
До этого отказ происходил раньше, чем заводилась запись, и причину нельзя было установить
ни тогда, ни потом — этим и кончилось то, что восемь корней одного контекста пятнадцать
этапов стояли пустыми. Категории — те же, которые программа уже типизирует (ADR 0015, 0039);
`status` и `doctor` читают их обратно и называют корень, по которому прохода не было.
Очистка — отдельная явная maintenance-операция:

```bash
cargo run -- index runs prune --keep 10          # только preview, ничего не меняет
cargo run -- index runs prune --keep 10 --apply  # удаляет
```

`--keep <N>` обязателен, принимает целое N >= 0 и означает: для каждого `root` сохранить
N самых новых закрытых run, которые вообще можно удалить. Удаляются только run со статусом
`completed` или `incomplete`. Run в статусе `running` и исторические run схемы v6 со
связью `OBSERVED` не удаляются никогда, в квоту `--keep` не входят и показываются
отдельными счётчиками; связь `OBSERVED` тоже не удаляется. Retention считается для каждого
root отдельно, поэтому активность по одному каталогу не стирает историю другого.
`--keep 0 --apply` удаляет все удаляемые run, защищённые остаются. Повторный `--apply`
идемпотентен.

Очистка не меняет `ReconcileEpoch`, `File`, `FileLocation` (включая `status` и
`seen_in_epoch`), `FileVersion`, `FileObservation`, `ContentChunk` и current-state:
следующий reconcile получает следующий монотонный sequence, id удалённых run не
переиспользуются. Roots и runs читаются keyset-страницами по 500, а все удаления одного
`--apply` выполняются в одной транзакции: ошибка на любой странице откатывает всё.

Отчёт содержит только счётчики, без путей и id:

```text
Reconcile run retention preview (keep 10 per root): nothing was changed.
Eligible closed runs: 12
Protected running runs: 0
Protected legacy OBSERVED runs: 1
Retained runs: 10
Would remove runs: 2
```

С `--apply` первая строка сообщает `retention applied`, последняя — `Removed runs`.
Preview завершается с кодом 0; неверные аргументы и ошибка хранилища — с кодом 1.

### Наблюдение: `index watch`

`crosskit index watch` без каталога наблюдает **весь контекст**; каталог сужает наблюдение до
одного корня. Все корни идут через **один** поток событий: `notify` держит один список путей и
пересобирает единственный поток FSEvents, поэтому цена почти не растёт с числом корней —
измерено, десять корней против десяти watcher'ов это +3 потока против +10 (ADR 0040).

**Корень, который не удалось поставить под наблюдение, не пропадает из индекса.** Проход
покрывает контекст, а не корень, из которого пришла подсказка, поэтому такой корень сверяется
каждым периодическим проходом — теряется задержка, а не покрытие. Watcher говорит об этом
первой же строкой:

```text
Watching: 9 of 10 root(s).
  /Users/alice/Projects/second: no change notifications — the root no longer exists
  Every pass still walks every root of this context, so what these roots lose is the
  latency of an event and not their place in the index.
```

Проба доставки регистрируется **на том же потоке**, что и корни, поэтому она ловит поток,
созданный и не стартовавший, — но по отдельному корню не доказывает ничего, и честной пробы
по корню не существует: она потребовала бы создать событие внутри наблюдаемого дерева
(ADR 0040).

`crosskit index watch <directory>` — foreground-команда, которая работает до Ctrl-C и
держит каталог сверенным. Она рекурсивно подписывается на события файловой системы
(`notify`, на macOS FSEvents), затем выполняет полный reconcile и повторяет его после
каждого объединённого пакета событий. Порядок важен: подписка ставится до первого
прохода, поэтому изменение во время bootstrap-прохода не теряется в окне между scan и
subscribe, а попадает в очередь и вызывает следующий проход.

Сразу после подписки watcher проверяет, что уведомления действительно доставляются:
под собственным наблюдением записывает и удаляет probe-файл в служебном каталоге
`<каталог данных>/watch-probe` и ждёт подсказку до 3 с. FSEvents-стрим может быть создан
и «запущен», но молчать (sandbox без доступа к FSEvents, том без журнала событий), и ОС
об этом не сообщает. Probe подтверждает доставку только для той же файловой системы:
если каталог данных лежит на другом устройстве, чем canonical root, или внутри самого
root, probe-файл не создаётся вовсе, а команда честно стартует в degraded periodic mode и
называет причину без пути. Так же честно она стартует degraded, если подсказка не
пришла. В degraded mode источником истины остаётся периодический reconcile, поэтому
eventual consistency сохраняется.

Probe выполняется в том же стандарте безопасности, что и сканер, descriptor-relative:
служебный каталог и `watch-probe` открываются как каталоги через FD с `O_NOFOLLOW`
(symlink на месте `watch-probe` отклоняется), файл создаётся только через `openat` с
`O_CREAT | O_EXCL | O_NOFOLLOW` и правами `0600` под непредсказуемым именем (существующий
файл или подложенный symlink никогда не перезаписывается, не truncate-ится и не
удаляется), запись идёт в уже открытый FD, удаление — `unlinkat` относительно доверенного
FD каталога и выполняется на каждом пути после создания файла: подсказка пришла, не
пришла или запись не удалась. Оба каталога проверяются через `fstat` открытого FD:
владелец — текущий effective user, группа и остальные без права записи, а `watch-probe`
строго `0700`; иначе probe отказывает категорией `ProbeUnavailable`. Перед `unlinkat`
имя сверяется `fstatat(AT_SYMLINK_NOFOLLOW)` с тем, что было создано: обычный файл с тем
же device и inode. Подменённый под тем же именем файл или symlink не удаляется, probe
завершается безопасной ошибкой. Любая подмена — безопасная ошибка без записи и удаления
чужих файлов. На платформах без этих гарантий небезопасного fallback нет: probe не
выполняется, watch стартует degraded. Ошибка подписки печатается только фиксированной
категорией (root not found, OS denied, resource limit, backend, probe): ни текст ошибки
notify, ни путь, ни тип ошибки ОС не пересекают границу application.

**Каталог без прав внутри корня.** На Linux один такой каталог отвергает рекурсивную
подписку целиком, и события перестают приходить даже по читаемой части дерева; на macOS то
же дерево подписывается без замечаний. Отказывать из-за этого watch не станет: он стартует
в том же degraded periodic mode и называет причину («ОС отказалась наблюдать каталог внутри
корня»). Проход, который идёт следом, обходит весь корень и считает такой каталог как failed
path — ровно как обычная сверка. Почему деградация, а не отказ — ADR 0015.

Событие — только подсказка, reconcile — источник истины. Watcher никогда не читает путь
из события, не пишет по нему в базу, не печатает его и не выводит из него rename:
событие лишь помечает root как dirty, а единственная логика scan → commit → tombstone —
тот же policy-aware `ReconcileService`, что и у `index reconcile`. Поэтому политика
применяется до любых syscalls по записи, а `Exclude`-путь, породивший системное
уведомление, не печатается, не сохраняется и не читается. Симлинки обрабатываются так же,
как в `index init` и `index reconcile`.

Расписание фиксировано и не настраивается:

- trailing debounce 500 мс: проход стартует, когда после последнего события прошло
  500 мс; один пакет событий даёт ровно один проход, проходы идут строго
  последовательно, второй reconcile никогда не запускается параллельно первому;
- периодический проход каждые 300 с даже без событий — страховка от потерянных
  событий; wall-clock файлов в решениях не участвует;
- после incomplete-прохода или ошибки хранилища — повтор с экспоненциальной задержкой
  1 с → 2 с → … → 60 с, сбрасываемой успешным проходом. Incomplete-проход, как и у
  `index reconcile`, не меняет статусы `missing`; watcher остаётся жив и не выдаёт
  ошибку за успех.

Ошибка или переполнение потока событий: состояние сразу считается dirty, выполняется
проход, и watcher переходит в явно обозначенный degraded periodic mode — дальше только
периодические проходы, события больше не считаются достоверными. Граф напрямую не
меняется, процесс не завершается и не сообщает, что event watching всё ещё активен.

Политика загружается один раз при старте; изменение `config.toml` требует перезапуска.

Ctrl-C обрабатывается через `ctrlc`: обработчик только уведомляет цикл. Watcher
перестаёт принимать новые пакеты и, если есть отложенные изменения или ожидающий
retry, выполняет один финальный проход. Успешный финальный проход — код 0 и summary;
incomplete или ошибка — код 1 и безопасное сообщение.

Вывод содержит только lifecycle и счётчики, без путей событий, содержимого и имён
исключённых файлов:

#### Разбор очереди заданий: `[watch] analyze`

По умолчанию watcher очередь не трогает: он сверяет дерево, задания копятся, разбирает их
`index jobs run`. Включается это двумя ключами и только явно — анализ в разрешающем
контексте стоит денег, и watcher, оставленный на ночь, не должен тратить их без разрешения:

```toml
[watch]
analyze = true
analyze_limit = 20
```

`analyze = true` без `analyze_limit` — **ошибка загрузки**, а не умолчание: умолчание здесь
было бы решением программы о том, сколько чужих денег стоит один проход. `analyze_limit = 0`
тоже отвергается — это «выключено», у которого уже есть спеллинг. Без обоих ключей watcher
работает ровно как до этапа 16, и слова `Analysis` в его выводе нет.

Что при этом происходит:

- разбор идёт **после каждого прохода, который завершился**. Проход, который не смог
  поручиться за диск, не закоммитил ревизий и не породил заданий;
- финальный проход при Ctrl-C очередь не разбирает совсем: человек, попросивший
  остановиться, не просит сначала потратить деньги. Очередь переживает остановку;
- Ctrl-C **во время** разбора берётся, когда текущий разбор закончится. Поэтому разбор и
  ограничен: `analyze_limit` — одновременно предел трат за проход и предел того, сколько
  watcher продолжает работать после просьбы остановиться. К моменту выхода каждое взятое
  задание уже либо `done`, либо обратно в очереди; захват, оставшийся от **убитого**
  процесса, возвращает аренда;
- правила раздела «AI-анализ» действуют целиком: запрещающий контекст — детерминированный
  обработчик, ключа нет — причина названа один раз в стартовом уведомлении и **ни одно
  задание не захвачено**. Watcher из-за этого не останавливается и не замолкает;
- отказ разбора (отказ хранилища) не ломает наблюдение: проход остаётся завершённым,
  watcher говорит, что анализ не удался, и продолжает;
- бюджет `max_run_bytes` — бюджет **одного разбора**, как и у одной команды
  `index jobs run`: обработчик строится внутри каждого разбора. Иначе watcher, проживший
  сутки, посреди ночи перестал бы анализировать и потратил бы оставшиеся попытки каждого
  задания на отказ «бюджет исчерпан», после чего они стали бы `dead`.

**Про память.** Этап 16 измерил, что watcher с `analyze_limit = 20000` на очереди из 10 000
заданий убивало ядро под 1 GiB, и что `index jobs run --limit 20000` в своём процессе умирал
так же — то есть дело было не в watcher'е, а в том, сколько заданий обрабатывает один процесс.
Этап 17 нашёл причину и убрал её: работник складывает журнал движка каждую тысячу заданий, и
тот же сценарий проходит целиком (раздел «Память», ADR 0023). `analyze_limit` остаётся
денежным пределом, памятным он больше не является.

```text
Watching /Users/me/notes (event-driven mode). Press Ctrl-C to stop.
Policy file: /Users/me/Library/Application Support/Crosskit/config.toml
Debounce: 500ms; periodic reconcile every 300s even without events.
Analysis: model claude-haiku-4-5-20251001; at most 20 job(s) per pass.
Pass 1 (bootstrap) completed: indexed 12 file(s) and 12 chunk(s), 0 metadata-only, 1 excluded, 0 marked missing, 0 relocated.
Pass 1 analysis: 12 claimed, 12 done, 0 failed, 0 skipped, 0 left in the queue.
Stopping: nothing pending.
Watch stopped.
...
Analysis sweeps: 1 (0 could not run)
Jobs claimed: 12; done: 12; failed: 0; skipped: 0; left in the queue: 0
```

Путей, содержимого и id в этих строках по-прежнему нет — только счётчики. `skipped` — это
доля лимита, которая ничего не купила: задания, которых больше не просит ни одно правило.
Когда она не ноль, watcher один раз за сессию называет `index jobs withdraw` и говорит, что
сам уборку не делает. Подробности и принятые решения — ADR 0022, ADR 0031.

Точный OS rename/move и связи `RENAMED_TO`/`MOVED_TO`, прямые записи `FileLocation` из
watcher, durable per-path `IndexJob`, daemon/IPC и hot reload конфигурации — будущие
этапы. `WatchRun` в базе не создаётся: отчёт watch живёт только в памяти процесса.

### Фоновая служба: `crosskit service`

`index watch` живёт, пока открыт терминал. **Служба** делает то же самое для **всех**
контекстов сразу, без терминала: стартует при входе в систему (агент launchd), после сбоя
поднимается снова и отвечает одной командой, что с ней.

```bash
crosskit service install     # показывает всё, что запишет, спрашивает [y/N], ставит и запускает
crosskit service status      # работает ли, с какого времени, какая сборка, и каждый контекст
crosskit service logs        # где журнал и его последние строки
crosskit service stop        # остановить до следующего входа или `service start`; агент остаётся
crosskit service start       # запустить снова
crosskit service restart     # скопировать эту сборку, перечитать конфигурацию, запустить заново
crosskit service uninstall   # остановить, удалить агент и копию программы; данные не трогаются
```

Внутри — один процесс и по потоку на контекст; каждый поток делает ровно то, что
`crosskit --context <имя> index watch`. Контекст, который не открылся (его базу держит
терминальный `index watch`, схема старая), ждёт и пробует снова раз в минуту — остальные
работают.

**Программа — копия.** `install` копирует запустившую его программу в
`…/Crosskit/bin/crosskit`, и служба работает на копии: `cargo build` переписывает
`target/release/crosskit` на месте, и служба на нём работала бы на чём придётся. После новой
сборки `status` говорит, что служба на старой, а `crosskit service restart` копирует новую и
перезапускает. Конфигурация тоже читается при старте: новый корень или контекст — тоже
`restart`, и `status` пишет «changed after the start», пока его не сделали.

**Модель без разрешения не зовётся.** Очередь разбирается, только если в конфигурации
`[watch] analyze = true` и `analyze_limit` (раздел выше); `install` говорит это до вопроса,
журнал и `status` — у каждого контекста.

```text
Service: running since 2026-10-13 09:30:12Z (2 h 5 min ago), process 4242.
Program: /Users/me/Library/Application Support/Crosskit/bin/crosskit, build of 2026-10-13 09:12:40Z.
Configuration: /Users/me/Library/Application Support/Crosskit/config.toml, unchanged since the start.
Journal: /Users/me/Library/Application Support/Crosskit/service/service.log

Context work: watching on change events, since 2 h 4 min ago
  Roots: 22
  Last pass: 40 s ago — Pass 31 (events) completed: 22 root(s), indexed 26125 file(s) and …
  Passes: 30 completed, 1 incomplete, 0 failed.
  Analysis: off — `[watch] analyze` is not set, so the queue is not worked and no model is called.
```

Что ещё нужно знать:

- **Пока служба работает, она — единственный писатель.** Пишущая команда (`index reconcile`,
  `index jobs run`, `migrate`, `index recover`) спрашивает «Stop the service while this
  command runs? [y/N]» и на «да» останавливает её, а когда команда закончится — как угодно,
  хоть по Ctrl-C, — служба запускается снова. Без того, кто ответит (скрипт, закрытый ввод),
  — прежний отказ с подсказкой. Руками: `crosskit service stop` и `crosskit service start`
  (агент остаётся, при следующем входе служба стартует сама).
- **Защищённые папки macOS.** Процесс из launchd не наследует доступа терминала к Documents,
  Desktop и Downloads. Такой корень `status` называет (`not-permitted`) и говорит, кому дать
  Full Disk Access.
- **Старт подписки ограничен 30 с.** Не ответила — контекст работает по таймеру, причина в
  `status`.
- **Проходит только изменённое.** Пути событий говорят, где искать: проход после правки
  обходит каталоги, в которых она была, а не все корни контекста. Весь контекст служба
  обходит при старте, при любом признаке потерянных событий и раз в 30 минут. На копии `work`
  правка находится в поиске через 1,2 с (p50), 1,6 с (p95). Между проходами по событиям — пауза
  3 с, и пачка правок ждёт тишины не дольше 5 с (ADR 0050).
- **Журнал** пишет сама служба: те же строки, что `index watch`, со временем и именем
  контекста, без содержимого файлов. Не больше двух файлов по мегабайту.
- **Лимит открытых файлов.** launchd даёт агенту 256 открытых файлов, и 30 октября служба в
  них упёрлась посреди контрольной точки. Теперь при старте она поднимает свой лимит до
  10 240 и пишет это первой строкой журнала (ADR 0060).

**Чтение через службу.** `search`, `graph` и `knowledge map` с `--json` и панель сначала
спрашивают сокет службы (`…/Crosskit/service/crosskit.sock`): служба отвечает той же строкой
из графов, которые уже держит, — без `busy` и без открытия базы на каждый запрос. Нет службы
или контекст она сейчас не держит — команда отвечает сама, как раньше. На копии `work`: 0
`busy` из 4 723 запросов с правками и без них (до этого — 3,2 % и 27 %). `ask` через службу не
идёт: он зовёт модель, а служба сама к модели не ходит. Протокол — ADR 0050.

Задачи служба тоже отдаёт: `tasks --json`, реплики задачи (`task-speech`) и её карту
(`task-map` — та же строка, что `tasks map <задача> --json`). Карту служба только показывает:
`--build` и `--join` зовут модель и идут командой. Отсюда desktop-приложение берёт всё, что
показывает (ADR 0059).

Тесты launchd не трогают: `launchctl` подменён сценарием, `HOME` — песочница
(`tests/cli_service.rs`, `tests/cli_service_changes.rs`). Решения и замеры — ADR 0049 и
ADR 0050.

### Очередь обогащения: `index jobs`

Каждый сохранённый evidence commit (`FileVersion` с observation и chunks) в той же
транзакции создаёт durable `InsightJob` — запись о том, что для этой неизменяемой ревизии
есть ожидающая задача enrichment. Job выводится детерминированно из `FileVersion`:
`id = insight-job:insight-outbox-v1:<FileVersion.id>`, `source_revision_id`,
`input_content_hash`, `pipeline_version`, `state = queued`, `revision_observed_at_unix_ms`
— момент, когда граф впервые увидел эту ревизию.
Он не содержит путь, имя файла, событие, текст chunk или raw error, и связан с ревизией
`FileVersion -[:REQUESTS_INSIGHT]-> InsightJob`.

Инварианты: location, version, observation, chunks, current state и job публикуются
атомарно, ошибка outbox откатывает весь commit; metadata-only commit job не создаёт;
для одной ревизии и версии pipeline ровно один job; повторное наблюдение или retry той же
ревизии не дублирует job и не переписывает его `state` и место в очереди; новая ревизия даёт
новый job; watcher ничего не пишет напрямую — job появляется только через reconcile,
сохранивший evidence. Миграция v8 ставит в очередь job для всех уже существующих
ревизий keyset-страницами, не меняя evidence и current state.

```bash
cargo run -- index jobs
```

```text
Context: work
Insight jobs queued: 12
Insight jobs claimed: 0
Insight jobs done: 34
Insight jobs failed: 0
Insight jobs dead: 0
```

Команда печатает только агрегаты: ни пути, ни id, ни хеша в выводе нет.

### Приведение очереди к правилам: `index jobs withdraw`

Проверка политики при захвате остаётся: правила меняются между проходами, и захват обязан
спрашивать. Но одного её недостаточно. `--limit` ограничивает **захваченное**, а платит
только **выполненное**: очередь, набранная до того, как исключения узнали машину, выдаёт
страницы заданий, которые ничего не стоят и при этом съедают лимит, заведённый ради денег.
На дереве владельца `index jobs run --limit 20` дал `Claimed 20, Completed 3, Skipped 17` —
чтобы добраться до 1 703 документов таким способом, команду пришлось бы запустить 86 раз.

Поэтому тот же вопрос задаётся один раз и по всей очереди:

```bash
cargo run -- index jobs withdraw
```

Пример вывода; числа здесь выдуманные, чтобы их не приняли за измерение:

```text
Context: work
Queued jobs examined: 4210
Withdrawn (no rule asks for them any more): 3640
Still queued: 570
```

Это обратная сторона постраничного наполнения задним числом, которым `index review approve`
ставит задания для уже существующих ревизий: страница читается, страница пишется, каждая —
отдельная транзакция, так что прерванный проход оставляет целые страницы, а следующий их
дописывает. Правило «нужно ли ещё это задание» — одно и то же для захвата и для прохода: хоть
один присутствующий путь, который политика допускает и покрывает правило анализа.

Отозванное задание ничего не стоило: попытка не считалась, модель не вызывалась. Состояние —
тот самый `skipped` из этапа 21, единственное обратимое: проход, снова увидевший путь,
возвращает задание в очередь. Ничего не отправляется наружу и ни один файл не читается,
поэтому команда работает без движка и без ключа (ADR 0031).

### Исполнение заданий: `index jobs run`

Задание проходит `queued → claimed → done`, либо `claimed → failed` и снова в очередь,
пока не кончатся попытки; после этого оно `dead` с категорией причины и само в очередь
не возвращается. Каждый переход — отдельная транзакция.

```text
                      ┌────────── worker пропал ──────────┐
                      │        (срок аренды истёк)        │
                      ▼                                   │
   queued ────claim────► claimed ────результат────► done  │
     ▲   ▲                  │                             │
     │   └──────────────────┴─────────────────────────────┘
     │                      │
     │                  отказ обработчика
     │                      ▼
     └──── попытки есть ── failed ── попытки кончились ──► dead
```

Один проход делает три вещи по порядку. Сначала **возврат**: задания, которых никто не
держит — захваченные с истёкшей арендой и отказавшие — либо снова встают в очередь, либо
становятся `dead`, если попытки кончились. Затем **захват**: страница заданий, раньше в ней
идёт та, чья ревизия **раньше наблюдалась**, не больше `--limit` (порядок — ADR 0030). Затем
**работа**: обработчик вызывается вне транзакции, записывается только исход.

Аренда — абсолютный момент в базе, а не таймер в процессе. Поэтому убитый worker не
держит задание навсегда: возврат решается по сроку, а не по тому, жив ли процесс, и
переживает перезапуск. Попытка считается **в момент захвата**, иначе задание, которое
убивает процесс, никогда не дошло бы до предела.

```bash
cargo run -- index jobs run --limit 100
```

```text
Context: work
Returned to the queue: 1
Retired as dead: 0
Claimed jobs: 12
Completed jobs: 11
Failed jobs: 1
Knowledge: 61 facts kept of 104 proposed — 6 rejected because the quote is not in its part, 35 because it does not name both ends, 2 otherwise; 52 entities, 4 spellings glued
Cost: 11 calls (0 answered from the cache), 183520 bytes sent, 401233 input and 31870 output tokens, $2.9011 as the engine reported it
```

#### Разобрать нужную папку, а не старейшее

Очередь берёт старейшие ревизии первыми (ADR 0030), и на настоящем дереве это редко то, что
нужно сегодня: первые 15 заданий `work` оказались документацией чужого публичного клона. Каталог
называется прямо:

```bash
# документы под каталогом — только их задания, в прежнем порядке
crosskit --context work index jobs run --under ~/Projects/erp/45-registry --limit 20
# беседы, которые правили файлы этого каталога или где вы их называли (те же пары, что `touches`)
crosskit --context work index jobs run --touching ~/Projects/erp/45-registry --limit 10
```

```text
Selected: 14 revisions under /Users/me/Projects/erp/45-registry; 14 of them queued
…
Cost: 14 calls (0 answered from the cache), 251300 bytes sent, …, $2.0410 as the engine reported it
```

Остальная очередь не трогается. Каталог вне контекста — отказ до любого вызова. Из бесед берётся
текущая ревизия транскрипта; у беседы задание есть, только если правило анализа её покрывает —
умолчание разбирает `.md` и `.txt`, беседам нужна маска `**/*.jsonl` (`crosskit index review`),
иначе строка `Selected:` так и скажет: `0 of them queued`. Путь, записанный в беседе
относительно, `--touching` не находит.

**Сколько стоит.** Перед прогоном — `crosskit knowledge`: строка `Rate:` даёт цену вызова и
цену 100 КБ, снятые с уже оплаченных вызовов этого контекста. На первых 15 заданиях `work` вышло
$0,08 и около 27 с на вызов; папка из 20 документов по 10 КБ — около $1,7 и девяти минут. Каждый
вызов несёт ≈ 25 тыс. токенов собственных инструкций инструмента, поэтому двадцать коротких
документов стоят дороже одного длинного того же объёма. Цена — прейскурантная, у подписки это
квота.

#### Беседы этой папки — и только они

Беседы по умолчанию не разбираются (правило берёт `.md` и `.txt`). Одобрить ровно те, что
правили файлы папки или где вы их называли, — одной командой, с ценой до записи:

```bash

```

```text
To approve: the 7 conversation(s) that worked on files under /Users/me/Projects/erp/45-registry — 7 transcript(s), 1193 parts, 1166188 bytes; asking them is 7 call(s), about $5.8033 and at least ~3 min (longer inputs than the time was measured on) at this context's rate (15 paid calls)
Of them 5 over 40 parts (the largest 270): a run holds them back until it is given --allow-large or --max-parts.
Of them 3 larger than one job may send (200000 bytes, `[insight] max_input_bytes`): they will be refused, not sent, unless the limit is raised first.
An approved conversation is asked again every time it grows: each new revision of its transcript is a new job.
Approve these 7 transcript(s) for analysis and write it to …/config.toml? [y/N]
```

Пишется по маске на транскрипт, не `**/*.jsonl`. `--yes` отвечает «да» заранее.

#### Большое задание ждёт явного «да»

Ревизия длиннее 40 кусков — беседа на сотни реплик — остаётся в очереди, а прогон называет её
цену: `Held back: 1 job(s) over 40 parts — 270 parts, … about $… They stay queued`. Взять:
`--allow-large`; сдвинуть порог: `--max-parts <N>`. Наблюдатель такие задания не берёт никогда.
Бюджет в байтах на задание (`[insight] max_input_bytes`, 200 КБ) действует отдельно: больше
него задание не отправляется вовсе. Кусок беседы весит свой текст в байтах.

#### Переспросить: `index jobs requeue`

Когда меняется вопрос модели (с этапа поправки — `revision-knowledge-tool-v2`: цитата обязана
называть оба конца), уже разобранное отвечено на прежний. Вернуть его в очередь с ценой:

```bash
crosskit --context work index jobs requeue --under ~/Projects/erp/45-registry
crosskit --context work index jobs run --under ~/Projects/erp/45-registry --limit 20
```

Без каталога — всё разобранное под прежним вопросом. Знания ревизии стоят, пока новый ответ их
не заменит.

#### Пересчёт без модели: `index jobs recheck`

Когда правило, что доказывает факт, меняется, уже записанные факты с ним не меняются сами.
`recheck` берёт каждую разобранную текущую ревизию, достаёт её ответ из кэша и проверяет заново
против её кусков — модель не вызывается, ничего не отправляется:

```text
Rechecked: 15 revisions from their cached answers (0 had none, 0 could not be read); no model was asked
Facts: 185 → 41
Knowledge: 41 facts kept of 193 proposed — 3 rejected because the quote is not in its part, 144 because it does not name both ends, 5 otherwise; 60 entities, 0 spellings glued
```

Две последние строки прогона — у контекста, который разрешил отправлять содержимое: что из ответов
сохранено как знание и что это стоило (раздел «Знания: `knowledge`»). Перед захватом каждый
прогон снимает факты ревизий, которые заменила новая.

Инварианты: захваченное задание не выдаётся второму worker'у; отказ обработчика не пишет
ничего, кроме состояния и категории; у задания не может быть двух результатов — это
свойство схемы (`InsightResult` с выводимым из задания id и связь `HAS_INSIGHT_RESULT`
как `ONE_ONE`), а не проверка в коде; ни один запрос не материализует очередь целиком;
переиндексация файла во время работы worker'а не трогает ни состояние захваченного
задания, ни его аренду, ни попытки.

Категории отказа закрыты: `input` — граф не держит того, что называет задание,
`handler` — обработчик не смог сделать работу, `lease-expired` — захват кончился раньше,
чем worker. Текста движка, текста провайдера и содержимого файла в них нет.

Обработчик — порт, и обработчиков два. Какой из них вообще может существовать, решает
контекст — см. следующий раздел.

### AI-анализ: что контекст разрешил

**Умолчание — запрет.** Содержимое файлов покидает машину только в том контексте, который
это явно разрешил:

```toml
[workspace.work]
include = ["~/Work"]
# строки нет — значит содержимое этого контекста наружу не уходит

[workspace.research]
include = ["~/Research"]
send_content_outside = true
```

Это не флаг, который где-то проверяется. Разрешение — значение (`ContentEgressPermit`),
которое запрещающий контекст не может произвести, а обработчик модели, исходящий запрос и
функция, достающая текст чанков из графа, требуют его по значению. **В запрещающем
контексте этих трёх объектов не существует**, поэтому собрать вызов не из чего.

Что делает `index jobs run`, зависит от контекста и наличия ключа:

| Контекст | `ANTHROPIC_API_KEY` | Что происходит |
| --- | --- | --- |
| не разрешил выход | любой | детерминированный обработчик: считает чанки, наружу ничего |
| разрешил | есть | модель называет тему ревизии |
| разрешил | нет | причина печатается один раз, выход 0, **ни одно задание не захвачено** |

Последняя строка — намеренно. Захват потратил бы попытки на вызов, которого не будет, а
тихий откат к счёту закрыл бы задание навсегда: `done` повторно не анализируется.

Ровно та же таблица действует для `index watch` с включённым `[watch] analyze`: обе команды
идут в очередь через одну композицию, поэтому правило, решающее, какой обработчик вообще
существует, написано один раз и разойтись между ними не может.

```toml
[insight]
model = "claude-haiku-4-5-20251001"  # умолчание: датированный снимок, не подвижный алиас
effort = ""                          # пустая строка убирает поле из запроса
max_input_bytes = 200000             # предел на одно задание
max_run_bytes = 20000000             # предел на один прогон
```

Умолчание выбрано под нагрузку: очередь на настоящем дереве — десятки тысяч заданий, а
ответ на каждое — одна строка темы по схеме из двух полей. На корпусе со средним файлом
11 765 байт десять тысяч ревизий стоят примерно $31 против $198–266 на модели верхнего
уровня. `effort` пуст, потому что модель умолчания этот параметр не принимает; модель, где
он уместен, задают вместе с ним. Расчёт, цены и то, что о качестве ещё не измерено, — в
ADR 0010.

Прогон очереди ограничен всегда: `--limit <N>` обязателен, а `max_run_bytes` держит второй
предел — по байтам. Безлимитного умолчания нет, поэтому первый запуск на большом дереве не
может обернуться неожиданным счётом.

Ключ читается только из переменной окружения `ANTHROPIC_API_KEY` — конфиг копируют, диффят
и вставляют. Адрес сервиса — константа в программе, не настройка.

**Строгая схема, дважды.** В запросе идёт JSON-схема `{topic, confidence}`, и всё, что
пришло, потом проходит доменный конструктор: тема — непустая строка не длиннее 120
символов, одна строка без управляющих символов; уверенность — число в `0..=1`. Второй
контроль и есть граница: ограничение длины не опрятность, а то, что не даёт содержимому
файла попасть в граф под видом метки. Сырой ответ не сохраняется и не печатается.

**Бюджеты в байтах, а не в токенах.** Байты известны точно и до чтения — граф хранит
диапазон каждого чанка, поэтому задание сверх предела отвергается, не загрузив содержимое.

**Кэш по входу.** Ключ — отпечаток содержимого, версия конвейера, модель и версия запроса.
Два файла с байт-в-байт одинаковым содержимым — один вопрос и одна оплата. Кэш лежит в базе
контекста, поэтому ответ, купленный для одного контекста, другому недоступен.

**Категории отказов** ложатся в жизненный цикл: `unavailable`, `budget-spent`, `handler` и
`lease-expired` повторяются; `schema`, `refused`, `input-too-large` и `input` уходят в
`dead` сразу, не тратя оставшиеся попытки на тот же конец. Ни текста провайдера, ни
промпта, ни содержимого — ни в записи задания, ни в выводе. Границу между двумя половинами
проводит одно правило: окончателен только отказ, означающий, что **ответ не подходит**;
отказ, означающий, что **мы не смогли его прочитать**, повторяем — `dead` не отменяется
ничем, поэтому лишний повтор дешевле лишних похорон (ADR 0033).

Подробности и принятые решения — ADR 0005, ADR 0009, ADR 0010 и ADR 0033.

### Поиск: `search`

```bash
cargo run -- --context work search "обход индекса"
cargo run -- search обход индекса --limit 5
cargo run -- search обход --after document:3e64d717:file:unix:16777230:16043440@sha256:03f2…
cargo run -- search обход --include-missing
```

**Одна строка — один файл.** Сколько бы мест внутри файла ни совпало, файл занимает в выдаче
одну строку: показывается то совпадение, которое оценено выше всех, и строка говорит, сколько
мест в этом файле нашлось ещё. Страница из пяти строк — это пять разных файлов.

#### Беседы: что индексируется и как их спрашивать

Транскрипт сессии Claude Code (`.jsonl`) читается не как текст, а как беседа: в индекс идут
**реплики**, а имя беседы становится отдельным документом. Вывод инструментов, вложения,
размышления модели и построчная обвязка не индексируются вовсе — на дереве владельца это
2,46 % байтов вместо ста, и `chats` ужался с 49 662 чанков до 6 990.

```bash
crosskit --context chats search "Беседа Е"      # по имени беседы
crosskit --context chats search "взаимозачёты"          # по словам реплик
crosskit --context chats search "text:контрагенты"      # только по телу реплик
crosskit --context chats search "conversation_name_prefix:долги"  # только по имени
```

Имя беседы индексируется отдельным полем `conversation_name_prefix` — по первым пяти буквам
слова, без морфологии: опечатка ломает морфологию (`разборали` → `разбора`, а имя даёт
`разбор`), а первые пять букв её переживают. Поле весит в запросе больше тела, и вес этот
большой не потому, что имя важнее, а потому, что BM25 считает короткое поле, которого нет у
99 % документов, очень длинным и придавливает его ровно во столько же раз (ADR 0038).
Обычный запрос без `поле:` спрашивает оба поля сразу, и знать про них не нужно.

Второе поле имени, через морфологию, здесь было и удалено этапом 33: померенное отдельно, оно
не дало ничего сверх префиксного.

Имя берётся из двух строк транскрипта: собственное имя владельца (`custom-title`) бьёт имя,
которое дала модель (`ai-title`); между двумя именами одной стороны побеждает последнее.

Беседа также записывает, **какие файлы трогала и с каким глаголом** — `read`, `wrote`,
`edited`. Команды `crosskit` для вопроса «в каком чате трогали этот файл» пока нет: факт в
графе есть, спросить его из терминала нечем.

#### Период: «на прошлой неделе», `--since`, `--until`

```bash
crosskit --context work search "сверка на прошлой неделе"
crosskit --context work search сверка --since 2026-09-21 --until 2026-09-27
```

```text
Context: work
Query: сверка на прошлой неделе
Period: 21–27 Sep 2026 (last week, Mon–Sun, local time)
Looked for: сверка
Results: 2 (at most 10 a page)
1. [present] /Users/alice/.claude/projects/-Users-alice-Projects-payments-api/9c21….jsonl
   event: reply 2026-09-23 12:00
   …
2. [present] /Users/alice/Projects/payments-api/ledger.md
   event: edited 2026-09-23 12:05
   …
```

**Период вычисляет программа, а не модель**, и печатает его первой строкой после запроса —
человек видит, как его поняли, раньше, чем читает выдачу. Неделя — с понедельника по
воскресенье, сутки — от местной полуночи; смещение пояса берётся у машины (`localtime_r`,
переменная `TZ` его меняет). Фразы — закрытый перечень данными рядом с языковыми пакетами
(`src/infrastructure/search/language_packs/periods/`): «сегодня», «вчера», «на этой / прошлой
неделе», «в этом / прошлом месяце», «в сентябре» (ближайший начавшийся) и то же по-английски.
Фраза, которой в перечне нет, периодом не считается. **Слова фразы не ищутся**: «сверка на
прошлой неделе» ищет `сверка` среди того, что было на прошлой неделе, и строка `Looked for`
это показывает. `--since` и `--until` — дни включительно; `--since` без `--until` — до конца
сегодняшнего дня; `--until` без `--since` отвергается. Флаг вместе с фразой — побеждает флаг,
и строка периода называет отложенную фразу.

**В период файл попадает только через событие со своим временем**: реплику беседы, сказанную в
нём, или касание файла беседой в нём — запись, правку или упоминание владельцем (строгое
правило `touches`, ADR 0041). Когда файл увидел индексатор, событием не считается: иначе
переиндексация сделала бы «свежим» всё дерево. У каждой строки выдачи печатается событие,
которое её туда поставило, в местном времени. Из беседы, шедшей несколько недель, в период
попадают только реплики этого периода. Если в периоде нет ничего подходящего, так и
говорится — выдачи из другой недели взамен нет.

Индекс для этого не перестраивается: время живёт в графе, а отбор делается внутри
ранжирования, до свёртки по файлу (ADR 0043). Запрос без периода работает ровно как раньше.

**Чего период не показал, он называет.** Беседа, которая переросла предел содержимого после
индексации, остаётся в графе прежней ревизией, и сказанное в ней позже не найти. Беседа с
репликой без записанного момента не может поставить такие куски в период. В обоих случаях
перед выдачей печатается одна строка `Not shown: …` — сколько и почему, — и та же строка
уходит модели в `ask`.

Поиск работает внутри одного контекста, по текущим версиям файлов. Слова вне опций
составляют запрос и соединяются пробелом, поэтому кавычки нужны только там, где их требует
сама оболочка. Понимаются слова, `"фраза целиком"`, `+обязательное`, `-исключённое`, `AND`,
`OR` и `поле:слово`; запрос, который прочитать нельзя, отвергается, а не расширяется до
того, который прочитать можно. Ранжирование — то, что даёт библиотека (BM25); своего
ранжирования здесь нет.

Строка результата говорит пять вещей: состояние файла, путь, фрагмент текста, на котором
совпало лучше всего, слова, по которым совпало, и — если мест было больше одного — сколько
их было ещё. Ниже — вывод `search "обход индекса" --limit 2 --include-missing`, поэтому в нём
виден и файл, которого уже нет на диске:

```text
Context: work
Query: обход индекса
Results: 2 (at most 2 a page)
1. [present] /Users/alice/Projects/notes/reconcile.md
   Сверщик обходит индекс и сообщает об удалённых локациях
   matched: обходит, индекс
   and in 3 more places in this file
2. [missing] /Users/alice/Projects/notes/old-plan.md
   прежний план обхода индекса, файла больше нет на диске
   matched: обхода, индекса
Next page: --after document:3e64d717:file:unix:16777230:16043440@sha256:03f2…
```

**Как оценивается строка.** Файл стоит своего лучшего совпадения, а каждое следующее стоит
всё меньше — то же допущение, которое BM25 делает про слово, повторённое внутри одного
фрагмента, только применённое к фрагментам одного файла. Поэтому беседа, где слово повторено
четыреста раз в одной реплике, не обходит беседу, где оно сказано в трёх разных, а беседа на
две тысячи реплик не выигрывает длиной: сколько бы совпадений ни было, они дают не больше
2,2 от лучшего.

**Пагинация — keyset.** Курсор — это место строки в порядке (оценка и идентификатор файла), а
не её номер в списке. Поэтому страница два стоит столько же, сколько страница один; один и
тот же запрос с одним и тем же курсором даёт тот же ответ; и файл не может появиться дважды
или пропасть из-за того, что два файла получили равную оценку. Чего курсор не переживает —
изменения индекса под ним: оценка зависит от того, что ещё лежит в индексе. Курсор начинается
со слова `document:`; курсор прежнего вида, называвший фрагмент, отвергается, а не читается
как чужой.

**Очень широкий запрос.** Свёртка держит счётчик на каждый файл, в котором запрос совпал, и
таких файлов не больше ста тысяч на запрос. Запрос, дошедший до этого потолка, отвечает
строкой «This query matches in more files than one answer folds…»: страница собрана из тех
файлов, которые свёртка удержала, и она об этом говорит, а не молчит.

**Исчезнувшие файлы.** Файл, у которого не осталось ни одной локации, сохраняет свои
документы. По умолчанию его в выдаче нет, а строка внизу говорит, сколько совпадений
скрыто; с `--include-missing` он есть и помечен `[missing]`. Содержимое в графе осталось,
файла на диске нет — это разные вещи, и выдача их не путает.

**История поиском не покрывается.** В индексе — документы текущей версии файла; появилась
новая текущая, документы прежней исчезают. Размер индекса поэтому ограничен числом файлов,
а не числом правок.

**Отбор по языку файла — по имени, а не по содержимому.** У документа есть поле
`source_language`, заполненное по суффиксу пути. Спрашивается оно тем же синтаксисом
запроса, который уже был:

```bash
cargo run -- --context work search source_language:python
cargo run -- --context work search "обход" AND source_language:php
```

Языков четырнадцать, и перечень закрыт: `php`, `yaml`, `python`, `javascript`, `html`,
`vue`, `typescript`, `markdown`, `go`, `volt`, `css`, `json`, `rust`, `scss`. Читается
последний суффикс без учёта регистра, поэтому `worker.d.ts` — `typescript`, а
`archive.tar.gz` — ничто. Файл, суффикс которого в таблице не назван (`.sql`, `.sh`,
`.toml`, файл без расширения), поля **не получает вовсе**: запрос по языку его не находит,
и значения-заглушки «неизвестно» в индексе нет — отсутствие честнее.

Это вывод из имени, а не факт о содержимом, и тип в коде называется так же прямо. Файл с
расширением `.py`, в котором лежит что угодно другое, всё равно будет `python`: Crosskit
не открывал его ради этого ответа и не утверждает большего, чем сказало имя. Таблица
суффиксов версионирована, и её версия входит в самоописание индекса, поэтому документы,
размеченные прежней таблицей, отличимы от размеченных нынешней.

Пользы сегодня ровно одна: отобрать файлы одного языка запросом, а не обходом дерева. Она
нужна тому, что будет — разбору синтаксиса, которого ещё нет, — и в этом этапе не появилось
ни одной грамматики, ни одной новой границы чанка (ADR 0035).

**Приватность.** Индекс лежит в каталоге на контекст (`search-<контекст>` рядом с
`graph-<контекст>.lbug`) — межконтекстного индекса не существует, как не существует
межконтекстной базы. В самом индексе только термины и идентификаторы: ни путей, ни текста,
ни статусов. Путь, фрагмент и состояние читаются из графа в момент ответа, поэтому путь,
который политика перестала допускать, не может быть напечатан — его нет в индексе, и
политика спрашивается заново. Сколько совпадений скрыто политикой, выдача говорит числом,
не называя ни одного пути. Каталог данных Crosskit встроенно исключён из индексации: иначе
контекст, покрывающий домашний каталог, индексировал бы собственную базу и собственный
индекс, а каждая запись в индекс выглядела бы как изменение на диске.

**Языки объявляются, а не угадываются:**

```toml
[search]
languages = ["ru", "en", "kk"]
```

Умолчание — `["ru", "en"]`. Казахский сборка несёт, но по умолчанию не объявляет: объявить
его значит сменить анализатор индекса и перестроить его, и это решение владельца корпуса.
Имя языка, которого в сборке нет, — ошибка загрузки конфигурации для любой команды, а не
молчаливый пропуск.

**Язык — это файл данных, а не ветка в коде.** Пакет описывает язык целиком: имя, версию
правил, письменность, алфавит, буквы-улики и способ приведения к основе — алгоритм Snowball
или список окончаний по слоям. Русский и английский описаны такими же файлами, как
казахский; добавление языка — это файл, а не правка кода. Пакет, который нельзя прочитать,
не загружается молча: отказ называет пакет и причину.

Нормализация выбирается **на токен, по буквам самого токена**:

| что в токене | кто нормализует |
| --- | --- |
| буква, которой нет у других объявленных языков той же письменности (`қ`, `ә`, `ң`) | только этот язык |
| букв-улик нет, но написать могли несколько объявленных языков этой письменности | все они; каждая различная основа идёт в индекс на одну позицию (не больше четырёх) |
| буквы, которых никто не объявлял, или две письменности в одном токене | никто: токен идёт точной формой |

Вторая строка — то, ради чего всё это: слово из русских букв мог написать и русский, и
казахский, и документ находится по любому из прочтений. Запись расширяется, **вопрос — нет**:
несколько терминов в одной позиции разбор вопроса читает как фразу, а фраза из двух прочтений
одного слова не совпадает ни с чем (полнота по русскому падала 0.95 → 0.39). Вместо этого
вопрос разбирается по разу на прочтение, и разборы соединяются через «или».

Что это стоит на текстах этого репозитория (1.63 МБ) и на корпусе 10 407 файлов:

| | индекс | к тексту | полнота / точность RU | полнота / точность EN |
| --- | ---: | ---: | --- | --- |
| `ru, en` | 0.64 МБ | 0.39× | 0.95 / 0.94 | 1.00 / 0.99 |
| `ru, en, kk` | 0.76 МБ | 0.47× | 0.95 / 0.94 | 1.00 / 0.99 |

Русский и английский не просели. Запрос к индексу: медиана 215 → 260 мкс (страница ответа —
около 5 мс, из них 4 мс — чтение графа).

На корпусе 10 407 файлов, контейнерный прогон под 1 GiB, тот же сценарий с обоими
восстановлениями:

| фаза | `ru, en` | `ru, en, kk` |
| --- | ---: | ---: |
| A холодная `index init` | 33.4 с | 34.9 с |
| B холостая сверка | 53.6 с | 55.6 с |
| C после мутации | 66.6 с | 71.2 с |
| D после reopen | 57.4 с | 62.0 с |
| индекс на диске | 3.1 МиБ (0.22×) | 3.3 МиБ (0.23×) |
| целая команда `search` | медиана 75.9 мс | медиана 77.1 мс |
| перестроение индекса | 1.04 с | 2.31 с |

Индексация подорожала на 4–8%: работа с текстом — малая доля прохода, и второе прочтение
слова её удваивает, а не проход. Перестроение — единственное место, где видно полную цену:
там нет ничего, кроме анализа текста, и оно стало вдвое дороже.

Казахский измерен на эталонном корпусе из `tests/fixtures/kazakh` (ADR 0016); числа полноты
и точности по нему публикуются после того, как владелец подтвердит группы словоформ, по
которым он судится. Подробности решения — ADR 0017.

**Самоописание индекса** хранится в самом индексе и сверяется на каждом чтении: список
полей, версия таблицы суффиксов, которой заполнено поле языка, версия токенизатора и список
нормализаций с их версиями. Несовпадение значит, что часть индекса написана правилами, до
которых запрос этой сборки не дотягивается: термины в другой форме — или поле, по которому
фильтрует запрос, которого у половины документов нет.

**`doctor` показывает обе беды и одно лечение:**

```text
Search index: 10450 documents against 10450 chunks of current versions (in step with the graph)
Search index written by: fields=chunk_id,file_id,source_language,text;suffixes=1;tokenizer=simple-lowercase/1;normalizations=ru/1,en/1
```

Меньше документов, чем чанков, — индекс отстал от графа. Другое самоописание — индекс
написан другими правилами. Индекс с другим набором полей этой сборкой не открывается вовсе,
и причина названа той же строкой:

```text
Search index: the search index of this context could not be read (the index was written with other fields); rebuild it with `crosskit index rebuild --search`
```

Перестроение лечит все три случая:

```bash
cargo run -- index rebuild --search
```

Отставание лечит и обычная сверка, без перестроения: каждый проход читает каждый файл,
который ему разрешено читать, и заново публикует документы той версии, которую граф после
коммита считает текущей. Поэтому проход, который не дописал индекс, ничем не отличается от
обычного отставания — следующий проход пишет индекс снова. Смена правил — другое дело:
проход переписывает документы только тех файлов, которые прочитал, поэтому индекс, где
остались документы исчезнувших файлов, приводит в порядок именно перестроение.

Перестроение читает граф и ничего в него не пишет, поэтому безопасно в любой момент. Новый
индекс становится видимым одним шагом в конце, поэтому прерванное перестроение оставляет
прежний индекс, а не пустой. `index rebuild` без `--search` — ошибка: перестраивается
только поисковый индекс, потому что граф — источник истины, из которого его пишут, а сам
он не восстанавливается ни из чего.

**Во время `index watch` искать можно.** Движок берёт блокировку файла базы только для
писателя, а для читателя не берёт никакой, поэтому команда, которая ничего не пишет,
открывает ту же базу read-only и отвечает из неё. Так работают `search`, `ask` и `doctor`:
открытие на чтение **всегда**, а не только когда на запись не пустили. Пока это было «сначала
на запись» — обычный поиск по свободной базе применял недостающие миграции и молча менял
схему графа; измерено и исправлено в ADR 0034. `doctor` говорит, из чего прочитал:

```text
Database: /Users/alice/.local/share/crosskit/graph-work.lbug (read-only: another process is writing to this context)
```

Чего такое открытие не делает: не создаёт базу, не мигрирует её (база от старой сборки —
отказ с обеими версиями в тексте) и не читает того, что писатель закоммитил, но ещё не
сложил в базу. Последнее — не формальность: пока проход активно пишет, открытие на чтение
чаще всего отказывает (во время холодной индексации 3 000 файлов удалась 21 попытка из 237,
и все — сразу после контрольной точки). Тогда команда говорит это своими словами — «этот
контекст сейчас индексирует другой процесс, попробуйте, когда проход закончится», — а не
текстом движка про журнал. Короткий повтор внутри команды измерен и не добавлен: он
конвертирует около процента отказов и добавляет до секунды ожидания остальным (ADR 0015).
Между проходами, где watcher проводит почти всё время, чтение работает: 15 запусков
smoke-теста из 15. Вторая **пишущая** команда по-прежнему
отвергается — писатель по-прежнему один. Владелец базы в фоне, у которого остальные
спрашивают, — это этап 13; read-only снимает ограничение с чтения, но не отменяет его.

**Запись индекса** — часть той же команды, что пишет граф: сначала коммит транзакции графа,
затем вопрос графу, какая версия теперь текущая, затем запись документов принятых версий.
Порядок именно такой: индекс, записанный первым, мог бы описывать транзакцию, которая потом
откатилась, и этого никто бы не обнаружил. Отказ индексации не валит коммит — граф держит
всё, что прочитал проход, — но печатается и остаётся обнаружимым сверкой чисел в `doctor`.

Подробности и измерения — ADR 0011, ADR 0012 и ADR 0013.

**Насколько поиск точен наверху** — это другое измерение, и оно требует корпуса и знания
правильного ответа. Полнота и точность выше сняты по словоформам: находится ли документ,
содержащий слово. На живом вопросе («в каком чате …?») спрашивают иное — стоит ли нужная
беседа первой. Это померено на настоящем корпусе бесед и записано в
`docs/search-quality-summary.md`. Первый прогон владельца дал **precision@1 0.60 и ответ в
пятёрке в 11 вопросах из 15**; там же — кандидат, который померили и не внедрили (стоп-слова:
+0.07, один вопрос из пятнадцати), и то, чем промахи объясняются на самом деле: предлог ни
при чём — `в` лежит в 23 % чанков и весит по BM25 вдвое меньше слова «контрагент»; зато **у
каждой беседы есть собственное имя, и поиск его не использовал**.

Что с тем же набором стало дальше:

| | этап 29 | этап 32 | этап 33 |
| --- | ---: | ---: | ---: |
| precision@1 | 0.60 | 0.67 | **0.80** |
| ответ в пятёрке | 11/15 | 14/15 | **15/15** |
| различных файлов в пятёрке | 2.4 | 3.0 | **5.0** |

Этап 32 выбросил из индекса вывод инструментов и довёл до него самую большую беседу
владельца; этап 33 сделал строкой выдачи файл и дал вес имени беседы (ADR 0038). Набор
вопросов лежит вне репозитория, в каталоге владельца: в нём настоящие вопросы, пути и имена
бесед. Каталог называет переменная, и прогоняется набор так:

```bash
CROSSKIT_SEARCH_QUALITY_DIR=<каталог владельца> \
  cargo test --release --offline --test search_quality_chats -- --ignored --nocapture
```

Без переменной измерение пишет, что задать, и ничего не делает.

Измерение идёт к настоящему контексту этой машины, а не к песочнице, и потому лежит под
`#[ignore]`, как бенчмарки. На чужой машине оно честно откажет: контекста `chats` там нет.

#### Для программы: `--json`

`search --json` отвечает не человеку, а программе — панели (`apps/panel/`), — одним объектом
на одной строке stdout. Текст без флага тот же, что был, байт в байт: это проверяет тест
`tests/cli_search_json.rs`. Список настроенных контекстов — `crosskit contexts --json`; он
читает только конфигурацию и ни одной базы не открывает.

```bash
crosskit --context work search "retry webhook" --json --limit 8
crosskit --context work search "retry webhook" --json --limit 8 --after <next>
crosskit contexts --json
```

```json
{"schema":2,"context":"work","query":"retry webhook","looked_for":"retry webhook","period":null,
 "results":[{"kind":"conversation","cursor":"document:…","path":"/Users/alice/.claude/projects/…/5b0c….jsonl",
   "state":"present","fragment":"…ретраи webhook и cron…","matched":["webhook"],"matches":3,"topic":null,
   "conversation":{"session_id":"5b0c77de-…","name":"Ретраи webhook","message_count":34,
                   "last_message_at_unix_ms":1788419370000}},
  {"kind":"file","cursor":"document:…","path":"/Users/alice/Projects/payments-api/src/retry.ts",
   "state":"present","fragment":"…","matched":["retry"],"matches":1,"topic":"платежи","conversation":null}],
 "next":"document:…","not_shown":{"by_policy":2,"missing":1,"lost_by_graph":0},
 "index":{"documents":120786,"written_by_this_build":true,"folding_stopped_at":null}}
```

* **Схема одна и с номером** — `schema`, объявлена в одном месте, `src/presentation/machine_answer.rs`.
  Номер растёт, когда поле меняет смысл или исчезает; читатель сверяет его первым и ответ
  другого номера не читает вовсе. Сейчас — **2**: в виде графа «вне контекста» стало состоянием
  файла, а у касания появился `by_time` (ADR 0046); страница `search` не менялась.
* **`kind` — беседа или файл**, и решает это граф: строка — беседа ровно тогда, когда ревизию
  её файла прочитали как беседу (ADR 0036). `session_id` — то, чем её продолжают
  (`claude --resume <session_id>`).
* **Только то, что ядро умеет сегодня.** Групп, «недавнего» на пустой запрос и фильтра по теме
  в схеме нет — они отсутствуют, а не пусты (`apps/panel/docs/row-shape.md`).
* **Отказ — тоже объект**, с категорией из закрытого списка и кодом выхода 1:
  `{"schema":2,"error":{"category":"busy","context":"work"}}`. Категории: `usage`,
  `unreadable-query`, `configuration`, `no-context`, `context-required`, `unknown-context`,
  `not-indexed`, `busy`, `needs-migration`, `needs-recovery`, `index-unreadable`, `not-found`
  (фокус `graph` не называет ничего в этом контексте), `failed`.
  Предложение для человека по-прежнему идёт в stderr; в stdout нет ни сообщений движка, ни
  путей вне поля `path` результата.
* Курсор `next` — тот же, что `Next page: --after …` в тексте, и проходит между формами в обе
  стороны.

### Где над этим работали: `touches`

```bash
crosskit --context chats touches draft_service.py
crosskit --context chats touches --in "Беседа Б"
```

Вопрос, ради которого заводились беседы в графе: **в каком чате мы работали над этим файлом**
— и обратный к нему, что эта беседа вообще трогала. Отвечает граф, а не поиск: беседа
записывает каждый файл, который трогал инструмент, и команда читает эти записи.

```text
Context: chats
File: draft_service.py

/Users/me/Projects/platform-local/modules/counterparty/draft_service.py
  2 conversation(s) worked on it
1. [read+wrote+edited] Беседа А
   session 7b5b7a47-…, 246 times, you named this file, first 20260904T093707Z
2. [read+edited] handoff.md и qa
   session ab515160-…, 10 times, first 20260921T082158Z

Left out, read and never named: 1 (add --include-in-passing)
```

**Путь набирается хвостом.** `draft_service.py` находит файл, где бы он ни лежал; хвост
сходится по границе сегмента, поэтому `service.py` не назовёт `draft_service.py`. Если хвост
подошёл нескольким файлам, команда говорит это первой строкой и отвечает по каждому отдельно
— выбирать за вас она не будет.

**В умолчании — то, над чем работали.** Строка входит в ответ, если файл писали, правили или
**вы назвали его сами**. Всё остальное — файлы, которые агент открыл по дороге: их не
выбрасывают, их не показывают. Сколько таких, сказано числом, и `--include-in-passing`
показывает их со счётчиком повторов.

На дереве владельца это 919 пар «беседа + файл»: 724 (79 %) в умолчании, 195 (21 %) за
флагом. Почему именно так и что значит «назвали сами» — ADR 0041.

**Чего команда не знает.** Касание записывается только тогда, когда путь получил файловый
инструмент: чтение, запись, правка. Путь из команды оболочки — `grep`, `cat`, скрипт — не
записывается нигде (ADR 0037: глагол у такой строки неизвестен в принципе). Поэтому пустой
ответ означает «файловым инструментом не трогали», а не «никто не открывал», и команда пишет
это прямо там, где отвечает пустотой. Мера у этого измеренная: в корпусе владельца 11 628
вызовов оболочки против 2 200 файловых, а **19 бесед из 63 не сделали ни одного файлового
вызова** — по ним эта команда молчит целиком.

**Контекст — свой.** Команда открывает граф одного контекста и только на чтение (ADR 0034);
путь в записи — строка, а не ссылка на файл (ADR 0037), поэтому беседы из `chats` называют
файлы рабочих контекстов, ничего оттуда не открывая.

### Из каких бесед состоит задача: `tasks`

```bash
crosskit --context work tasks
crosskit --context work tasks --json
crosskit --context work tasks confirm <беседа> --name "<имя>"
```

Одна задача идёт через много бесед. Новую открывают, когда заполнен контекст, обычно с
handoff-файла; другую платформу подключают, когда кончился лимит подписки. Команда
показывает, какие беседы контекста складываются в одну задачу. Задачи она находит по тому,
что записано в самих беседах, без модели (ADR 0051, ADR 0052).

```text
Context: work
2 candidate task(s), by what the conversations' logs record. Nothing is kept yet.

Task 1 — 3 conversations, 2026-09-02 … 2026-09-29
  2026-09-02  Двойная скидка в корзине  [relay-file, shared-writes]
  2026-09-20  Скидка: продолжение  [relay-file]
  2026-09-21  Возвраты по частям (neighbour only)  [neighbours]
```

Признаки связи:

| признак | что значит |
| --- | --- |
| `relay-file` | беседа в самом начале ссылается на документ (`.md`, `.txt`, `.rst`), который написала более ранняя |
| `named-conversation` | владелец в начале беседы называет более раннюю беседу по имени |
| `same-tracker-task` | обе несут ссылку на одну задачу трекера |
| `shared-writes` | обе писали одни и те же файлы |
| `neighbours` | беседа началась в той же папке не позже чем через два часа после конца другой |

Беседа, связанная с задачей только соседством, помечена `(neighbour only)`: она подсказка, а не
решение.

**Что не считается связью:**
- файл или ветка, которых касается больше четырёх бесед: README, манифест, долгоживущая ветка;
- файл кода, который одна беседа написала, а другая прочитала;
- упоминание в беседе, которая перечисляет больше двух других: это обзор, а не продолжение.

Правила подобраны замером на одной задаче владельца (ADR 0051): без них пять бесед задачи
тонули в группе из шестидесяти.

**Работает по графу, а не по журналам.** Claude Code удаляет журналы примерно через месяц,
Crosskit хранит прочитанное, поэтому в задачу попадают и беседы, которых на диске уже нет.

**Свежесть — та же, что у графа.** Беседа попадает в задачу только после того, как её прочитал
проход индекса. Без фоновой службы (`crosskit service install`) новые беседы появятся только
после `crosskit --context <имя> index reconcile`.

**Решения владельца** (ADR 0053):

```bash
crosskit --context work tasks confirm 7b5b7a47 --name "Реестр юрлиц"   # кандидат → задача
crosskit --context work tasks merge "Реестр юрлиц" 03e514e4             # добавить кандидата целиком
crosskit --context work tasks add "Реестр юрлиц" 9036af1d               # добавить одну беседу
crosskit --context work tasks drop "Реестр юрлиц" c2557de4              # убрать навсегда
crosskit --context work tasks reject d6aa1092                           # кандидат — не задача
crosskit --context work tasks rename "Реестр юрлиц" "Реестр контрагентов"
```

Беседа называется первыми символами сессии, которые печатает список; задача — именем. Решения
лежат в `tasks-<контекст>.json` рядом с графом, а не в нём, поэтому служба не останавливается.
Решение сильнее сшивки:
- убранная беседа не возвращается в задачу;
- отклонённый кандидат не предлагается снова;
- то, что сшивка свяжет с задачей позже, приходит в неё как `Proposed`.

**Риски и «готово»** (ADR 0061):

```bash
crosskit --context work tasks accept "Двойная скидка" aaaa1111 63 --reason "возвраты пересчитает отдельная задача"
crosskit --context work tasks resolve "Двойная скидка" aaaa1111 118 --reason "интеграционные тесты прошли в CI"
crosskit --context work tasks reopen "Двойная скидка" aaaa1111 63
crosskit --context work tasks finish "Двойная скидка"
crosskit --context work tasks resume "Двойная скидка"
```

Риск называется беседой и репликой, где стоит его цитата: так его печатает `tasks map`.
Принятый или закрытый риск перестаёт быть открытым, а его причина видна в карте. Решение
хранится в книге задач и переживает перестройку карты, если та находит риск в той же
реплике. Задача с открытым critical готовой не отмечается: `finish` называет, сколько таких
рисков осталось. `tasks --json` у каждой задачи отдаёт её ход: сколько бесед размечено,
шагов основной линии, состояние HEAD, открытые и решённые риски.

**Карта решений задачи** (ADR 0054, ADR 0055, ADR 0057):

```bash
crosskit --context work tasks map "Реестр юрлиц"                        # что уже построено
crosskit --context work tasks map "Реестр юрлиц" --build --only 9b2fb426 # построить одну беседу
crosskit --context work tasks map "Реестр юрлиц" --build                # все беседы задачи
crosskit --context work tasks map "Реестр юрлиц" --json
```

По каждой беседе задачи карта показывает:
- развилки, где выбирали подход;
- ветки с тем, что с ними стало: `✓` выбрано, `✗` отклонено, `○` отложено, `?` ждёт решения,
  `ᵃ` решил агент, `⊘` брошено;
- риски по уровням и находки вне задачи.

Каждый узел стоит на номере реплики и дословной цитате из неё. Узел, цитату которого программа не
нашла в этой реплике, отбрасывается и только считается.

Карта задачи (ADR 0056) сводится из карт её бесед:
- основная линия ключевых решений;
- риски задачи — для каждого видно, в скольких беседах он поднимался; открытый риск, поднятый
  трижды, становится на уровень серьёзнее;
- находки вне задачи.

Каждый пункт называет беседу и реплику, где лежит его цитата. Карты отдельных бесед видны с
`--detail`.

Без `--build` команда показывает построенное и модель не зовёт. С `--build` она спрашивает
установленный `claude` (по умолчанию `--model sonnet`) только о репликах, которых карта ещё не
покрывает. Для этого нужно разрешение контекста `send_content_outside`, и расходуется лимит
подписки. Карты лежат в `maps-<контекст>/` рядом с графом; построенное заново не спрашивается.

Каждое окно реплик спрашивается дважды (вопрос `decision-map-v4`): сначала только о решениях
владельца, потом только о рисках. Если один из двух вопросов не получил ответа, окно не
засчитывается, и следующий `--build` начинает с него. Беседа на 383 реплики — 22 вызова,
4,27 $ лимита и около 12 минут; сводка двух бесед — 0,43 $.

**Чего команда пока не знает:**
- рабочего каталога и ветки беседы: граф их не хранит, местом беседы считается папка её журнала;
- бесед Codex: Crosskit их пока не индексирует.

### Окрестность: `graph`

```bash
crosskit --context work graph --focus conversation:<сессия>
crosskit --context work graph --focus path:/Users/me/Projects/payments-api/src/contract.rs --depth 1
crosskit --context work graph --focus file:<id> --json
```

Что связано с одной беседой или одним файлом: реплики, которые трогали файлы, сами файлы,
корни контекста, под которыми они лежат, темы — и на втором шаге другие беседы тех же
файлов. То, что панель рисует по ⇥ (ADR 0045); без панели — деревом:

```text
Context: work
Depth 2, at most 100 nodes
conversation «Договоры в payments-api» — session 5e55-…, 59 replies, 57 not drawn (focus: conversation:5e55-…)
  reply #12 by model, 20260903T070110Z
    [edited, reply placed by time] file [present] /Users/me/Projects/payments-api/src/contract.rs (focus: file:file:unix:…)
      [wrote, reply placed by time] reply #4 by model, 20260905T101500Z
        conversation «Сверка договоров» — session 7c1d-…, 31 replies, 30 not drawn (focus: conversation:7c1d-…)
      project /Users/me/Projects/payments-api
  reply #20 by model, 20260903T071240Z
    [edited, reply placed by time] file [outside this context] /Users/me/elsewhere/registry.rs
  also project payments-api

Nodes: 8 of 8 — conversations 2 of 2, replies 3 of 3, files 2 of 2, projects 1 of 1
Left out, read and never named: 1 (add --include-in-passing)
```

* **Фокус** — `conversation:<сессия>` (поле `session_id` строки `search --json`),
  `path:<путь>` (поле `path`) или `file:<id>` и `conversation:<сессия>` из узлов самого вида:
  у каждого узла, на который можно встать, это написано в скобках.
* **Шаг — переход «беседа ↔ файл»**, реплика стоит на нём. `--depth` — 1 или 2 (умолчание 2),
  `--limit` — от 1 до 100 узлов (умолчание 100). Больше не принимается, а отказывается: три
  шага, показанные как два, прочитались бы как конец графа.
* **Реплика — та, за которой последовало касание**: последняя, сказанная не позже первого
  касания этого файла этой беседой. Связи «реплика → касание» в графе нет, это чтение по
  времени; касание без времени рисуется от самой беседы.
* **Путь — файл только внутри контекста.** Есть место с этим путём — узел файла
  (`[present]`/`[missing]`); нет — тот же узел файла в состоянии `[outside this context]`
  (`file.state = "outside"` в `--json`), без перехода. Путь, записанный относительно, читается от
  корня проекта беседы, и две записи одного файла складываются в одну линию. Другие контексты не
  открываются (ADR 0008, 0037). Файл, которого политика не допускает, считается и не
  называется.
* **Строгое умолчание то же, что у `touches`**: прочитано один раз, никто не назвал — в счёт
  `Left out…`; `--include-in-passing` рисует и это.
* **Обрезка не молчит**: `Nodes: 100 of 271, cut at the limit — conversations 6 of 6, replies 44
  of 121, files 40 of 74, …` — по каждому виду. Первый шаг двухшагового вида берёт не больше
  двух третей узлов, и вторым шагом остаётся куда идти: без этого беседа на 2 016 реплик с 138
  файлами заполняла все сто узлов собственными файлами, и из шести бесед второго шага не
  рисовалась ни одна.
* **Тема** — узел, только если разметка её нашла; **проект** — корень контекста из
  конфигурации (узла «проект» в графе нет), и это написано в происхождении узла. Папка бесед
  (`~/.claude/projects/<код пути>`) — часть проекта, чьим путём она названа, а не второй проект.
* **Реплика по времени помечена**: у ребра от реплики `reply placed by time` в тексте и
  `touch.by_time: true` в `--json`.

`--json` — тот же вид одним объектом схемы 2 (`src/presentation/machine_graph.rs`):

```json
{"schema":2,"context":"work","focus":"conversation:5e55-…","depth":2,"limit":100,
 "nodes":[{"id":"conversation:5e55-…","kind":"conversation","label":"Договоры в payments-api","depth":0,
   "focusable":true,"provenance":{"record":"Conversation","key":"conversation:…"},
   "conversation":{"session_id":"5e55-…","message_count":59,"replies_not_shown":57,
                   "last_message_at_unix_ms":1788419370000},
   "reply":null,"file":null,"project":null}, …],
 "edges":[{"from":"reply:5e55-…:12","to":"file:…","kind":"touched",
   "touch":{"verbs":["edited"],"named":false,"times":3,"by_time":true}}, …],
 "truncated":false,
 "counts":{"conversation":{"shown":2,"found":2},"reply":{"shown":3,"found":3}, …},
 "not_shown":{"in_passing":1,"by_policy":0},
 "provenance_summary":[{"record":"Conversation","nodes":2}, …]}
```

Виды узлов: `conversation`, `reply`, `file` (`present`, `missing`, `outside`), `project`, `topic`; рёбер — `has-reply`,
`touched` (с `touch`), `in-project`, `about`. У каждого узла — `provenance`: из какой записи
графа он взят (`Conversation`, `Message`, `File`, `FileTouch`, `InsightResult`) или
`configuration` у проекта. Граф только читается, база на запись не открывается (ADR 0034).

### Знания: `knowledge`

Тот же вызов модели, что даёт файлу тему, достаёт из него **сущности и связи-факты** «субъект —
предикат — объект»: «Пакет документов — belongs-to — Контрагент», «Контрагент — identified-by —
БИН» (ADR 0048). Модель получает ревизию пронумерованными частями и у каждой связи называет
часть и **дословную цитату**. Связь сохраняется, только если программа находит цитату в тексте
этой части: пересказ, выпавшая разметка или выпрямленные кавычки — отказ, и он считается
отдельно. И цитата обязана **называть оба конца** связи: после сведения к основам тем же
анализатором в ней есть все слова имени субъекта и все слова имени объекта — или их написание из
ответа модели. «Контрагент — identified-by — БИН» с цитатой «БИН» отвергается и считается своей
строкой: такое слово стоит в каждом куске о нём. Ни одной связи без источника и ни одного конца связи строкой: связь указывает на
сущности рёбрами, а сущность — это ключ имени («Контрагент», «контрагенты» и «Контрагентов» —
одна сущность, ключ — основы слов тем же анализатором, что пишет индекс поиска).

Знания достаёт обычная очередь — никакого отдельного механизма (нужную папку называют прямо,
раздел «Разобрать нужную папку» выше); прогон печатает, что
сохранено, что отвергнуто и сколько это стоило:

```text
Knowledge: 148 facts kept of 178 proposed — 2 rejected because the quote is not in its part, 28 because it does not name both ends, 0 otherwise; 90 entities, 0 spellings glued
Cost: 8 calls (0 answered from the cache), 105786 bytes sent, 376455 input and 26424 output tokens, $1.8983 as the engine reported it
```

Цена — та, что сообщил движок: у инструмента подписки это цена той же работы по прейскуранту,
мера квоты, а не счёт; HTTPS-движок цены не сообщает (`no price`).

```bash
crosskit --context work knowledge                       # сколько знаний, что отвергнуто, цена и прогноз очереди
crosskit --context work knowledge entities --type concept
crosskit --context work knowledge show контрагент       # сущность, все её связи, цитата и источник каждой
crosskit --context work knowledge map --json            # весь граф одним объектом — его рисует панель
```

```text
Context: work
Контрагент (concept)
  Сторона договора поставки.
  also written: Контрагенты
  5 facts, from 3 sources

  Контрагент —identified-by→ БИН  (weight 9)
    «Контрагент уникален по БИН»
    /Users/me/Projects/supply-registry/registry.md, part 1

  Бухгалтер по расчётам —responsible-for→ Сверка с госреестром  (weight 6)
    «Ответственный за сверку с госреестром — бухгалтер по расчётам»
    conversation «Кто ведёт сверку» (session c3a1-…), reply 2 — /Users/me/.claude/projects/…/c3a1-….jsonl
```

`crosskit knowledge` без слова — числа и прогноз: сколько сущностей и фактов, сколько
написаний склеено, доля отвергнутых по цитате, цена на кусок и **прогноз на всю очередь по двум
ставкам** — постоянной части вызова (собственные инструкции инструмента, ≈ 25 тыс. входных
токенов на любой вызов) и части за байт содержимого. Ставки подбираются по уже оплаченным
вызовам; ответ из кэша второй раз не считается.

Видно ровно то, что видит поиск: факты текущей ревизии файла, через путь, который политика
контекста допускает. Новая ревизия файла заменяет его факты целиком; факты заменённой ревизии
не показываются сразу и снимаются следующим прогоном очереди. Контексты не смешиваются: одно
понятие в двух контекстах — две сущности.

**Чего ключ не склеивает** — и на карте это две сущности: перевод (`counterparty` и
«Контрагент»), сокращение («БИН» и «бизнес-идентификационный номер»), синоним («Поставщик» и
«Контрагент»), часть и целое имени («Карточка» и «Карточка контрагента»), порядок слов.

#### Словарь типов: `[knowledge]`

Типы сущностей и предикаты — **закрытые списки**: модель выбирает только из них (они стоят в
JSON-схеме вопроса как перечисления), а программа проверяет ещё раз. Без секции действуют
встроенные:

```toml
[knowledge]
entity_types = ["concept", "attribute", "organization", "person", "role", "system",
                "dataset", "document", "process", "rule", "task", "issue"]
relation_types = ["is-a", "part-of", "belongs-to", "has-attribute", "identified-by", "uses",
                  "stored-in", "produces", "depends-on", "references", "responsible-for",
                  "governs", "replaces", "contradicts", "related-to"]
```

Как менять: написать в `config.toml` один или оба списка — названный список заменяет встроенный
целиком, неназванный остаётся встроенным. Тип — одна строка от 1 до 40 символов, на любом языке,
в списке не больше 48 и без повторов; иначе конфигурация не загружается. Изменённый словарь —
**новый вопрос**: отпечаток словаря входит в ключ кэша, прежние ответы не подаются, и
пересобирать знания придётся прогоном очереди заново. Порядок списка задаёт цвет типа на карте
панели, поэтому новый тип дописывают в конец. `related-to` — последнее средство: модель берёт
его, только когда другой не подходит.

Почему такие списки — ADR 0048, решение 8: они выведены из образца владельца, предметной
области и пробного прогона на выдуманном корпусе (9 из 12 типов и все 15 предикатов
использованы). **Пробный прогон на своём корпусе — за вами**, и списки стоит поправить по нему:

```bash
crosskit --context work index jobs run --limit 15     # первые 15 заданий очереди
crosskit --context work knowledge entities --limit 100
crosskit --context work knowledge map --json | python3 -c 'import json,sys,collections; m=json.load(sys.stdin); print(collections.Counter(e["type"] for e in m["entities"])); print(collections.Counter(f["predicate"] for f in m["facts"]))'
```

Пределы — чтобы описание не стало каналом для целого файла: имя до 80 символов, описание до 240,
цитата от 8 до 240, не больше 60 сущностей и 80 связей на ответ, вес 0–10. Элемент за пределом
отвергается целиком, а не обрезается.

### Вопрос: `ask`

```bash
cargo run -- --context work ask "что делает сверщик и когда он помечает файл missing?"
```

Петля целиком: индекс находит подходящие куски, граф говорит, что в них написано и какие из
них этот запуск вправе показать, модель отвечает по этим выдержкам, а источники под ответом
называет Crosskit.

```text
Context: work
Question: что делает сверщик и когда он помечает файл missing?

Сверщик обходит корень заново под той же политикой и помечает missing только те локации,
которых не видел ни один проход, начавшийся не раньше него.

Sources sent: 4 of at most 8 (7213 bytes of at most 40000)
Sources used:
  [1] /Users/alice/Projects/crosscode/docs/how-it-works.md
  [3] /Users/alice/Projects/crosscode/README.md
```

**Разрешение обязательно.** Вопрос модели — это содержимое, уходящее с машины, поэтому
команда требует того же пропуска, что и AI-анализ этапа 6: `send_content_outside = true` у
контекста. Контекст, который этого не говорил, получает отказ с причиной и с той строкой,
которая его изменит. Тихой деградации здесь нет намеренно: всё, что можно сделать без
модели, называется `crosskit search`, и выдавать это за ответ значило бы показать команду,
которая как будто сработала. Разрешение проверяется **раньше** ключа: контекст, который не
разрешал, отвергается по своей причине.

**Источники называет Crosskit, а не модель.** Модель получает вопрос и выдержки,
пронумерованные с единицы, — ни пути, ни имени файла, ни идентификатора. Она ссылается на
номера; номер ищется в собственном списке отправленного, и печатается путь оттуда. Ответ,
сославшийся на номер, которого не посылали, отвергается целиком: это единственная форма
неверного ответа, которая поставила бы перед читателем чужой файл.

**Вопрос ищется по своим словам.** Проза полна символов, которые язык запросов читает как
указания (`+`, `-`, `"`, `поле:слово`), поэтому в индекс уходят слова вопроса, а не вопрос
целиком. Который из них важен, решает индекс.

**Вопрос о периоде.** «Над чем я работал на прошлой неделе?» отвечается по выдержкам из этой
недели и только из неё — по тем же правилам, что `search` с периодом (раздел выше): период
вычисляется программой и печатается перед ответом, слова фразы не ищутся, флаги `--since` и
`--until` работают так же. У каждого источника под ответом — событие, которое поставило его в
период. Модель получает период одной строкой («the question is about 21–27 Sep 2026, local
time…»), чтобы не называть дат, которых в выдержках нет; лишнего вызова модели нет. Ключ
кэша включает **даты** периода, а не слова: тот же вопрос через неделю — другой ключ. Если в
периоде ничего не совпало, ничего не отправляется.

```text
Context: work
Question: над чем я работал на прошлой неделе?
Period: 21–27 Sep 2026 (last week, Mon–Sun, local time)
Looked for: над чем я работал
…
Sources used:
  [1] /Users/alice/.claude/projects/-Users-alice-Projects-payments-api/9c21….jsonl — reply 2026-09-23 12:00
  [2] /Users/alice/Projects/payments-api/ledger.md — edited 2026-09-23 12:05
```

**Бюджет — сколько уходит с машины:**

```toml
[ask]
max_sources = 8      # сколько выдержек уходит в один вопрос
max_bytes = 40000    # сколько байт они занимают вместе
```

Бюджет тратится в порядке, в котором ранжировал индекс, поэтому отбрасывается то, что
совпало хуже. Первая выдержка берётся всегда и режется по бюджету, а не выбрасывается. Что
ушло и каков был предел — печатается в ответе.

**Приватность.** Выдержки собираются тем же кодом, что страница `search`: путь, который
политика прячет или который принадлежит другому контексту, не показывается **и не
отправляется**. Ответ приходит по строгой схеме `{answer, sources}`; всё, что в неё не
укладывается, — типизированный отказ, и сырой текст провайдера не сохраняется и не
печатается.

**Кэш.** Тот же вопрос по тем же источникам той же модели с той же версией запроса не
оплачивается второй раз: ответ лежит в `ask-<контекст>` рядом с базой и индексом. Каталог
производный — удаляется в любой момент, и следующий вопрос просто задаётся заново.

**Чего здесь нет:** эмбеддингов, гибридного ранжирования и диалога с историей. Один вопрос —
один ответ. Почему поиск по словам раньше поиска по смыслу: сначала замыкается петля, и
становится видно, где она рвётся; процедура измерения качества — `docs/ask-quality-run.md`,
решение и числа — ADR 0018.

### Публикация источников батчами

Скан не публикует каждый файл отдельной транзакцией. Общий путь сканирования, которым
пользуются `index init` и `index reconcile`, копит прочитанные источники в буфере и
публикует их одной ограниченной транзакцией: до 100 источников или до 4 MiB текста chunk,
что наступит раньше. Лимиты внутренние и не настраиваются; вместе они держат память скана
независимой от размера каталога. Источник, который сам больше байтового лимита,
публикуется отдельным батчем.

Атомарность — «весь батч или ничего»: ошибка на любом источнике откатывает всю текущую
транзакцию, но отдельный источник никогда не бывает опубликован частично, а ранее
закоммиченный батч не откатывается. Счётчики отчёта начисляются только после успешного
flush. Всё прочитанное публикуется до завершения скана, включая incomplete reconcile,
иначе финализация могла бы ошибочно пометить такие файлы `missing`. Повтор целого батча
безопасен: идентификаторы ревизий, chunks и jobs неизменяемы, поэтому дубликатов не
возникает. Подробности — в ADR 0006.

Значения 100 и 4 MiB выбраны измерением. Чтобы прогнать бенчмарк на других лимитах,
бинарник собирается с feature `batch-limit-benchmark`: она берёт лимиты из окружения
компилятора и отвергает нечисловое или нулевое значение, а `doctor` печатает фактические
лимиты собранного бинарника. `tests/batch_limits.rs` читает их оттуда и отказывается
отчитываться о прогоне, лимиты которого не подтвердил. В обычной сборке feature выключена,
production остаётся с одним compile-time значением, и пользовательской настройки лимитов
не появляется.

```bash
CROSSKIT_BATCH_LIMIT_SOURCES=50 CROSSKIT_BATCH_LIMIT_PAYLOAD_MIB=2 \
  cargo test --release --offline --features batch-limit-benchmark \
  --test batch_limits -- --ignored --nocapture
```

Обычные проверки эту ветку не собирают, поэтому вместе с ними запускается её дешёвая
компиляция без прогона бенчмарка:

```bash
cargo test --offline --features batch-limit-benchmark --no-run
cargo clippy --offline --tests --features batch-limit-benchmark -- -D warnings
```

Батч пишется set-based: один statement на вид записи на весь батч через `UNWIND $rows`
вместо примерно 25 statement на источник. Все query text статические, пользовательские
значения идут только параметрами, а перед записью батч одним чтением сверяет immutable
поля уже сохранённых строк, так что `MERGE` не подменяет проверку неизменяемости. Каждый
пишущий statement возвращает число обработанных строк, и оно сверяется с числом
отправленных. Наблюдения получают непрерывный диапазон sequence, выделенный один раз
внутри транзакции строго по порядку источников, а current state при нескольких
наблюдениях одного файла выбирается по `(observed_at, sequence)`, то есть так же, как при
записи по одному. Схема v8 не менялась. Подробности — в ADR 0007.

### Нечистая остановка: что она стоит и как вернуть контекст

Батч, который движок принял, лежит не в базе. Он лежит в журнале рядом с ней
(`graph-<контекст>.lbug.wal`), и в саму базу движок складывает его на контрольной точке: она
случается, когда журнал перерастает примерно 16 MiB, когда базу закрывают и — с этапа 11 —
в конце каждого прохода `index watch`.

Процесс, который остановили не дав ему закрыть базу — Ctrl-C на `index init`, OOM-killer,
выключенный ноутбук, — оставляет журнал, который движок дочитать может не всегда:

| убитый проход | база после убийства |
| --- | --- |
| писал новое содержимое (`index init`, сверка после правок, первый проход watcher'а) | не открывается: macOS 10 прогонов из 10, Linux 6 из 6 |
| только отмечал, что файлы на месте (холостая сверка) | открывается, 3 из 3 |
| watcher, убитый **между** проходами | открывается, всё записанное на месте: каждый проход складывается в базу до того, как объявлен завершённым |

Работа, закоммиченная после последней контрольной точки, не переживает остановку ни в одном
случае. Разница в том, открывается ли база вообще.

**Что делать, если не открывается.** Одна команда:

```bash
cargo run -- index recover
```

Она смотрит, в каком состоянии контекст, и только для этой одной беды переносит журнал в
сторону — в тот же каталог, под именем со временем
(`graph-work.lbug.wal.aside-20260922T143000Z`). **Ничего не удаляется**: операции удаления в
этой команде нет вовсе, и повторное восстановление не затрёт прежний журнал. На контексте,
который открывается, команда не делает ничего и говорит об этом. На контексте, который
прямо сейчас индексирует другой процесс, — отказывается: забрать журнал у живого писателя
значит забрать проход, который он пишет.

Писатель, остановленный посреди контрольной точки, оставляет другие файлы: журнал, который
она переносила в базу (`.wal.checkpoint`), и её теневые страницы (`.shadow`). Их команда
убирает второй ступенью и так же рядом, если после первой граф всё ещё не открывается
(ADR 0060).

```text
Context: work
Database: /Users/alice/.local/share/crosskit/graph-work.lbug
A recovery moves the write-ahead log aside and keeps it. What the interrupted pass had
written since the last checkpoint is not readable from it and does not come back; the graph
is written again from the files on disk, which costs one pass.
Recovered: the graph opens again.
Log moved to: …/graph-work.lbug.wal.aside-20260922T143000Z
Next: `crosskit --context work index reconcile <каталог>` … doctor … `index rebuild --search` …
```

Дальше обычная сверка наполняет граф заново, а `index rebuild --search` — поисковый индекс.
Весь этот цикл — смоук-тест `tests/cli_unclean_stop.rs`, он проходит на обеих платформах.

**Спросить, не чиня:**

```bash
cargo run -- index recover --check
```

Печатает одну строку — `Graph state: opens | busy | log-unreadable | failed` — и возвращает
0 только для первого. Эту же команду Crosskit запускает сам, дочерним процессом, прежде чем
открыть базу, рядом с которой лежит журнал: движок на такой базе не всегда отказывает, а
иногда умирает по сигналу (на Linux — три базы из шести), и процесс, который умер, диагноза
не печатает. Дочерний процесс платит этот риск, а команда остаётся жива и говорит, что
случилось и что делать. Пока журнала рядом с базой нет — то есть на любом здоровом
контексте — ничего не запускается.

### Измеренная пропускная способность

Baseline Этапа 2G писал каждый источник отдельной транзакцией. Ниже измерения профиля
`scale` (10 407 файлов) в release на одной и той же машине, macOS aarch64; peak RSS снят
снаружи через `/usr/bin/time -l` вокруг уже собранного тестового бинарника:

| Фаза | 2G, транзакция на источник | 2H, батчи транзакций | 2I, set-based батчи | 2K, связи по ключу |
| --- | --- | --- | --- | --- |
| cold `index init` | 472.4 с | 418.9 с | 56.7 с | 33.5 с |
| idle `index reconcile` | 507.1 с | 438.7 с | 110.8 с | 48.9 с |
| reconcile после мутации | 501.4 с | 432.6 с | 242.4 с | 68.3 с |
| reconcile после reopen | 528.1 с | 442.6 с | 165.3 с | 62.2 с |

Счётчики, размер базы и очередь insight jobs во всех трёх измерениях совпадают. Числа
привязаны к машине и служат baseline для сравнения, а не обещанием скорости.

Стоимость reconcile больше не растёт с накопленной историей наблюдений. Раньше росла:
три statement, связывающие наблюдение с файлом, ревизией и его порядком, планировались
полными сканами таблиц `File`, `FileObservation` и самой таблицы связей. Теперь связи
новых наблюдений создаются через два точечных поиска по первичному ключу каждая, и
стоимость батча не зависит от того, сколько истории уже лежит в базе (ADR 0007).

**Что добавил поиск (этап 9).** Тот же профиль `scale`, один и тот же день и одна и та же
машина, без поиска и с ним: 28.84 → 28.45 с на холодной `index init`, 40.18 → 40.24 на
холостой сверке, 51.23 → 51.27 после мутации, 43.41 → 42.81 после reopen. Разница во всех
фазах внутри разброса между прогонами. Сама работа с текстом измерена отдельно и стоит
0.5 с на 14.4 МБ; четверть прогона, которую поиск занимал в первой версии, уходила не на
неё, а на то, что индекс делали видимым после каждой пачки файлов (ADR 0013).

Воспроизводится ignored-тестом `tests/memory_diagnostic.rs` (macOS-only, peak RSS берётся
у операционной системы):

```bash
cargo test --release --offline --test memory_diagnostic -- --ignored --nocapture
```

Команда запускается без переменных окружения и воспроизводит именно приведённые ниже
числа: 2 000 файлов, 30 проходов истории, измерение каждые 6. Переменные
`CROSSKIT_DIAGNOSTIC_FILES`, `CROSSKIT_DIAGNOSTIC_PASSES` и
`CROSSKIT_DIAGNOSTIC_CHECKPOINT` нужны, только чтобы посмотреть вокруг этой точки;
фактические значения прогона записываются в `report.txt`.

На корпусе из 2 000 файлов при росте истории с 4 000 до 76 000 наблюдений один idle
reconcile остаётся в пределах 3.1–5.3 с и 279–379 MiB; размер базы при этом доходит до
231.9 MiB, а её открытие стоит 121 MiB. Изолирующий замер на копии базы показывает, что
именно изменилось: 2 000 наблюдений без связей стоят 0.8 с и 224 MiB, с нынешними связями
— 1.1 с и 247 MiB, с прежними — 29.1 с и 1 223 MiB. С buffer pool 128 MiB нынешние связи
записываются успешно, прежние не выполнялись вовсе.

Число строк и размер базы по шагам детерминированы, а время и peak RSS колеблются между
прогонами и зависят от загрузки машины: это baseline для сравнения, а не константа.

Peak RSS всего scale-прогона: 463 MiB при записи по одному источнику в транзакции, 1 166
MiB после перехода на set-based батчи, 489–551 MiB на текущем коде по пяти прогонам.
Остаток относительно первого числа даёт не история наблюдений и не размер батча: при
изменении лимитов батча от 25 до 200 источников peak RSS полного сценария держится в
541–567 MiB, а время отличается почти вдвое (ADR 0006). Пик принадлежит не одной фазе:
он приходится на первичную индексацию (489, 497, 524 MiB) или на проход после мутации
(486, 538, 551 MiB), тогда как idle reconcile стабильно легче (355–404 MiB). Пик всего
прогона в каждом случае совпадает с самым тяжёлым из этих вызовов, то есть сам бенчмарк
ничего к нему не добавляет. Порог «не более 10% над 463 MiB» поэтому пока не достигнут.

### Current-state: измерение и замена pointer creation

Этап 2M измерил current-state batch path на 10 407 identities, не меняя production
statement. Все пять statement (`current order` lookup, два remove и два set) тогда по плану
сканировали таблицы; lookup и removals сканируют ещё и relationship table. Каждый statement
зафиксирован capability-тестом с `EXPLAIN` и `PROFILE`; profile write выполняется в
откатываемой транзакции.

Этап 2N заменил ровно два батчевых statement: create `CURRENT_VERSION` и create
`CURRENT_OBSERVATION` берут каждый из своих двух primary key отдельным `MATCH` вместо
перечисления через запятую. План каждого — два `QUERY_PRIMARY_KEY_LOOKUP` без
node/relationship scans. Isolated fresh pointer creation: median 10.9 s до замены и 1.9 s
после, при 10.8 s у снятой формы в том же прогоне; полная current-state sequence
12.0 → 3.1 s на fresh и 23.6 → 6.8 s на reconcile. Lookup current order, оба removal,
schema, миграции, граница транзакции, batch limits и public CLI не менялись; `ONE_ONE`
остаётся единственной защитой от дубля pointer. Снятая батчевая comma-separated форма
зафиксирована тестом как сканирующая, чтобы разница оставалась проверяемой.

Форма шаблона решает только в батчевых statement, где ключи приходят строками `UNWIND`.
Одиночный fallback-путь (`persist_sources_one_by_one`) передаёт ключи скалярными
параметрами, и планировщик достаёт оба конца по первичному ключу независимо от написания:
запятая и два `MATCH` дают идентичный план без сканов таблиц. Его текст поэтому не
менялся; оба скалярных create и оба скалярных removal вынесены константами в тот же
source, что и батчевые, а эквивалентность двух написаний закреплена capability-тестом.

В macOS diagnostic каждый workload выполняется трижды на отдельной копии fixture под
`/usr/bin/time -l`. Maximum isolated RSS current-state workload — 222 MiB после 2N против
232 MiB в 2M, поэтому current-state не объясняет peak полного scale-прогона 489–551 MiB:
он исключён именно как следующий RSS-рычаг, и порог 2I на тот момент оставался открытым. Candidate lookup
order по `observation.id` в production не вошёл — он всё ещё сканирует и скрывает
отсутствующую `ORDERS`-связь. Подробные планы, инварианты и все min/median/max — в
ADR 0007.

### Конфигурация движка и остаточная память

Этап 2O измерил, сколько остаточного peak RSS принадлежит политике движка. База открывается
с `SystemConfig::default()`: размер буферного пула и число потоков движок выбирает сам, и
до 2O это не проверялось. Ручка для измерения живёт под выключенной по умолчанию feature
`engine-tuning-benchmark` и берёт значения из окружения компилятора; нечисловое или нулевое
значение — ошибка сборки. Released Crosskit про движок из окружения не читает ничего.

Измерено на scale-корпусе, два прогона на точку. Пул решает ровно один шаг: `auto` даёт пик
522–523 MiB, любое явное значение от 256 до 1024 MiB — 459–500 MiB, и между ними разницы
нет. Число потоков не управляет ни памятью, ни временем. Пул 128 MiB нерабочий: движок
отказывает на checkpoint после коммита с `Buffer manager exception: the buffer pool is full`,
и при этом процесс всё равно занимает 388–639 MiB, то есть основная масса пулу не
принадлежит.

На полном сценарии пул 256 MiB даёт 484 и 467 MiB против 532 MiB на дефолте, при том же
времени (296–307 с). Конфигурация объясняет только верхушку около 55 MiB: остальные
~400 MiB держит сам проход.

Этап 2P проверил кандидата на допустимом входе и **оставил пул автоматическим**. Политика
разрешает файл до 100 MiB, и такой источник публикуется одной транзакцией примерно на
25 600 chunks. При `auto` он индексируется; при любом явном значении пула — от 256 MiB до
24 GiB — движок отказывает, причём 24-гигабайтный пул отказывает, израсходовав 2.1 GiB, то
есть дело не в размере, а в самом факте явного значения. Ограничение сверху вида
`min(fixed, auto)` по той же причине не помогает. На практике фиксированный пул 256 MiB
становится необъявленным лимитом на размер файла: 32 MiB проходит, 64 MiB уже нет.

Отсюда же следует, что порог 2I в 509 MiB осмыслен только для корпуса из мелких файлов: на
допустимом входе один файл в 16 MiB даёт 592 MiB. Закрывать 2I выбором пула поэтому было
нельзя.

Этап 2T понизил `max_content_size_mb` со 100 до 16 MiB. Значение выбрано по кривой: источник
такого размера даёт 322–334 MiB, то есть более 150 MiB запаса до порога, тогда как 32 MiB
доходит до 387. Предел компилируется в программу и служит потолком — политика может читать
меньше, но не больше. Файл крупнее предела индексируется по метаданным, его содержимое не
открывается, и он считается отдельной строкой отчёта.

Порог 2I после 2T оставался открытым. Источник предельного размера его выполнял с запасом
(пять прогонов: 333–345 MiB), корпус — нет: две серии по пять прогонов дали медианы 677 и 674 MiB.
Причина не в коде: контрольная нагрузка всё это время стояла на 117–121 MiB, загрузка
процессора за время серий упала вчетверо без влияния на числа, а размер пула движка
неразличим. Тот же код накануне давал на корпусе 502–558 MiB. Peak RSS зависит от давления
памяти хоста — под давлением страницы сжимаются и перестают быть резидентными, — поэтому
сравнимы только прогоны одной серии на одной машине.

Этап 2S убрал вторую копию содержимого: источник больше не материализуется целиком.
Первый проход по файлу считает отпечаток и проверяет, текст ли это, второй нарезает чанки
скользящим окном. Освобождать текст после нарезки было бесполезно — измерение показало, что
пик к тому моменту уже достигнут. Потоковое чтение легче примерно на 39 MiB в чередующемся
сравнении на предельном файле, а на корпусе два пути неразличимы. Попутно устранена
квадратичная трата времени: язык определялся заново для каждого чанка сканированием всего
текста, из-за чего предельный файл обрабатывался около двух с половиной минут вместо девяти
секунд. Пришедшая на смену письменность чанка (`script`, этап 8) считается по тексту самого
чанка и ничего не перечитывает, поэтому та ловушка не возвращается.

Порог 2I и после 2S оставался открытым: источник предельного размера держался в
485–557 MiB, то есть выше 509 в большинстве прогонов. Остаток составляют постоянная часть процесса с открытой
базой (около 256 MiB) и все чанки источника, существующие одновременно; последнее снимается
только передачей чанков в store потоком, что меняет порт.

Этап 2R применил вывод 2Q к `chunk_store` и попутно нашёл, что связи чанков писались
формой, отвергнутой ещё в 2K: перечисление концов через запятую и `MERGE` давали три
скана узловых таблиц и скан таблицы связей, без единого ключа. Теперь связь нового чанка
пишется отдельным `MATCH` на каждый ключ и `CREATE` — два primary-key lookup без сканов, а
прежний `MERGE` остался только для строк, уже бывших в базе. Чанки одного источника
записываются страницами по 100 строк внутри той же транзакции, поэтому источник
по-прежнему публикуется целиком или не публикуется вовсе.

На файле 100 MiB форма связей дала около 400 MiB, страницы — около 1 230 MiB. Кривая
одного источника: 16 MiB стоили 695 MiB, стали 326; 64 MiB стоили 2 090 MiB, стали 446.
Наклон упал примерно с 20 до 3 MiB RSS на MiB контента.

Порог 2I при этом закрыт **не был**. Полный scale-прогон укладывается дважды (пики 499.5 и
460.3 MiB против 522 и 473 до этапа), но источник предельного размера колеблется вокруг
порога: восемь прогонов дали 438–559 MiB, три из них выше 509. Остаток держит слой чтения:
нарезка источника стоит 249 MiB до любой записи, потому что файл присутствует в памяти
байтами, строкой и чанками одновременно. Снять это может только потоковое чтение, то есть
работа в application, а не в store.

Этап 2Q разложил эту цену. Расход растёт объёмом контента, а не числом чанков: тот же файл
в 100 MiB, порезанный на 1 601 или на 102 601 чанк, стоит одинаково. По слоям на файле
100 MiB: чтение и нарезка 249 MiB, проекция в строки ничего, сборка параметров +179 MiB,
запись +1 507 MiB. Основную массу держит не транзакция, а размер одного `UNWIND`-statement:
те же чанки, записанные страницами внутри той же транзакции, стоят 484 MiB вместо 2 618 и
не дороже по времени. Инвариант «один источник — одна транзакция» поэтому сохраняется, а
предел для одного источника должен выражаться размером контента: на текущем коде под
509 MiB держатся примерно 8 MiB контента, со страничной записью — предельные 100 MiB.

Отказ движка по памяти приходит типизированной ошибкой со статическим сообщением, без
текста движка и без частичной записи; `doctor` печатает запрошенную конфигурацию движка и в
обычной сборке. Подробные таблицы — в ADR 0007.

### Память: требование к машине и baseline аллокаций

Этап 2U отменил критерий 2I в абсолютных мегабайтах peak RSS и заменил его двумя
измерениями. Причина: базовые 463 MiB этапа 2H невоспроизводимы — того кода больше нет, —
а под давлением памяти хост сжимает страницы, и они перестают быть резидентными, поэтому
любое прежнее число занижено на величину, зависевшую от состояния машины в тот час.
Нормировать тоже не на что: контрольная нагрузка стояла на 117–121 MiB, пока корпус в той
же серии ходил 632–728 MiB. Peak RSS остаётся диагностикой для чередующихся сравнений
внутри одной серии на одной машине и больше не критерий приёмки; состояние хоста
записывается вместе с любым числом RSS.

**Требование к машине.** Полный scale-сценарий с обоими сценариями восстановления
проверен под жёстким лимитом памяти: Linux-контейнер с cgroup v2, swap выключен, лимит
наложен на бенчмарк вместе со всеми его процессами.

корпусе, который мерили. **На настоящем дереве владельца это почти втрое не так**: 26 125 файлов

про их разницу установлено, — ниже, под кривой без лимита.

Каждая строка таблицы ограничена с обеих сторон: лимит на ступень ниже убит ядром, а не «не
проверялся». Это не пропорция и не обещание для произвольного дерева: корпус синтетический, а
реальный каталог с другим распределением размеров стоит иначе — теперь известно, насколько.
Число говорит, что сто тысяч файлов достижимы на обычной машине, а не то, что на каждые сто
тысяч нужно ровно два гигабайта.

Время на тех же точках: 100 000 файлов — холодная индексация 470.9 с, холостая сверка
440.4 с. Под лимитом прогон идёт чуть дольше, чем без него (445 с и 440 с на macOS): движок
вытесняет страницы вместо того, чтобы держать всё.

Наименьшие проверенные рабочие лимиты: **704 MiB** для корпуса в 10 000 файлов и
**352 MiB** для источника предельного размера. Нижние границы этой таблицы измерены до
поиска; с поиском перепроверен только критерий — 1 GiB, и он проходит целиком, вместе с
обоими сценариями восстановления (ADR 0013). На всех проходящих лимитах счётчики фаз,
размер базы, очередь jobs и оба сценария восстановления совпадают с macOS-эталоном.
Убийство подтверждается с двух сторон: процесс заканчивается сигналом 9 без кода возврата,
и контейнер помечается `OOMKilled`.

Воспроизводится так (образ должен нести GCC 13 или новее — заголовки движка требуют
`<format>`; сценарий с нечитаемым каталогом требует непривилегированного пользователя,
потому что root читает каталог без прав):

```bash
docker volume create crosskit-target
docker run --rm -v "$PWD:/src" -w /src -v crosskit-target:/target \
  -e CARGO_TARGET_DIR=/target rust:1-trixie \
  sh -c 'cargo test --release --test scale_indexing --no-run && chmod -R a+rX /target'
docker run --rm -m 1g --memory-swap 1g --user 1000:1000 \
  -v crosskit-target:/target:ro \
  -e HOME=/tmp -e CROSSKIT_SCALE_PROFILE=scale -e CROSSKIT_SCALE_DIR=/tmp/bench \
  rust:1-trixie \
  sh -c 'exec $(ls -t /target/release/deps/scale_indexing-* | grep -v "\.d$" | head -1) \
    --ignored --nocapture --exact indexing_stays_correct_idempotent_and_recoverable_at_scale'
```

`ls -t … | head -1` берёт самый свежий бинарник: том с артефактами переживает прогоны, и
после пересборки в нём лежит несколько.

Этот же прогон — единственное место, где видно столкновение zstd: `tantivy` с набором фич
по умолчанию тянет `zstd-sys`, а движок несёт свой zstd внутри `liblbug.a`, и на Linux две
копии символов дают отказ линковки. На macOS это только предупреждение, поэтому набор фич в
`Cargo.toml` проверяется здесь.

**Память работника: что росло и что с этим сделано (этап 17).** Этап 16 оставил измерение:
`index jobs run --limit 20000` на очереди из 10 000 заданий убивало ядро под 1 GiB примерно на
семитысячном задании. Это оказалось не свойством watcher'а и не свойством наших аллокаций.

Атрибуция, macOS, без лимита — четыре точки, каждая свой граф и свой процесс:

| заданий | peak RSS | аллокации нашей стороны | база |
| ---: | ---: | ---: | ---: |
| 1 000 | 293 MiB | 138 694 байта | 27 MiB |
| 5 000 | 753 MiB | 138 694 байта | 50 MiB |
| 10 000 | 1 381 MiB | 138 703 байта | 87 MiB |
| 20 000 | 1 450 MiB | 138 719 байт | 141 MiB |

Наша сторона — 0.13 MiB и не шевелится при двадцатикратной разнице в числе заданий, хотя
число вызовов аллокатора растёт линейно. Те же 10 000 заданий, разложенные по 1 000 на
процесс, держатся на 287–332 MiB, причём последний процесс работает над графом с 9 000
результатов и стоит столько же, сколько первый: рост идёт за процесс и за число сделанных
заданий, а не за размер графа.

Против движка напрямую, 20 000 одинаково мелких транзакций, каждая форма в своём процессе:

| форма | peak RSS |
| --- | ---: |
| один узел, новое соединение на транзакцию | 86.3 MiB |
| один узел, одно соединение | 87.2 MiB |
| **узел и связь** | **639.0 MiB** |
| узел и связь, контрольная точка каждые 1 000 | **176.9 MiB** |

Растёт запись **связи**, и держится это до контрольной точки; соединения ни при чём. Поэтому
работник просит движок сложить журнал каждые 1 000 завершённых заданий — не ради надёжности,
то в журнале уже durable, а ради памяти. Проход короче тысячи до неё не доходит: watcher со
своим пределом в двадцать заданий за проход делает контрольную точку после каждого прохода
сам.

Повторный замер, контейнер, лимит 1 GiB:

| заданий | до | после |
| ---: | --- | --- |
| 1 000 | проходит, 256 MiB | проходит, **253 MiB** |
| 5 000 | проходит, 747 MiB | проходит, **295 MiB** |
| 10 000 | **убит сигналом 9** | проходит, **304 MiB** |
| 20 000 | **убит сигналом 9** | проходит, **336 MiB** |

Остаточный наклон назван, а не замолчан: 83 MiB на двадцатикратной разнице против 1 157 MiB
до починки, и часть его — сам граф, выросший вчетверо. Дальше 20 000 в одном процессе
измерить не удалось по другой причине: корпус в 40 000 файлов не индексируется под 1 GiB, и
это свойство сверки, а не работника.

**Buffer pool и лимит среды.** Движок подбирает пул из `sysconf(_SC_PHYS_PAGES)` — это память
**машины**, а не лимит cgroup: в контейнере с лимитом 1 GiB он видит 19 971 MiB и целится в
пул около 16 GiB, никогда не вытесняя страницу. Дефект настоящий и исправлен — где лимит
строже машины, Crosskit называет потолок в половину лимита (`memory.max` cgroup v2 или
`memory.limit_in_bytes` v1), и `doctor` печатает и потолок, и лимит, из которого он выведен.
Никакой настройки: число приходит от ядра.

Но причиной роста он не был: с ним одним прогон по-прежнему убивался, а с контрольными
точками проходит и при нейтрализованном пуле (292–403 MiB против 253–336 MiB с ним). Место он
заслужил другим — сдвигает границу, с которой машина справляется:

| лимит | до этапа 17 | после |
| --- | --- | --- |
| 1 GiB | проходит, cold init 653 MiB | проходит, cold init **547 MiB** |
| 704 MiB | проходит | — |
| 640 MiB | ядро убивает на первой индексации | **проходит**, cold init 463 MiB |
| 512 MiB | — | ядро убивает на первой индексации |

Наименьший рабочий лимит для корпуса в 10 000 файлов — **640 MiB** вместо 704 MiB. Предельный
файл в 16 MiB под лимитом 512 MiB индексируется целиком, пик 342 MiB. Пол у потолка пула —
256 MiB, вдвое от наименьшего, при котором предельный файл ещё индексируется (перемерено: при
64 MiB он отвергается, при 128 MiB проходит); под лимитом, где половина оказалась бы ниже пола,
потолок не называется вовсе, потому что обмен убийства на отказ по размеру файла — обмен
худшего на ещё худшее (ADR 0023).

**Baseline аллокаций.** Feature `allocation-profile` подключает обёртку над системным
аллокатором, которая считает сумму живых аллокаций и её максимум; бинарь печатает результат
в stderr, когда заканчивается, и бенчмарки показывают его рядом с peak RSS каждой фазы.
Released Crosskit собирается с системным аллокатором и об этом ничего не знает.

```bash
cargo test --release --offline --features allocation-profile \
  --test largest_source -- --ignored --nocapture
```

Считаются **только аллокации Rust**: движок — C++ и берёт память у системного аллокатора
мимо этого счётчика. Метрика нужна не вместо RSS, а для нашей стороны — чтения, проекции,
маршалинга. Фаза здесь — одна команда CLI в своём процессе.

| Фаза | Аллокации, байт | Peak RSS в тех же прогонах |
| --- | ---: | --- |
| Корпус, A cold `index init` | 1 081 362 | 653.3 / 668.6 MiB |
| Корпус, B idle `index reconcile` | 1 079 646 | 487.8 / 479.4 MiB |
| Корпус, C после мутации | 1 066 706 | 698.1 / 695.0 MiB |
| Корпус, D после reopen | 1 087 695 | 610.2 / 558.0 MiB |
| Корпус, прерванный проход | 1 092 013 | 630.9 / 566.5 MiB |
| Источник 16 MiB, cold `index init` | 21 697 444 | 409.4 / 420.8 / 426.0 MiB |
| Источник 16 MiB, idle `index reconcile` | 21 696 037 | 280.2 / 279.7 / 271.6 MiB |

Колонка аллокаций совпадает побайтно во всех повторах; RSS тех же фаз расходится до 52 MiB.
Порога по этим числам не выдумывается: это baseline, с которым сравнивается следующее
изменение читающего слоя. Содержательно: на корпусе из мелких файлов наша сторона держит
около мегабайта, то есть почти весь RSS принадлежит движку; на одном источнике в 16 MiB —
20.7 MiB, то есть содержимое источника и его чанки.

**Идентичность файла на файловых системах, переиспользующих inode.** Crosskit берёт
идентичность файла как `file:unix:<device>:<inode>`. ext4 и overlayfs отдают освободившийся
номер inode следующему созданному файлу, APFS — никогда. Поэтому на Linux новый файл может
получить идентичность удалённого: его ревизии повиснут на `File`-узле удалённого, а ретайр
прочитается как relocated, а не как просто missing. В мутации бенчмарка это происходит с
499–500 файлами из 500, на macOS — ни разу. Бенчмарк это измеряет и утверждает
`relocated == renamed + reused` вместо числа, верного для одной файловой системы. Решение
по самой модели идентичности не принималось.

### Нагрузочная проверка индексирования

Масштабный сценарий живёт в ignored-тесте `tests/scale_indexing.rs` и никогда не
выполняется обычным `cargo test`. Он Unix-only: бенчмарк гоняет descriptor-relative
walker и снимает права с каталога, чтобы прервать проход. На других платформах весь
бенчмарк компилируется прочь, поэтому обычный `cargo test` собирается как всегда, а явный
запуск с `--ignored` честно падает с сообщением, что нужен Unix, вместо имитации
измерений. Он измеряет и проверяет текущий pipeline
`walker → SourceCommit → одна транзакция на источник → evidence, current state, InsightJob`
на большой директории:

```bash
cargo test --release --offline --test scale_indexing -- --ignored --nocapture
CROSSKIT_SCALE_PROFILE=scale cargo test --release --offline --test scale_indexing -- --ignored --nocapture
```

Профиль задаёт `CROSSKIT_SCALE_PROFILE`: `smoke` (~1 000 файлов, по умолчанию), `scale`
(10 000 включённых текстовых файлов), `stress` (25 000, только вручную) — или просто число
включённых текстовых файлов, например `50000`. Числовая форма нужна кривой по размеру
корпуса, точкам которой не соответствует ни одно прилагательное. Пиковый RSS
меряется снаружи, средствами ОС; на macOS:

```bash
CROSSKIT_SCALE_PROFILE=scale /usr/bin/time -l \
  cargo test --release --offline --test scale_indexing -- --ignored --nocapture
```

Corpus синтетический и детерминированный: файлы генерируются из индекса, поэтому два
прогона одного профиля дают одинаковое дерево. Личные файлы пользователя не читаются и не
используются. Corpus создаётся в отдельной benchmark-директории (по умолчанию во временном
каталоге, либо в `CROSSKIT_SCALE_DIR`), база — в собственном `CROSSKIT_DATA_DIR` внутри
неё, и ничего за пределами этой директории тест не трогает. Директория остаётся после
прогона для inspection, её путь и файл `report.txt` печатаются в выводе.

Corpus содержит вложенные тексты, бинарные файлы, metadata-only каталог, файл больше
лимита содержимого, встроенные Exclude (`.git`, `node_modules`, `target`, `.env`, `*.key`,
`.pnpm-store`, `vendor`, `__pycache__`) и правило по маркеру каталога,
symlink наружу и hard link. Четыре фазы: cold `index init`, idle `index reconcile`,
reconcile после детерминированной мутации (изменение, удаление, переименование, перенос
под Exclude, создание) и reopen с двумя сценариями восстановления: прерывание из-за
нечитаемого каталога и убийство процесса в середине прохода.

Отдельный ignored-тест `tests/largest_source.rs` индексирует один источник предельного
размера — файл ровно на потолке `max_content_size_mb`, 16 MiB и 4 096 чанков — и повторяет
по нему idle reconcile. Корпус scale состоит из мелких файлов и такого источника не
содержит, а именно он задаёт стоимость одной транзакции, поэтому его меряют отдельно:

```bash
cargo test --release --offline --test largest_source -- --ignored --nocapture
```

Тест утверждает, что источник прочитан как контент и нарезан целиком: если потолок когда-
нибудь опустится ниже 16 MiB, файл станет metadata-only и тест упадёт здесь, вместо того
чтобы молча мерить не то. Сам потолок закреплён unit-тестом рядом с читателем политики.

Для каждой фазы печатаются профиль, число файлов и размер corpus, wall-clock, peak RSS,
размер базы, все счётчики CLI и число queued `InsightJob`. Каждый вызов CLI измеряется
своим процессом, поэтому отчёт говорит, какая фаза держит пик, а не одно число на весь
прогон. В `report.txt` попадают те же строки, включая прерванный проход с его кодом
возврата; проход, убитый сигналом, не измеряется намеренно, и отчёт об этом говорит.
Проверяются инварианты, а не время: тест не содержит порогов по времени и памяти, потому
что они зависят от машины. Измерения — это baseline для будущих оптимизаций, а не обещание
фиксированной скорости где угодно.

### До какого дерева это масштабируется

Кривая по размеру корпуса и атрибуция того, что растёт, живут в ignored-тесте
`tests/corpus_scale.rs`. Три измерения, каждое отвечает на свой вопрос:

```bash
# кривая: 10k/25k/50k/100k файлов, холодная индексация и холостая сверка, каждая в своём процессе
cargo test --release --offline --test corpus_scale -- --ignored --nocapture \
  --exact indexing_a_tree_of_every_size_stays_within_the_memory_of_the_machine

# слои одного прохода: всё / только локации / только поисковый индекс
cargo test --release --offline --test corpus_scale -- --ignored --nocapture \
  --exact where_the_memory_of_a_pass_belongs

# критерий: равные проходы в один растущий граф
cargo test --release --offline --test corpus_scale -- --ignored --nocapture \
  --exact a_pass_costs_the_tree_it_walks_or_the_graph_it_writes_into
```

Добавьте `--features allocation-profile`, чтобы рядом с памятью процесса встала своя:
аллокации, которые стоят на месте, пока RSS растёт, говорят, что растёт не Crosskit.

**Что утверждает бенчмарк.** Только равные проходы, и только отношением. Последний проход
делает работу первого над графом в `N` раз большим и не имеет права стоить пропорционально:
планка — половина пропорционального числа. Измеренное лежит на 2.0x, форма со сканами
давала 9.4x, поэтому планка разделяет их с запасом и не закрепляет число одной машины.
Секунды не утверждаются никогда, пик памяти — тоже (он диагностика, правило этапа 2U).

**Числа этапа 18, macOS, без лимита.** Кривая по размеру корпуса:

| файлов | холодная | пик RSS | холостая сверка | пик RSS | база | индекс |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 000 | 20.8 с | 561 MiB | 14.4 с | 461 MiB | 107 MiB | 3.1 MiB |
| 25 000 | 62.5 с | 1 024 MiB | 48.0 с | 653 MiB | 253 MiB | 7.5 MiB |
| 50 000 | 161.2 с | 1 220 MiB | 140.4 с | 681 MiB | 464 MiB | 15.1 MiB |
| 100 000 | 445.0 с | 1 443 MiB | 440.0 с | 774 MiB | 643 MiB | 30.1 MiB |

**Настоящее дерево против этой кривой, та же машина. Перемерено 26 сентября 2026.** Контекст
`gitlab-two`, холодная индексация десяти корней:

| корпус | файлов | чанков | холодная | пик RSS |
| --- | ---: | ---: | ---: | ---: |
| синтетика | 25 000 | ~26 250 | 62.5 с | 1 024 MiB |
| **дерево владельца** | **26 125** | **105 236** | **118.6 с** | **2 732 MiB** |

**Почему строка перемерена.** Этап 35 записал сюда 182.3 с и 2 890 MiB, сняв их на машине, где
восемь процессов держали по ядру каждый — состояние, прожившее 27 часов и накрывшее замеры
этапов с 31 по 36. Перемер на незагруженной машине (load 1.3, 86 % простоя): два холодных
прогона подряд в свой `CROSSKIT_DATA_DIR`, тот же бинарник, **117.9 и 119.2 с, пик 2 724 и
2 740 MiB**, файлов и чанков ровно столько же — 26 125 и 105 236. Загруженная машина завысила
время в 1.54 раза, пик — на 5.5 %: ошибка по времени вышла на порядок крупнее ошибки по
памяти. Направление искажения безопасное — занятая машина делает числа хуже настоящих, —
но 182.3 с уже стояли в документации как измеренный факт.

При том же числе файлов настоящее дерево стоит **в 2.7 раза больше памяти** и почти вдвое
больше времени. Отношение по времени — единственное здесь смешанное: 62.5 с синтетики сняты
этапом 18 на машине, состояние которой никто не записал, и на чистой машине не перемерялись.
Требование «гигабайт на 25 000 файлов» из таблицы под лимитом к такому дереву
**не применимо**, и оговорка «реальный каталог будет стоить иначе» получила своё число.

Чем эти корпуса различаются — названо, посчитано и **не сведено к причине**: синтетика даёт
1.05 чанка на файл (39 файлов из 40 — меньше одного чанка), дерево владельца — **4.03**;
в нём лежат `alder-core` — 2 892 файла и 690 МБ документов — и десять корней вместо
одного. Какая из этих трёх разниц отвечает за 2.7x, **никто не устанавливал**: атрибуции пика
на настоящем дереве не делал ни один этап, и до неё это наблюдение, а не объяснение.

Синтетическая таблица ниже остаётся как есть: она честна про то, что мерила.

До этапа 18 холостая сверка 50 000 файлов шла **2 086.5 с** против 140.4 с сейчас — в
14.9 раза дольше, — а на 100 000 заняла бы больше двух часов. Причина была не в памяти:
шесть statements пути записи доставали строки сканом вместо ключа, поэтому проход стоил не
дерева, которое обходит, а всего графа, в который пишет. Разбор — в ADR 0024.

Равные проходы по 10 000 файлов в один граф, последний к первому: **9.42x → 2.03x**. На
десяти проходах, то есть на ста тысячах файлов в одном графе, — 3.01x при графе, выросшем
в десять раз: пропорционально было бы 10x, логарифмически 3.3x.

**Что росло и чем вылечено (этап 19).** Аллокации самого Crosskit шли за числом файлов **в
проходе**: 32.1 МБ на 10 000 против 116.8 МБ на 100 000. Разбор показал, что копятся не
документы — писатель сбрасывает сегменты сам и упирается в плато 27 МБ, — а очередь удалений,
по 1 240 байт на файл, линейно и без границы. Уменьшить запись очереди нельзя: термин в три
байта вместо тридцати восьми стоит 1 210 Б против 1 240, то есть платится структура вокруг
термина, а она принадлежит библиотеке.

Причина оказалась не в интервале коммита, а в работе, которой не должно быть. Проход читает
каждый файл, который обходит; у неизменившегося файла версия остаётся текущей, поэтому условие
публикации выполнялось — и **каждая холостая сверка переписывала индекс целиком**. Теперь
публикуется только файл, чья текущая версия изменилась, а файлу, которого граф раньше не знал,
удаление не ставится вовсе: его документов в индексе нет.

| проход | 10 000 | 25 000 | 50 000 |
| --- | ---: | ---: | ---: |
| холодная индексация, до | 32.1 | 49.2 | 55.0 МБ |
| холодная индексация, **после** | **19.93** | **19.91** | **19.98 МБ** |
| холостая сверка, до | 32.2 | 50.6 | 81.4 МБ |
| холостая сверка, **после** | **1.22** | **1.24** | **1.27 МБ** |

Цена, измеренная A/B на одной машине: холодная индексация +3.0%, холостая сверка +3.7%,
переоткрытие +2.8% — внутри разброса, — а сверка после массовой мутации +11.4%, вне его.
Платится один дополнительный запрос к графу на батч. Латентность запроса не пострадала
(97.5 → 99.3 мс медиана), размер индекса тот же. Разбор — в ADR 0025.

Интервал коммита при этом не трогали: индекс по-прежнему коммитится один раз в конце прохода,
как решил этап 9. Ручка для будущих замеров есть — feature `search-commit-benchmark` берёт
интервал из `CROSSKIT_SEARCH_COMMIT_FILES` при компиляции, — и она выключена.

## Структура проекта

```text
crosskit/
├── Cargo.toml
├── README.md
├── docs/
│   ├── knowledge-graph-architecture.md
│   └── adr/
├── tests/           CLI smoke-тесты, включая изоляцию контекстов и границу выхода
│                     содержимого, и ignored: live_model_call плюс нагрузочные
│                     scale_indexing, largest_source, memory_diagnostic, batch_limits,
│                     engine_tuning
├── apps/            оболочки поверх ядра: `panel/` (нативная macOS) и `desktop/` (Swift,
│                     ещё нет); решение и его причины — в ADR 0032 и ADR 0058
└── src/
    ├── lib.rs       ядро как библиотека: наружу — только `run_to_exit_code`
    ├── main.rs      CLI-бинарь; здесь же `#[global_allocator]` диагностической сборки
    ├── domain/          knowledge/ (словарь типов, предложение модели, цитата, ключ
    │                    сущности, проверка ответа, вид карты — ADR 0048),
    │                    evidence, insight_job, insight_work, insight_result, insight_topic,
    │                    insight_budget, insight_cache, file_identity, file_location,
    │                    index_policy, reconcile, run_retention, search_rank,
    │                    text_normalization, source_path, source_commit, workspace,
    │                    context_proposal, context_grouping, proposed_context,
    │                    project_signals, git_remote
    ├── application/     initial_scan, reconcile, run_retention, watch, insight_queue,
    │                    insight_worker, insight_analysis, knowledge_map, search, search_index,
    │                    search_indexing, policy_explain, context_proposal,
    │                    subtree_volumes, repository и порты source_walker, watch_ports,
    │                    search_ports
    ├── infrastructure/
    │   ├── anthropic/   единственный провайдер модели и единственное место с сетью
    │   ├── analysis/    выбор движка, инструмент подписки и knowledge_answer — один вопрос
    │   │                и одна схема ответа на оба движка
    │   ├── config/      файл политики `[index]`, `[workspace.…]`, `[insight]`, `[search]`,
│   │                `[ask]`, `[watch]` и `[knowledge]`, и единственное место, которое его пишет
    │   ├── insight_run  одна композиция очереди на `index jobs run` и `index watch`
    │   ├── filesystem/  descriptor-relative walker, notify watcher и plain-text evidence
    │   ├── ladybug/     миграции, store-модули, репозиторий LadybugDB и graph_presence —
│   │                состояние контекста, читаемое без открытия базы
    │   └── search/      анализатор, индекс на контекст, коллектор строк-документов и ключ
    │                    сущности тем же анализатором
    └── presentation/    команды setup, status, migrate, doctor, index, index rebuild,
                         index recover, index runs, index watch, index jobs,
                         index jobs run, index jobs withdraw, policy,
                         contexts propose, search, ask, touches, graph, knowledge;
                         context_draft — один рендер черновика для setup и propose;
                         one_voice_tests — составные сообщения этого слоя, каждое
                         проверено на то, что не говорит одного и того же дважды;
                         общий разбор `--context`
```

## Возможности

- обнаружение Claude Code, Codex, Cursor, OpenCode, GitHub Copilot и ChatGPT;
- онбординг при первом запуске;
- компактная локальная статистика по каждому найденному инструменту при каждом запуске;
- количество чатов и использованных токенов, когда клиент хранит эти данные локально;
- остаток лимита Codex, если в локальной сессии есть актуальные rate-limit данные;
- общий объём установки и локальных данных каждого инструмента на диске.

Недоступные локально показатели отображаются как `—`. Для серверных лимитов некоторых
провайдеров позже потребуется отдельная интеграция с их API.

Чтобы повторно запустить сканирование и показать онбординг:

```bash
cargo run -- --reset-onboarding
```
