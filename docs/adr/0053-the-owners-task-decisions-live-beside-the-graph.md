# ADR 0053: решения владельца о задачах живут рядом с графом, а не в нём

Статус: принято 2026-10-29 (срез 2 разработки задач), ждёт приёмки владельца. Схема графа не
меняется, остаётся v18. Номер машинного ответа не меняется (2): у `tasks --json` добавлено поле
`confirmed`, прежнее поле `tasks` (кандидаты) значит то же, что значило.

## Контекст

Срез 1 (ADR 0052) вычисляет кандидатов в задачи при каждом вызове. Поправить их нельзя: нельзя
слить раннюю и позднюю фазы одной работы, убрать лишнюю беседу, назвать задачу. Владелец решил
начать срез 2 с этого.

Предлагалось хранить задачи в графе: миграция v18 → v19, таблицы `Task` и `TaskMember`. До кода
выяснилось, что это не годится.
- **У графа один писатель — фоновая служба (ADR 0049).** Она держит файловую блокировку базы всё
  время работы. Пишущая команда сначала спрашивает «Stop the service? [y/N]», ждёт до 130 с,
  пока служба отпустит базу, и запускает её снова. Для решения, которое человек принимает за
  секунду и будет принимать из интерфейса, это неприемлемо.
- **Служба работает на копии программы**, которая обновляется только `service restart`. Копия
  под v18 открывает базу v19 на запись без отказа, а на вопросы отвечает старым кодом.

## Решение 1: книга решений — файл контекста

Решения лежат в `tasks-<контекст>.json` в каталоге данных, рядом с `graph-<контекст>.lbug`.
Граф остаётся тем, что прочитано с диска, а файл — тем, что решил человек. Так же рядом с графом
уже лежат решения человека о контекстах и исключениях в `config.toml`.

Файл заменяется целиком: он пишется рядом с собой и переименовывается поверх старого. Читатель
видит книгу либо до решения, либо после, но не половину. У файла есть номер версии. Файл
незнакомой версии программа отказывается читать, а не читает как что-то другое.

Отклонено:

| вариант | почему нет |
| --- | --- |
| таблицы в графе (v19) | каждое решение останавливает службу; старая копия службы не видит новую схему |
| служба пишет решения в граф | граф — это прочитанное с диска; смешивать с ним решения человека значит, что `index rebuild` и миграции должны знать, чего не трогать |

## Решение 2: решение сильнее сшивки

Книга (`domain::task_book`) хранит подтверждённые задачи и отклонённых кандидатов, а при каждом
показе накладывается на свежих кандидатов (`TaskBook::arrange`):
- **беседа принадлежит одной задаче**: перенести её можно, только сначала убрав из прежней;
- **убранная беседа** (`drop`) больше не предлагается для этой задачи, даже если сшивка снова её
  свяжет. Вернуть её можно только явно (`add`);
- **отклонённый кандидат** (`reject`) не предлагается снова, пока все его беседы остаются внутри
  отклонённого набора. Если к ним присоединилась новая беседа, кандидат появится снова: с новой
  беседой это уже другой вопрос;
- **кандидат, задевший подтверждённую задачу**, не показывается отдельно. Его остальные беседы
  предлагаются этой задаче (`proposed`), и владелец решает, добавлять ли их.

`confirm` берёт сильно связанные беседы кандидата. Беседы, связанные только соседством, остаются
предложенными. Беседу называют по сессии или по её началу, если оно однозначно; список печатает
первые восемь символов. Задачу называют по имени или по id: id — `task:<первая сессия>`, и
переименование его не меняет.

## Решение 3: решения принимает служба, отказ приходит данными

Пока служба работает, ни одна другая программа не может открыть граф, а решению нужны кандидаты.
Поэтому `tasks` во всех формах — список, решение, текст и `--json` — сначала спрашивает службу.
Служба принимает решение сама: граф у неё открыт, а пишет она только файл книги. Текст CLI
печатает из машинного ответа службы, так что доска одна, а способов её напечатать два.

Отказ решения (беседы нет, начало сессии неоднозначно, имя занято) приходит от службы не фразой,
а видом и данными: `{"declined": {"kind": "ambiguous-conversation", "reference": …,
"sessions": […]}}`. Фразу собирает CLI, и это та же фраза, что дал бы его собственный прогон.
Правило машинного ответа «ни одной фразы в поле» не нарушено. Без этого клиент получил бы голую
категорию, ответил бы сам и сказал бы «база занята» вместо «такой беседы нет».

## Цена

- **Книга и граф могут разойтись.** В книге может остаться беседа, которой граф больше не знает,
  например после `index rebuild` в чистый каталог. Она остаётся в задаче, в список не попадает и
  не теряется.
- **Решения пишутся без блокировки между процессами.** Служба и CLI без службы не пишут книгу
  одновременно: CLI пишет сам, только когда службы нет. Два CLI одновременно — гонка, при которой
  последняя запись выигрывает. Это принято для одного человека за одним компьютером.
- **Правки владельца станут разметкой, но пока ею не стали.** Каждое `drop` и `reject` — это
  ответ на вопрос, где сшивка ошиблась. Считать по книге точность сшивки — отдельный шаг.
