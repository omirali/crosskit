# ADR 0056: карта задачи сводится из карт её бесед

Статус: принято 2026-10-29, ждёт приёмки владельца. Схема графа не меняется. Номер машинного
ответа не меняется (2): в `tasks map --json` добавлено поле `joined`.

## Контекст

Первая версия карты (ADR 0055) размечала каждую беседу отдельно, и карта задачи была склейкой
карт бесед по датам. Владелец спросил прямо: зачем тогда карта решений в рамках задачи? Главное
в концепции — общая основная линия задачи и риск, который тянется из беседы в беседу, — этим не
давалось.

## Решение 1: два слоя

- **Карта беседы** (ADR 0055) — слой доказательств. Каждый узел стоит на реплике и дословной
  цитате. Это дорогой слой: модель читает реплики, и строится он один раз с дальнейшим
  достраиванием.
- **Карта задачи** — слой смысла. Модель читает не реплики, а узлы карт бесед с их кодами
  (`c0.f3`, `c1.r5`) и возвращает:
  - основную линию задачи — ключевые решения по порядку, где одно решение из нескольких бесед
    стало одним шагом;
  - риски задачи — один риск из разных бесед стал одним пунктом;
  - находки вне задачи.

  Это десятки килобайт вместо мегабайт, поэтому слой стоит центы и пересобирается, как только
  выросла любая карта беседы.

## Решение 2: смысл ограничен доказательствами

Пункт карты задачи сам ничего не доказывает. Он называет узлы карт бесед, а у каждого из них
есть цитата. Программа (`domain::task_synthesis::grounded`):
- **отбрасывает код**, которого нет ни в одной карте, и пункт, у которого не осталось ни одного
  кода;
- **называет риск закрытым или принятым** только если так помечен хоть один из его узлов;
  иначе риск открыт, что бы ни сказала модель;
- **ставит уровень риска не ниже худшего из его узлов** и поднимает его на ступень, если
  открытый риск поднимался трижды и больше (`RAISED_OFTEN`). Это правило концепции «повтор
  поднимает уровень», и работать оно может только на уровне задачи.

От любого пункта карты задачи можно дойти до беседы, реплики и цитаты: вывод называет их
(`«Договоры и пакеты…» [62]`), а `--json` отдаёт сессию, код узла и номер реплики.

## Решение 3: сводка помнит, из чего сделана

Сводка хранится в `maps-<контекст>/task-<id>.json` вместе с «отпечатком» карт, из которых она
сделана: сессия, версия вопроса и последняя реплика каждой беседы. Если отпечаток разошёлся с
картами, сводка показывается с пометкой «устарела», и следующий `--build` собирает её заново.
Если не разошёлся, `--build` её не трогает.

`tasks map <задача>` показывает карту задачи. Карты отдельных бесед видны с `--detail`, а с
`--only <беседа>` показывается одна беседа без сводки: сводка собирается из всех.

## Решение 4: вопрос v3 для бесед

Первый запуск v2 показал три изъяна, и вопрос v3 (`decision-map-v3`) отвечает на каждый:
- **граница окна читалась как конец беседы.** Теперь окно говорит: «реплики N–M из K, беседа
  продолжается»;
- **пропускались самые дорогие решения.** В каждом окне обязательно проверяются прод (данные,
  скрипты, релиз, обход ревью), секреты и массовые правки данных;
- **модель писала о собственной разметке.** Теперь она прямо названа размечающей, а не
  участником беседы.

Смена версии вопроса перестраивает карты бесед заново: смешивать узлы двух вопросов нельзя.

## Чего ещё нет

Связи бесед из сшивки (эстафета, названная беседа) пока не рисуются на основной линии. Порядок
шагов задаёт модель по датам бесед. Ребро «продолжение» между беседами — следующий шаг.

## Первый запуск, 29 октября 2026

Задача `quarry`: две беседы на v3 — `quarry-ledger` (381 реплика) и связанная с ней беседа на
59 реплик. Затем сводка `--join`: она сводит уже построенные карты и о репликах ничего не
спрашивает.

| | |
| --- | --- |
| карты бесед на v3 | 2,40 $ + 0,55 $ |
| сводка | 0,34 $ |
| в сводке | 8 шагов основной линии, 46 рисков (32 открыты), 5 находок вне задачи |

**v3 улучшил риски и испортил развилки.**
- Найдены оба `critical`, которые v2 пропускал: массовые правки прод-базы скриптами без MR и
  отсутствие ролей модуля на проде. Граница окна больше не читается как конец беседы.
- Развилок в `quarry-ledger` стало **6 вместо 21**: пропали «сначала данные», форма без AI,
  обязательный договор. Перечень проверок отнял внимание модели у решений владельца.
- Поэтому и основная линия задачи пока бедная: 8 шагов, среди них мелочь вроде формата имён
  таблиц в документации.

Вывод: один вопрос не держит одновременно решения владельца и проверку рисков.

**Следующее — два прохода на окно:**
- первый ищет только решения владельца — то, что хорошо делал v2;
- второй ищет только риски по перечню v3.

Это примерно вдвое дороже, зато каждый проход занят одним делом.
