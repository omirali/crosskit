# ADR 0052: задачи сшиваются по графу, а не по журналам

Статус: принято 2026-10-29 (первый срез разработки задач), ждёт приёмки владельца.
Схема графа не меняется: остаётся v18. Номер машинного ответа не меняется (2): `tasks --json` —
новый объект рядом с прежними.

## Контекст

ADR 0051 приняла направление: задача — сущность Crosskit, беседы сшиваются в неё по фактам из
журналов, без модели. Замер на машине владельца подобрал правила и нашёл главное препятствие:
Claude Code удаляет журналы примерно через месяц, а копии в хранилище Codex теряют инструменты,
имя и время.

Владелец выбрал начать разработку с ядра, до разметки списка кандидатов.

## Решение 1: сшивка читает граф

Граф уже хранит по каждой беседе имя, время каждой реплики и говорящего, текст реплик кусками
и касания файлов с глаголом и временем (ADR 0036, 0041). Этого хватает на четыре признака из
пяти: эстафету, названную беседу, задачу трекера и общие файлы.

Сшивка читает граф, а не журналы, потому что граф хранит прочитанное, когда журнала на диске
уже нет. Первый прогон на машине владельца нашёл задачу из бесед 1–9 сентября, журналов которых
на диске уже нет.

Порт `ConversationLogReader` отдаёт записи как есть: реплики с говорящим, куски с текстом,
касания. Какой кусок сказал владелец, решает application тем же правилом, по которому периоды
размещают кусок во времени (`replies_behind`, ADR 0043). Кусок принадлежит владельцу, только
если владельцу принадлежат все реплики, из которых он мог быть вырезан.

Отклонено:

| вариант | почему нет |
| --- | --- |
| читать журналы на диске, как замер | беседы старше месяца пропали бы, а с ними начало задачи |
| хранить связь «кусок → реплика» в схеме | правило без схемы уже есть и проверено на периодах; новая колонка — это миграция ради того, что считается |

## Решение 2: правила замера становятся правилами продукта

Правила замера переносятся в продукт как есть: `StitchRules::product`.
- общий журнал — файл или ветка, которых касается больше 4 бесед;
- продолжение ищется в первых трёх репликах владельца;
- эстафета — только через документ;
- беседа, которая называет больше двух других, — обзор.

Модуль `domain::task_stitching` перестаёт быть замерочным: продукт и замер сшивают одними
правилами. Подписи признаков для отчёта замера живут в отчёте, а в домене их нет.

## Решение 3: чего этот срез не знает и говорит об этом

- **Рабочий каталог и ветка беседы в графе не хранятся.** Признак «одна ветка» в продукте не
  срабатывает. Местом беседы для признака «соседство» служит папка её журнала: Claude Code
  кладёт беседы одного каталога в одну папку. Хранить каталог и ветку — отдельное решение, со
  сменой схемы.
- **Codex Crosskit не индексирует.** Его беседы и копии в продукт не попадают, это следующий срез
  через app-server (ADR 0051, решение 3).
- **Относительное имя файла из одного компонента** (`handoff.md`) не превращается в ключ: каталога,
  от которого его отсчитать, граф не знает. Путь из двух компонентов и больше ключом служит сам.

## Решение 4: реплика за куском восстанавливается по длине кусков

У правила `replies_behind` есть слабое место. Если хоть одна реплика длиннее 16 КиБ (вставленный
вывод запроса, дамп), её режут на несколько кусков. С этого места правило знает только
промежуток реплик, из которых мог быть вырезан кусок. Кусок засчитывается владельцу, только если
все реплики промежутка — его. Поэтому после одной длинной вставки почти вся дальнейшая речь
владельца терялась. На графе владельца так выпала связь «Договоры и пакеты в проде» →
«Counterparty данные…»: в октябре в эту беседу вставляли большие выводы SQL.

Нарезка детерминирована (`pieces_of`). Каждый кусок разрезанной реплики, кроме последнего, весит
16 КиБ, без максимум трёх байт до границы символа. Значит, кусок такой длины продолжает реплику,
а любой другой её заканчивает. `exact_replies_behind` считает реплики по этому правилу. Если
счёт совпал с числом реплик беседы, реплика за каждым куском известна точно. Если не совпал
(реплика случайно кончилась ровно на размере куска), остаётся промежуток. Размер куска теперь
живёт в домене, `MOST_BYTES_PER_REPLY_CHUNK`, и его читают и запись, и чтение.

Периоды по-прежнему пользуются промежутком. Перевести их на точное правило — отдельное решение
со своей проверкой.

## Решение 5: кандидат вычисляется, а не хранится

`crosskit tasks` вычисляет кандидатов при каждом вызове. Подтверждение, слияние и деление задач
человеком требуют хранения, и это следующий срез. Пока владелец не разметил кандидатов, хранить
нечего, кроме догадок.

## Как проверено

- Модульные тесты домена и application на выдуманных беседах.
- Сквозной тест на настоящем графе: три журнала проиндексированы, беседа, открытая на чужом
  handoff, найдена в одной задаче с ним, а посторонняя — ни в какой
  (`infrastructure/task_pipeline_tests.rs`).
- Прогон на графах владельца: `personal` — 3 кандидата за 0,3 с, `work` — 4 кандидата за 0,8 с.
  Задача `quarry` в `work` была разбита на несколько кандидатов, а бесед её поздней фазы в графе
  не было.
- **Причина — граф, не сшивка.** Граф `work` последний раз обновлялся 1 октября, `personal` —
  5 октября: фоновая служба не установлена, а ручных проходов после этих дат не было. При этом
  граф держит 68 бесед из папки, где на диске их осталось 12. Claude Code удалил остальные, а
  Crosskit сохранил.
- **Проход `index reconcile` на копии графа `work`** (3 мин 13 с, машина загружена):
  - ни одно место файла не отмечено пропавшим, и беседы, которых нет на диске, сохранились;
  - с новыми беседами и правилом решения 4 задача `quarry` — один кандидат из 11 бесед, от
    2 сентября до 21 октября;
  - ранняя фаза той же работы (6 бесед, 1–9 сентября) — отдельный кандидат. Одна ли это задача,
    решает владелец: это подтверждение и слияние, то есть следующий срез.
