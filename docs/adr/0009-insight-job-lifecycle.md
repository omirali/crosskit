# ADR 0009: жизненный цикл InsightJob

Статус: принято 2026-09-21 (Этап 5)

## Контекст

С этапа 2F каждая сохранённая ревизия кладёт в outbox durable `InsightJob` (ADR 0005).
Очередь наполняется и растёт, исполнителя нет. Состояние было ровно одно — `queued`.

Исполнителю нужны не модели, а механика: взять задание так, чтобы его не взял никто
другой; вернуть его, если процесс умер посреди работы; повторить ограниченное число раз;
не записать второй результат для одного задания; не материализовать очередь целиком.
Всё это проверяемо без единого AI-провайдера, поэтому вводится сначала оно, а обработчик
на этом этапе — детерминированный.

## Решение

### Состояния и переходы

```text
                      ┌────────── worker пропал ──────────┐
                      │        (срок аренды истёк)        │
                      ▼                                   │
   queued ────claim────► claimed ────результат────► done  │
     ▲   ▲                  │                             │
     │   └──────────────────┴─────────────────────────────┘
     │                      │
     │                  отказ обработчика
     │                      ▼
     └──── попытки есть ── failed ── попытки кончились ──► dead
```

Пять состояний: `queued`, `claimed`, `done`, `failed`, `dead`. Каждый переход —
отдельная транзакция.

Один проход worker'а делает три вещи по порядку:

1. **Recovery.** Возвращает то, что никто не держит: `claimed` с истёкшей арендой и
   `failed`. Каждое либо снова `queued`, либо `dead`, если попытки кончились.
2. **Claim.** Берёт страницу `queued` в порядке постановки. *(Этап 24 назвал этот порядок
   точно и исправил его: старейшая ревизия первой — ADR 0030.)*
3. **Работа.** Обработчик вызывается вне транзакции; записывается только исход —
   `done` вместе с результатом, либо `failed` с категорией.

`failed` — отдельное хранимое состояние, а не немедленный возврат в очередь. Это
судейское решение: так один проход пробует задание ровно один раз и не крутится на
отравленном задании N раз подряд. `dead` возвращается только вручную — «без
автоматического возврата» из постановки этапа.

Попытка считается **в момент захвата**, а не в момент завершения. Иначе задание, которое
убивает процесс, никогда не дойдёт до предела и будет повторяться вечно.

### Аренда вместо проверки живости

Захват пишет `claimed_at_unix_ms` и `lease_expires_at_unix_ms` — абсолютный момент, а не
длительность. Возврат определяется сравнением с текущим временем, а не тем, жив ли
процесс: живость нельзя узнать после перезапуска, а срок лежит в базе и переживает его.

Про часы отдельно, потому что это был кандидат в вердикт **C**. Wall clock не годился бы,
если бы от него зависела корректность. Он от него не зависит:

- перевод часов (DST) не влияет — Unix-время монотонно в UTC и не знает о зонах;
- скачок NTP назад продлевает аренду: задание подождёт дольше, ничего не теряется;
- скачок вперёд освобождает аренду рано: задание вернётся в очередь и будет сделано
  второй раз, но **второго результата не появится** — его отвергает схема, а не расчёт
  времени;
- между машинами вопрос не стоит: база — embedded, один writer, один процесс.

Поэтому корректность держится не на часах, а на схеме и на транзакциях; аренда влияет
только на то, как быстро брошенное задание вернётся. Вердикт **A**, а не **C**.

### Идемпотентность схемой

`InsightResult.id` выводится из id задания: `insight-result:<job id>`. Второй результат
того же задания отвергается primary key. Связь
`HAS_INSIGHT_RESULT(FROM InsightJob TO InsightResult ONE_ONE)` отвергает и второе ребро,
поэтому результат нельзя добавить, просто переименовав его. Проверки в коде нет — обе
защиты в схеме, и обе проверены тестом, который пытается записать второй результат и
читает граф после отказа.

### Ограниченность

Ни один запрос не читает очередь целиком:

- захват — `ORDER BY created_at_unix_ms, id LIMIT $limit`, лимит параметр, не конкатенация.
  *(Этап 24 заменил ключ сортировки на момент наблюдения ревизии и переименовал колонку в
  `revision_observed_at_unix_ms` — ADR 0030. Ограниченность осталась той же.)*;
- recovery — страницы по 500 строк, цикл до пустой страницы; страница всегда покидает
  состояние, из которого прочитана, поэтому цикл заканчивается;
- сводка — один групповой `COUNT` по состояниям, не более пяти строк.

`--limit N` ограничивает проход целиком; страница захвата — внутренняя константа 100.

### Схема v10

```text
ALTER TABLE InsightJob ADD attempts INT64 DEFAULT 0;
ALTER TABLE InsightJob ADD claimed_at_unix_ms INT64 DEFAULT 0;
ALTER TABLE InsightJob ADD lease_expires_at_unix_ms INT64 DEFAULT 0;
ALTER TABLE InsightJob ADD last_error_category STRING DEFAULT '';
CREATE NODE TABLE InsightResult(id PRIMARY KEY, job_id, source_revision_id,
                                input_content_hash, chunk_count, text_bytes,
                                produced_at_unix_ms);
CREATE REL TABLE HAS_INSIGHT_RESULT(FROM InsightJob TO InsightResult ONE_ONE);
```

Уже сохранённые поля, включая `created_at_unix_ms`, не переписываются: миграция только
добавляет колонки. Значение по умолчанию применяется и к строкам, созданным позже, —
это проверено против движка, поэтому путь записи outbox (set-based, ADR 0007) не
менялся ни одним оператором, и цена индексации осталась прежней.

### Категории отказа

Закрытый набор: `input` — граф не держит того, что называет задание (ревизии нет, или
хеш содержимого не тот); `handler` — обработчик не смог сделать работу; `lease-expired`
— захват кончился раньше, чем worker. Ни текста движка, ни текста провайдера, ни
содержимого файла; в записи задания и в выводе команды — только категория.

### Обработчик как порт

`InsightHandler` получает захваченное задание и отвечает результатом или категорией.
Реализация этапа — `RevisionSummaryHandler`: считает по уже сохранённым чанкам ревизии
их число и сумму байтовых диапазонов (`COUNT(chunk)` и `SUM(end_byte - start_byte)`).
(Этап 6 перенёс его в application под именем `CountedInsightHandler`, чтобы оба обработчика
читали вход через один порт; что он делает, не изменилось — ADR 0010.)
Текст чанков не читается ни одним запросом, поэтому содержимое файла не может попасть ни
в результат, ни в отчёт, ни в ошибку. AI-обработчик встанет на то же место: жизненный
цикл о нём ничего не знает.

## Инварианты

1. Захваченное задание не выдаётся второму worker'у; состояние входит в паттерн,
   который его двигает, поэтому переход, который больше не применим, ничего не меняет и
   сообщает об этом.
2. Истёкшая аренда возвращает задание в очередь; попытка при этом уже посчитана.
3. Отказ обработчика не пишет ничего, кроме состояния и категории: частичного результата
   не существует.
4. После предела попыток задание `dead` и само в очередь не возвращается.
5. У задания не может быть двух результатов — это свойство схемы.
6. Переиндексация файла во время работы worker'а не трогает ни состояние захваченного
   задания, ни его аренду, ни его попытки; новая ревизия даёт новое задание.
7. Ни один запрос не материализует очередь целиком.

## Условие, при котором проверка перехода перестаёт быть достаточной

Записано здесь, чтобы нашли там, где будут менять.

Переход из `claimed` проверяет, что задание **всё ещё захвачено**, а не что его захватил
именно этот worker. Отличить один захват от другого нельзя моментом времени: два захвата
помещаются в одну миллисекунду, — для этого нужен токен захвата с nonce, который пишется
при захвате и входит в паттерн перехода.

**Пока writer один, токен не нужен.** База embedded, `enable_multi_writes(false)`, один
процесс: проигравший гонку в худшем случае повторит работу, но второго результата не
появится — его отвергает схема.

**Условие смены: появление фонового сервиса с несколькими исполнителями** (этап
«Background service», `crosskitd`, или любой другой режим, где по одной базе работают
два и более worker'а одновременно). С этого момента проверки «ещё захвачено»
недостаточно: worker, чья аренда истекла и чьё задание уже взял другой, допишет свой
результат по чужому захвату. Тогда захват обязан писать токен, `ClaimedInsightJob` —
нести его, а переходы `complete` и `fail` — включать его в паттерн наряду с состоянием.

## Что не входит в этап 5

AI-провайдеры, сеть, токены, промпты, кэш, entity resolution; несколько видов заданий;
daemon и IPC; поиск. Per-path `IndexJob` по-прежнему остаётся будущей моделью daemon/IPC
(ADR 0005): watcher работает как «событие → dirty flag → полный reconcile».

## Последствия

Очередь, которая наполнялась с этапа 2F, теперь доходит до результата, и каждый её
отказ виден числом и категорией. Insight Layer получает готовое гнездо: заменяется
обработчик, а не жизненный цикл.

Поиск (прежний этап 5) сдвигается на этап 6 — он опирается на результаты, которых до
этого этапа не существовало.
