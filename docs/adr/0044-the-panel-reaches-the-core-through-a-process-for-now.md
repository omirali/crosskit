# ADR 0044: панель ходит к ядру через процесс — пока

Статус: принято 2026-10-01 (Этап UI-3). Временное отступление от ADR 0032, решение 3. Схему
графа и набор полей индекса не меняет; добавляет один внешний контракт — машинный ответ.

## Контекст

ADR 0032 провёл границу между приложениями и ядром процессом-демоном `crosskitd`. Демона нет,
протокола нет, а панель (`apps/panel/`) до этого этапа показывала выдуманную выдачу. Владелец
хочет попробовать панель на своих беседах и файлах раньше, чем строить демон, — и только
такая проба скажет, каким демону быть.

Вопрос этапа поэтому не «как дотянуться до ядра», а «годится ли самое простое — по процессу
`crosskit` на каждый запрос — для ежедневной работы, и если нет, то почему». Известная цена
названа заранее: открытие хранилища и старт процесса на каждый запрос.

## Решение 1: мост — CLI с машинным ответом, а не второй вход в базу

Панель не открывает базу и не читает `config.toml`. Всё, что она знает о данных, приходит из
двух команд:

- `crosskit contexts --json` — настроенные контексты, из одной конфигурации;
- `crosskit --context <имя> search <запрос> --json [--limit N] [--after <курсор>]` — страница.

CLI не стал клиентом демона и не изменил поведения для человека: без флага текст тот же байт в
байт (тест `tests/cli_search_json.rs` сравнивает с выводом сборки, где флага не было). Поток
команды один; текстовый отчёт печатает по ходу, как прежде, машинный — собирает и печатает
один объект в конце.

## Решение 2: схема одна, с номером, и отказ — её объект

Машинный ответ объявлен в одном месте, `src/presentation/machine_answer.rs`, и несёт
`"schema": 1`. Номер растёт, когда поле меняет смысл или исчезает; добавленное рядом поле его
не меняет. Читатель сверяет номер первым и ответ другого номера не читает вовсе — это и есть
ответ на «версионирование протокола», которое ADR 0032 назвало платой за границу-процесс, в
самом малом виде.

В схеме **только то, что ядро умеет сегодня** (`apps/panel/docs/row-shape.md`): путь, вид строки,
имя беседы и её сессия, выдержка, совпавшие слова, тема, курсор следующей страницы, «не
показано» по политике, по отсутствию на диске и по отставанию индекса. Групп, «недавнего» на
пустой запрос и поиска по теме там нет — они отсутствуют, а не пусты.

**Вид строки решает граф.** Строка — беседа ровно тогда, когда ревизию её файла прочитали как
беседу: у неё есть `Conversation` (ADR 0036). Поиск читает её тем же разрешением совпадений,
одним запросом по ключу `conversation:<ревизия>`, который писатель и читатель вычисляют одной
функцией. Текстовый вывод этого не печатает и не изменился.

**Отказ — объект схемы** с категорией из закрытого списка (`usage`, `unreadable-query`,
`configuration`, `no-context`, `context-required`, `unknown-context`, `not-indexed`, `busy`,
`needs-migration`, `needs-recovery`, `index-unreadable`, `failed`) и кодом выхода 1. Категория
решается там, где типизированная ошибка ещё в руках (`src/presentation/refusal.rs`), а не
угадывается потом по словам. В stdout нет ни сообщений движка, ни путей вне поля `path`;
предложение для человека идёт в stderr, как всегда.

Известный край: отказ, случившийся раньше, чем команда дошла до `search`, — `--context` без
имени, `--help` — остаётся текстом. Панель так не спрашивает.

## Решение 3: старая буква не затирает новую и не держит процесс

Каждый запрос панели получает номер; ответ принимается, только если он новее последнего
принятого (`AnswerOrder`). Новая буква отменяет задачу старой, и отмена завершает процесс
(`SIGTERM`), а не дожидается его — иначе быстрый набор копит процессы, и каждый держит
открытую базу. Процесс, не ответивший за 10 с, завершается, и панель говорит «ядро не
ответило». Все три поведения проверены тестами цели `CrosskitPanelTests`.

## Измерено

Дерево владельца, 1 октября 2026. Панель собрана Debug, ядро — `cargo build --release`.
50 запросов из одного–трёх обычных слов разработки (файл вне репозитория), плюс прогрев
первым запросом, который в счёт не идёт; страница 8 строк. Запрос подставляется в строку
целиком, нажатия клавиши нет — подделать его без «Универсального доступа» нельзя; доставка
нажатия до обработчика — доли миллисекунды (замер UI-1).

Состояние машины: `vm.loadavg` 2.55 перед первым прогоном `work`, 1.93 перед вторым, 3.52
перед третьим; сверху `ps` — по одному процессу на 7–14 % (VS Code, `mds`, расширение
редактора), без сборок и других замеров рядом.
Время, снятое на машине с loadavg ~2–3, завышено (`.claude/rules/20-quality-workflow.md`), —
значит, ниже сказано скорее «не лучше чем», чем «ровно».

**От строки запроса до кадра со строками** (панель, `--replay`):

| контекст | документов | p50 | p95 |
| --- | --- | --- | --- |
| `work`, прогон 2 | 120 786 | 128.6 мс | 150.5 мс |
| `work`, прогон 3 | 120 786 | 132.5 мс | 152.1 мс |
| `personal` | 4 843 | 115.4 мс | 125.7 мс |

По отрезкам, `work`, прогон 3 (p50 / p95):

| отрезок | p50 | p95 |
| --- | --- | --- |
| от смены строки до запуска процесса | 2.6 мс | 4.2 мс |
| процесс `crosskit search --json`, от запуска до выхода | 112.4 мс | 131.2 мс |
| разбор JSON в страницу | 0.8 мс | 1.1 мс |
| перестройка экрана | 6.7 мс | 7.1 мс |
| до ближайшего кадра | 9.4 мс | 10.5 мс |

Внутри процесса (`bridge_measurement`, те же 50 запросов, те же шаги, что у `search --json`;
каждый запрос открывает и закрывает всё заново):

| шаг | p50 | p95 |
| --- | --- | --- |
| конфигурация и выбор контекста | 0.3 мс | 0.4 мс |
| открытие графа | 28.8 мс | 29.7 мс |
| открытие индекса | 0.2 мс | 0.2 мс |
| запрос | 28.3 мс | 49.4 мс |
| строка JSON | 0.0 мс | 0.0 мс |
| закрытие | 12.4 мс | 13.2 мс |
| **итого в процессе** | **70.1 мс** | **91.4 мс** |

Старт программы без единого открытия — `crosskit --version` из панели — 6.0 / 6.9 мс.
Остаток процесса, **≈ 36 мс** (112.4 − 70.1 − 6.0), измерен только как разность: это то, что
процесс платит один раз, а повторные вызовы внутри одного процесса — нет. Первый вызов в
свежем процессе замера дал 298 мс на открытие графа, но снят он сразу после пересборки, на
холодном кеше файлов, и ценой каждого процесса его считать нельзя.

**Первая версия моста стоила на 30 мс больше, и причина — в панели.** Задача запроса
наследовала главный поток и стартовала только после того, как он перерисует экран с пометкой
«обновляется»: «до запуска процесса» был 31.7 мс, итог — p50 152.6 / p95 172.1. Запрос теперь
уходит отвязанной задачей до перерисовки.

**Под фильтром «Чаты» (⌘2)** на `work`: p50 130.0 мс, **p95 414.0 мс**. Фильтра в запросе ядра
нет (row-shape.md, конфликт 6), и когда первая страница ядра не держит ни одной беседы, панель
дочитывает следующие — каждая новым процессом, до первой беседы и не больше четырёх. Отрезок
«процесс» при этом тот же (p50 112.0), поэтому хвост — число процессов, а не машина, хотя снят
он сразу после семи сборок feature (`vm.loadavg` 6.55, за 15 минут — 6.89). Первая версия
добирала до полной страницы и стоила p50 413 мс.

**Рядом с `index watch`** (песочница, не дерево владельца: 3 000 файлов, 200 правок каждые
0,5 с — проход за проходом без пауз, 200 запросов `search --json` раз в 50 мс): **26 отказов
`busy` из 200 (13 %)**, ответивших — p50 76 мс, p95 543 мс, максимум 746 мс. Это не ломает
порядок ответов и не оставляет процессов, но читатель рядом с идущим проходом то не
пускается, то ждёт его.

## Вердикт: А

**p95 от строки до выдачи — 151–152 мс на `work`, меньше ~200 мс.** Мост годится для ежедневной
работы, и демон (этап 13, только чтение) ждёт другой причины. Одно исключение — фильтр ⌘2/⌘3:
p95 414 мс, но лечит его не демон, а фильтр по виду строки в запросе ядра — тогда это снова
один процесс. Две причины демона уже видны и названы числом:

- **Блокировка.** Во время прохода `index watch` 13 % запросов получают `busy`, и p95 растёт до
  543 мс. Пока проходов нет — а у владельца `watch` большую часть времени ждёт событий, —
  этого нет совсем. Демон, который сам владеет записью, отвечает на чтение без этого спора
  (ADR 0032, причина 2).
- **Фиксированная цена процесса — главная статья.** Из 112 мс процесса запрос — 28; открытие
  графа (29), закрытие (12) и разовая цена процесса (≈ 36) — 77 мс, которые не зависят от
  запроса и почти не зависят от размера контекста (`personal` на 4,8 тыс. документов — 95 мс
  процесса). Долгоживущий процесс снял бы их целиком; на сегодняшнем числе это не нужно.

Остальные причины из постановки — `ask` в панели и долгоживущий индекс — этим этапом не
мерились.

**При каком числе мост перестаёт годиться.** Когда p95 того же замера на том же контексте
перейдёт 200 мс на спокойной машине, или когда доля `busy` станет заметна в обычной работе, а
не только под непрерывными проходами. Запас сегодня — около 50 мс; запрос на 120 тыс.
документах — 28 мс из них, и он растёт с контекстом, а остальное — нет.

## Что остаётся временным

- Процесс на каждую страницу. Граница по ADR 0032 — по-прежнему демон; мост остаётся
  запасным путём и тогда, когда демон появится: CLI сохраняет прямой доступ (ADR 0032,
  решение 4).
- Список контекстов читается один раз при старте панели; конфигурация, изменённая после
  запуска, видна после перезапуска.
- Время файла в ответе `search` не отдаётся — его нет в разрешении совпадений, и схема его не
  придумывает.

## Как повторить

```bash
sysctl -n vm.loadavg; ps -Ao pcpu,comm -r | head
cargo build --release --offline
xcodebuild -project apps/panel/CrosskitPanel.xcodeproj -scheme CrosskitPanel build
APP=$(xcodebuild -project apps/panel/CrosskitPanel.xcodeproj -scheme CrosskitPanel \
      -showBuildSettings | awk -F' = ' '/ BUILT_PRODUCTS_DIR /{print $2}' | head -1)
"$APP/CrosskitPanel.app/Contents/MacOS/CrosskitPanel" \
  --core="$PWD/target/release/crosskit" --context=work --replay=<файл запросов>

CROSSKIT_BRIDGE_CONTEXT=work CROSSKIT_BRIDGE_QUERIES=<файл запросов> \
  cargo test --release --offline --lib bridge_measurement -- --ignored --nocapture
```

Файл запросов — по запросу на строку, вне репозитория. Панель печатает каждый запрос и итог,
затем выходит.
