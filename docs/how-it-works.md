# Как это работает

Этот документ — для понимания, а не для справки. Он объясняет, что делает Crosskit, из
чего он собран и почему собран именно так, на схемах и обычными словами. Технические
термины объясняются там, где впервые встречаются; словарь — в конце.

Остальные документы отвечают на другие вопросы, и этот их не заменяет:

| документ | вопрос, на который он отвечает |
| --- | --- |
| `docs/knowledge-graph-architecture.md` | какова цель системы и где её границы |
| `docs/adr/` | почему принято конкретное решение и на каких измерениях оно стоит |
| `README.md` | как этим пользоваться: команды, конфигурация, числа |
| `HANDOFF.md` | где проект стоит прямо сейчас |
| **этот файл** | **как всё это работает вместе и зачем устроено так** |

## 1. Что такое Crosskit

Локальное приложение, которое строит граф знаний о файлах на вашем компьютере: что есть
на диске, как оно менялось, что внутри, и — в перспективе — что об этом думает ИИ.
Ничего не уходит в облако без явного разрешения, база лежит файлом на вашей машине.

Сегодня система **честно знает, что лежит на диске и как оно менялось**, **умеет искать по
словам** внутри контекста, **отвечает на вопрос** по своим файлам моделью и **разбирает беседы
с ИИ как беседы**, а не как текстовые файлы: у беседы есть имя, реплики и перечень файлов,
которых она касалась. Беседа лежит в том же контексте, что и проект, в котором она шла.

Смотреть на это можно двумя способами: командой `crosskit` в терминале и **панелью** —
окном по ⌥Space, которое ищет, показывает граф связей беседы и её файлов (раздел 12) и карту
знаний контекста (раздел 13).

Чего нет:

- **ответов модели через службу.** Служба держит базы и отвечает на чтение — поиск, граф, карту
  знаний — по своему сокету (раздел 7, ADR 0050), но `ask` идёт мимо неё: он зовёт модель, а
  служба сама к модели не ходит;
- **проверенного на настоящем корпусе слоя знаний.** Слой построен (раздел 13): модель достаёт
  из файлов и бесед сущности и связи-факты, у каждой связи — цитата, которую программа нашла в
  источнике, а панель рисует их картой. Но разобран им пока только выдуманный корпус: сколько
  фактов он даст на рабочих документах владельца и сколько отвергнет — не измерено;
- **противоречий** («это решение отменяет то») — их никто не ищет. И отдельно: расширять вопрос
  словами, которые часто стоят рядом в беседах, измерили и отказались — поиску это не помогло
  (раздел 15).

## 2. Что лежит в графе

**Граф** — способ хранения, где есть *узлы* (вещи) и *связи* между ними. Наши узлы:

```text
                    ┌──────────┐
                    │   File   │  сам объект файловой системы —
                    └────┬─────┘  не путь, а то, на что путь указывает
                         │
          ┌──────────────┼──────────────┐
          │              │              │
    LOCATED_AT      HAS_VERSION    HAS_OBSERVATION
          │              │              │
   ┌──────▼──────┐ ┌─────▼──────┐ ┌─────▼──────────┐
   │FileLocation │ │FileVersion │ │FileObservation │
   │ путь, имя,  │ │ содержимое │ │ «видели тогда» │
   │ размер,     │ │ с таким    │ │                │
   │ present /   │ │ отпечатком │ │                │
   │ missing     │ └─────┬──────┘ └─────┬──────────┘
   └─────────────┘       │              │
                    HAS_CHUNK        ORDERS
                         │              │
                 ┌───────▼──────┐  ┌────▼──────────────┐
                 │ ContentChunk │  │ ObservationOrder  │
                 │ кусок текста │  │ номер по порядку: │
                 │ см. ниже     │  │ что было позже    │
                 └──────────────┘  └───────────────────┘
```

Размер куска задаёт не константа, а разборщик. У текста это ~4 КБ на границе пробела. У
беседы кусок — **одна реплика**, и это не аккуратность, а условие: правило «слово, сказанное
в трёх разных репликах, весит больше слова, четыреста раз повторённого в одном вставленном
логе» существует только тогда, когда у реплики есть граница, которую можно посчитать.

Три идеи, на которых держится вся модель:

**Файл — это не путь.** Путь может измениться, объект останется тем же. Поэтому пути живут
отдельными узлами, и у одного файла их может быть несколько (жёсткие ссылки — когда один
и тот же файл виден под двумя именами).

**Версия неизменяема.** Изменили файл — появилась новая версия, старая осталась навсегда.
История не переписывается.

**Наблюдение — самостоятельный факт.** «Мы видели эту версию в такой-то момент» — не
свойство версии, а отдельная запись. Поэтому повторная сверка ничего не портит: она
добавляет факт, а не правит старый.

Поверх этих узлов с этапа знаний лежат ещё три (раздел 13): `Entity` — понятие работы,
названное ключом имени; `EntityMention` — как его назвал один файл; `Fact` — связь двух сущностей
с цитатой, проведённая ребром к куску, в котором цитата найдена. Знание всегда указывает на
доказательство, а не наоборот: карта читает факт только через ребро к его куску.

### Беседа — тоже доказательство

Транскрипт сессии с ИИ — файл как файл, но внутри него разговора мало. Померили: **2.46 %
его байт** — это то, что кто-то сказал. Остальное — вывод инструментов (он лежит в файле
дважды, в обвязке строки и в теле сообщения), вложенные файлы, размышления модели и
служебная обвязка на каждой строке. Индекс, читавший транскрипт как текст, отвечал на
вопросы про логи.

**И даже из этих процентов не всё сказал человек.** Этап 37 померил: под ролью владельца, уже
после отбрасывания `isMeta`, лежат блоки, которые положила туда обвязка — отчёт фонового
задания, строка редактора о том, какой файл открыт. Это **31 % его байтов**, они есть в 37 %
его реплик, и доля разговора в корпусе с ними 2.51 %, а без них 2.26 %. Ни один вывод от этого
не меняется, но «слова владельца» в любом числе этого проекта — это роль в транскрипте, а не
то, что человек набрал руками. Разбор — `docs/insight-layer-measurement.md`, вердикт Б.

Поэтому у беседы свои узлы:

```text
   FileVersion ──HAS_CONVERSATION──► Conversation
                                      имя, кем названа, когда шла,
                                      сколько реплик
                                          │
                                     HAS_MESSAGE
                                          │
                                     ┌────▼─────┐
                                     │ Message  │  роль: владелец или модель
                                     └────┬─────┘
                                       TOUCHED
                                          │
                                     ┌────▼──────────────────────────┐
                                     │ FileTouch                     │
                                     │ путь строкой, глагол, время   │
                                     │ глагол: читал / писал / правил│
                                     └───────────────────────────────┘
```

**Имя берётся из двух строк, а не из одной.** Claude Code даёт беседе имя сам и по ходу его
меняет; владелец может переименовать её своей рукой. Его имя побеждает модельное, последнее
побеждает предыдущие. Без этого правила беседа «Беседа Е» называлась бы
`Conversation D`, и вопрос по-русски её бы не нашёл.

**`FileTouch` — это факт, а не догадка модели.** Когда инструмент открывает файл, он
записывает это структурным полем: имя действия и путь. Отсюда и глагол. Пути, выдранные из
строк команд оболочки, **не** извлекаются: у них глагол неизвестен в принципе (`cat` читал,
`sed -i` правил, `rg` просто просмотрел), и 61 % таких путей на настоящем дереве вообще не
существует. Записать их значило бы записать догадку.

**Цель связи — путь строкой, а не узел файла.** Беседа часто трогает файлы, которых в её
контексте нет: чужой проект, системный каталог, файл, удалённый с тех пор. Ребро к узлу,
которого нет в базе, построить нельзя, а базы разных контекстов не пересекаются намеренно
(раздел 6). Поэтому записывается путь, а превращение пути в файл — работа читателя, в момент
чтения и **только внутри своего контекста**. С тех пор как беседа лежит в контексте своего
проекта (этап 39, раздел 6), её касания своих файлов почти всегда находят файл: так граф в
панели и рисует линию «беседа → файл». Касание файла вне контекста остаётся путём — видно,
что он был, а перехода нет. Путь, записанный инструментом относительно (`docs/…`), читается от
корня проекта беседы.

**У касания есть две отметки, и обе — для чтения, а не для отбора.** Агент открывает по дороге
чужие файлы: ищет, идёт по импорту, заглядывает к соседу за соглашением. Это факты, и граф их
держит, но «мы работали над этим файлом» значит не это. Поэтому на касании записано, сколько
раз оно случилось и **назвал ли владелец этот файл своими словами**, а строгость живёт в
команде `touches`: в ответ по умолчанию входит то, что писали, правили или назвали, остальное
сосчитано и открывается флагом. Правило простое и выбрано замером: имя файла, сказанное
человеком — не внутри блока, который обвязка сама положила под его роль. Ничего при этом не
выбрасывается: касание, которое не записали, восстановить нечем, а записанное можно спрятать
в любой момент.

Плюс служебное:

```text
CURRENT_VERSION      какая версия актуальна сейчас
CURRENT_OBSERVATION  каким наблюдением это подтверждено
InsightJob           «эту версию надо проанализировать» — очередь
ReconcileRun         запись о каждом проходе сверки — и о каждой попытке,
                     которая обходом не стала (статус `failed` и категория отказа)
```

## 3. Путь одного файла через систему

```text
каталог, в который собираемся войти
  │
  ├─ 0. несёт CACHEDIR.TAG или pyvenv.cfg? ─► да ─► не входим вовсе,
  │                                                 поддерево не существует
  ▼ нет
файл ~/Notes/idea.md
  │
  ├─ 1. политика: читать?  ─► нет ─► только метаданные, конец
  │                        ─► пропустить ─► ни одного системного вызова
  ▼ да
  2. открыть безопасно
     открывается относительно уже открытого каталога, без перехода
     по символическим ссылкам, с проверкой, что это обычный файл
  │
  ▼
  3. снять отпечаток: устройство, номер файла, рождение, размер, mtime
  │
  ▼
  4. каким разборщиком читать — решает имя файла
     имя кончается на .jsonl ─► разборщик беседы
     иначе                   ─► разборщик текста
     имя обещало беседу, а внутри её нет ─► читается как текст,
                                            и это отчёт разборщика, а не нюх
  │
  ▼
  5. прочитать потоком:
     текст   — первый проход SHA-256 и проверка UTF-8, второй — куски ~4 КБ
     беседа  — строка за строкой, реплики складываются, остальное считается
               и выбрасывается
     текста нет нигде ─► версия публикуется, кусков ноль
  │
  ▼
  6. проверить, что файл не менялся во время чтения
     менялся ─► не публикуем вовсе, считаем «нестабильным»
  │
  ▼ не менялся
  7. одна транзакция:
     путь → файл → версия → наблюдение → куски → текущее состояние
     → задание в очередь
     ошибка на любом шаге ─► не записалось ничего
```

Шаг 6 — то, чего обычно не делают. Если файл переписали ровно в момент чтения, в базу
попал бы «франкенштейн» из двух версий. Такое мы просто не публикуем и считаем отдельным
счётчиком.

**Предел на содержимое считается по содержимому, а не по обёртке.** У текста это одно и то
же: файл и есть содержимое, и слишком большой файл не открывается вовсе. У транскрипта нет:
самая крупная беседа владельца — 58.5 МиБ файла и 1.5 МБ разговора внутри. Пока предел
сравнивали с файлом, она была невидима поиску целиком, и никакое ранжирование не дотянулось
бы до того, что не проиндексировано. Теперь предел применяется к разговору, а чтение
останавливается, как только сказанного набралось на предел, — а не после того, как всё уже
лежит в памяти и осталось вынести приговор.

**Транзакция** — «всё или ничего»: либо записались все куски, версия и связи, либо ничего.
Проверяется не обещанием, а тестами с инъекцией ошибки в середину записи.

## 4. Чего система принципиально не делает

Главный принцип — **отказ по умолчанию**. Если правило не сказало «можно», ответ «нет».

```text
путь не покрыт ни одним правилом   → не индексируется
файл не отнесён к контексту        → содержимое не читается
контекст не разрешил выход наружу  → запрос к модели не собирается
идентичность под сомнением         → заводится новая, история не сливается
пропуск не подтверждён             → watcher честно работает по таймеру
```

Ошибка в сторону «не сделали» дешёвая и заметная. Ошибка в сторону «сделали лишнее» —
утечка или испорченная история, и она необратима.

Ещё одно сквозное правило — **приватность вывода**: в консоль и в сообщения об ошибках
никогда не попадают пути скрытых политикой файлов, текст документов и внутренние
сообщения движка базы. Это проверяется тестами-сентинелами: в файл кладётся уникальная
строка, и тест требует, чтобы она не нашлась там, где её быть не должно.

## 5. Идентичность файла

Файл опознаётся парой «номер диска + **inode**» (внутренний номер файла в файловой
системе). Этого оказалось мало:

```text
macOS (APFS):
   удалили A (inode 500) → создали B → B получил inode 991      всё хорошо

Linux (ext4, overlayfs):
   удалили A (inode 500) → создали B → B получил inode 500
   ┌──────────────────────────────────────────────┐
   │ B наследует узел File удалённого A           │
   │ версии A остаются висеть на этом узле        │
   │ истории двух разных файлов слипаются         │
   └──────────────────────────────────────────────┘
```

Обнаружилось случайно: при прогоне в Linux-контейнере счётчик переименований показал 999
вместо 500. Проверка отдельно: ext4 переиспользует номер в 20 случаях из 20, в мутации
сценария — 498 из 500.

Решение: граф запоминает, когда впервые увидел файл под этой парой, и сравнивает с
**временем рождения** файла (birth time — момент создания, отдельный от времени
изменения). Файл, родившийся позже первого наблюдения, не может быть тем файлом, и
получает свою ветку идентичности. Идентификаторы уже известных файлов при этом не
меняются.

Правило одностороннее: при любой неуверенности идентичность считается новой. Разделить
историю одного файла надвое — поправимо. Слить историю двух разных — нет.

На файловых системах, которые не хранят время рождения, ветвиться нечем, и защита не
работает. Программа не молчит об этом: `doctor` говорит о способности платформы, а
каждый скан считает источники, у которых времени рождения не оказалось.

## 6. Контексты: граница конфиденциальности

На одной машине лежат файлы работодателя, личные проекты, иногда файлы другого человека.
Требование простое: **когда ИИ отвечает внутри рабочего контекста, ничего из личного не
может быть упомянуто, процитировано или использовано**.

Это не фильтр удобства, а граница конфиденциальности. Разница принципиальная: фильтр
можно починить потом, границу — нет.

```text
конфигурация:
   контекст «работа»  ← ~/work/**, ~/Projects/acme-*
   контекст «личное»  ← ~/Projects/my-blog, ~/Documents/личное/**
   остальное          ← не индексируется вовсе

на диске:
   graph-работа.lbug   ← две отдельные базы,
   graph-личное.lbug      а не одна с колонкой «чей файл»
```

Почему две базы, а не пометка на узлах: **запрос не может выйти за пределы своей базы
физически**. В одной общей базе изоляция держалась бы на том, что никто и никогда не
забудет дописать условие в очередной запрос. Здесь забывать нечего.

Границу держат три вещи:

```text
1. пересечение правил запрещено   две маски не могут претендовать на один
                                  путь — конфигурация отвергается при загрузке
2. корень принадлежит контексту   команда с чужим или ничьим корнем
                                  отказывает до открытия базы
3. базы раздельны                 кросс-запроса не существует
```

Показательный эпизод: сначала был написан четвёртый механизм — исключать чужие пути прямо
в обходе. Потом выяснилось, что он недостижим: если корень ваш, а пересечения запрещены,
чужого пути внутри быть не может. Механизм удалили. Недостижимый код, который якобы
держит границу, хуже его отсутствия — его нельзя проверить.

Цена строгости: вырез поддерева («работа» на весь домашний каталог, «личное» на папку
внутри него) не выражается — такие правила пересекаются и отвергаются.

Одна команда работает **внутри** одного контекста: и разговор с ИИ, и поиск принадлежат
одному, и переключение означает новую сессию, а не смену фильтра. Обойти несколько за один
запуск умеют только те команды, которые ничего не пересекают, — `status` читает каждый
контекст, `migrate` приводит каждый к схеме сборки, `setup` индексирует каждый, который
только что записал. Они открывают контексты по очереди, каждый своей базой; ни одна функция
не получает двух сразу.

### У контекста несколько корней, и обходятся все

Контекст — это не одна папка. В конфигурации он объявлен **списком** корней: у владельца
сегодня два контекста, и в рабочем их 21 (проекты, их папки бесед и две папки без git), в
личном — 4. До этапа 39 контекстов было пять, по хостам git, и корней семнадцать.

Долгое время единица работы этому не соответствовала. Обход брал **один каталог**, и
провести список через него мог только `setup` — а он останавливал контекст на первом же
каталоге, который не прочитался. Чем это кончилось, написано в разделе 14; коротко — восемь
корней из десяти не индексировались никогда, а программа пятнадцать этапов отвечала
«проиндексировано».

Теперь единица работы совпадает с единицей конфигурации:

```text
обход по контексту: корень за корнем, каждый отдельно
   корень не прочитался ─► он назван, с причиной и с записью попытки в графе
                           остальные девять идут дальше
   итог ─► «Roots walked: 9 of 10», а не «удалось / не удалось»
```

И это видно каждый день, а не один раз в выводе, который никто не сохранил: `status` печатает
каждый корень, сколько в нём файлов и когда его в последний раз обходили. Корень, которого не
обходили ни разу, говорит об этом словами.

Каталог как аргумент остался — но как сужение по явной просьбе, а не как единственная
возможность.

**Отложено сознательно** (записано в ADR 0008 как принятое направление, не реализовано):
общий контекст для книг и справочников, который читают остальные; тени — пометка «у этого
содержимого есть двойник в другом контексте» без раскрытия, где именно; смешанные папки с
назначением пофайлово; классификация контекста через ИИ.

### Откуда берётся первая конфигурация

Всё выше описывает, как контексты работают, когда они уже написаны. Но написать их надо с
чистого листа: маски путей по дереву, которое человек помнит в общих чертах и точно не
помнит поимённо. Это и есть место, где настройку бросают.

`crosskit contexts propose <каталог>` обходит дерево и печатает **черновик**. Не
конфигурацию — черновик: команда ничего не пишет, ни конфига, ни базы, ни индекса.

```text
обход (тот же, что у скана)        улики                      сборка
──────────────────────────        ─────                      ──────
каталог за каталогом,       →  .git и хост его remote    →  группа = хост
относительно дескрипторов      Cargo.toml, go.mod …         группа = «без remote»
симлинки не траверсятся        Documents, Downloads …       группа = «личное»
нечитаемый — счётчик           объём и глубина              остальное → список
                                                            «решайте сами»
```

Ключевое в этой картинке — стрелки идут в одну сторону. Ни один шаг не спрашивает модель,
не ходит в сеть и не смотрит на имена файлов «похоже ли это на проект». Улика — это
найденная на диске вещь с точным именем: запись `.git`, файл `Cargo.toml`, каталог
`Downloads` прямо в домашнем каталоге. Под каждой строкой черновика напечатано, на какой
улике она стоит; строки без улики не бывает.

**Одно исключение для содержимого.** Команда не читает файлы — кроме `.git/config`, и из
него берутся только **хост** remote и **первая группа** его пути (`gitlab.example.org` и
`acme` из `…/acme/team/repo.git`). Не URL целиком, не подгруппы, не аккаунт, не имя
репозитория: значение, которое поднимается из разбора наверх, физически не несёт ничего,
кроме этих двух, поэтому напечатать лишнее нечем. Группа добавилась на этапе 39: на дереве
владельца под одним рабочим сервером лежат три организации, и по хосту их не различить
(ADR 0042 поверх ADR 0019). Сам каталог `.git` не обходится: впускается он и `config` в нём,
всё остальное отвергается ещё до `stat` — хранилище объектов не открывается ни разу.

`contexts propose` — это черновик для того, кто пишет конфигурацию руками. Первый запуск
делает `setup` (ниже): он собирает те же улики, но группирует по группе `origin` и спрашивает
человека.

**Черновик обязан загружаться.** Из запрета пересечений (пункт 1 выше) следуют три правила
сборки, которые держит программа, а не читатель:

```text
репозиторий в репозитории  →  предлагается только внешний,
                              с пометкой «покрывает N внутри»
~/Documents с проектом     →  не предлагается целиком:
внутри                        вырез поддерева не выражается
два хоста и нет origin     →  не предлагается вовсе:
                              оба хоста названы, решает человек
```

Последняя строка — то же правило, что во всей системе: неуверенность объявляется, а не
разрешается в пользу удобного варианта. Проверяется это не на глаз — тест берёт вывод
команды, кладёт его в файл политики и спрашивает у `policy explain`, какому контексту
принадлежит файл внутри проекта.

Подробности и обоснование исключения для `.git/config` — ADR 0019.

### Кто отвечает на вопрос

Ответ даёт не «модель», а **движок**, выбранный один раз и используемый обеими дорогами —
и очередью разметки, и командой `ask`:

```text
[analysis] engine = "claude-code"   установленный инструмент подписки — умолчание
                 = "anthropic-api"  HTTP-провайдер с ключом в окружении
```

Умолчание — подписка, потому что её токены уже оплачены тем, кто ею пользуется. Порты при
этом не изменились: и разметка, и `ask` принимают доменный запрос и отвечают доменным
значением или категорией — ни один не знает про HTTP, ключ или подпроцесс. Третий движок
добавляется расширением одного перечисления.

Инструмент вызывается неинтерактивно, содержимое идёт ему в стандартный ввод, ответ
запрашивается по JSON-схеме. Схему инструмент **обещает**, а проверяет доменный конструктор
на этой стороне — как и у HTTP-провайдера, потому что обещание это не граница.

```text
вызов ─► своя группа процессов
      ─► таймаут 180 с ─► убивается вся группа, не один процесс
                          (внук инструмента иначе переживает вызов — измерено)
      ─► ответ не по схеме ─► категория, и ничего из написанного
                              инструментом не печатается и не хранится
```

**Чего не было у API.** Инструмент ведёт свои журналы на диске. По умолчанию он пишет
транскрипт со всем переданным содержимым в `~/.claude/projects/…`; Crosskit всегда
передаёт `--no-session-persistence`, и тогда этот файл не появляется. Но `todos` и `debug`
он пишет при каждом вызове. Это свойство канала, а не утечка Crosskit, и выбор подписки
означает согласие с ним. Измерения — ADR 0028.

Правило выхода содержимого от смены движка не изменилось: подписка не делает содержимое
локальным, разрешение контекста требуется так же, и запрещающий контекст по-прежнему
физически не может собрать вызов.

### Что разбирается, а что ждёт

Разбор стоит времени. На настоящем дереве полный разбор — 77 часов подписки, и до этого этапа
конвейер строил продукт, которого никто не читал. Поэтому решение принимается до того, как
работа появится:

```text
ревизия опубликована
  │
  ├─ покрыта automatic или approved? ─► нет ─► задания нет вовсе
  │                                            (не задание в особом состоянии — ни одного)
  ▼ да
  задание в очереди
  │
  ▼ при захвате
  ├─ правило больше не покрывает? ─► skipped, модель не вызвана
  ▼
  разбор ─► тема
```

Умолчание — документы: когда это мерили, на дереве владельца правило покрывало 1 703 ревизии
из 25 952 (6.6 %) — около пяти часов вместо семидесяти семи. **Числа с тех пор сдвинулись, и
не только оттого, что дерево живёт:** тогда в графе лежала седьмая часть рабочих корней, и
про остальные никто не знал (раздел 14). Сегодня (5 октября, два контекста) в графах 27 254
ревизии и 1 970 заданий в очереди, и ни одно ещё не разобрано: разметку никто не запускал. Пропорция, ради которой правило заводили, от этого не изменилась: платят
за разобранное, а разбирают не всё. Остальное не создаёт заданий и видно в `index review`,
сгруппированные по виду и по каталогу, каждая группа с ценой в часах. Решение принимается
пачкой и записывается маской, поэтому оно продолжает работать для того, что появится потом.

Тема после этого видна глазами: строкой `about:` в выдаче поиска и отдельным полем выдержки
в `ask`. У файла без анализа строки нет — не пустая метка, а отсутствие. Числа и обоснование
умолчаний — ADR 0029.

### Почему исключения не список имён

Первый живой прогон на настоящем дереве дал запрос `product`, у которого семь результатов из
десяти пришли из питоновского окружения. Очевидный ответ — дописать `.venv` в список — был
отвергнут: список имён отстаёт всегда, потому что знает только те инструменты, которые
существовали на момент его написания.

Поэтому правил два, и они разной природы:

```text
признак   каталог несёт CACHEDIR.TAG или pyvenv.cfg
          ─► не входим, поддерева не существует
          маркер оставил тот, кто сделал каталог, поэтому
          правило работает для инструментов, о которых мы не знаем

имя       только там, где признака нет, и только то,
          что посчитано на настоящем дереве:
          .pnpm-store, vendor, __pycache__
```

На дереве владельца два маркера пометили 15 каталогов — все питоновские окружения целиком,
ровно причину засорённой выдачи, — и слово «python» не появилось ни в одном правиле. Вместе с
тремя именами это убрало 168 687 файлов из 200 813, которые политика пропускала: остались
исходники.

Позже это пересчитали от всего дерева, а не от того, что пропускала прежняя политика, — и
правила подтвердились без остатка: в крупнейшем рабочем контексте из 379 678 файлов имена
сняли 315 991, маркеры — 37 562, вместе ровно 353 553, то есть всю разницу до 26 125
допущенных. Разные знаменатели дают разные проценты (−84 % и −93 %), а правила те же. Имена, которые «бывают», но на дереве не встретились ни разу (`.tox`, `Pods`,
`.terraform` и подобные), не добавлены — это тот же отстающий список, написанный заранее.

`.gitignore` измерен как возможная замена и отклонён: сверх принятых правил он добавил бы
2.1 % файлов, а 24 % того, что они ловят, пропустил бы — `vendor` и содержимое окружений
часто коммитят намеренно. Числа и решение — ADR 0026.

### С чего человек начинает

Раньше всего остального — `crosskit --help`: список команд, по строке на каждую, и где
начать. Грамматику одной спрашивают у неё самой (`crosskit setup --help`), и это тот же
текст, которым она отказывает, — не копия, а та же строка, поэтому справка не может
разойтись с тем, что разборщик на самом деле принимает.

Слово, которое командой не является, отвергается по имени и со списком настоящих. Это
важнее, чем кажется: до этого опечатка проваливалась в обзор найденных AI-инструментов и
**заканчивалась успехом**, так что скрипт не мог отличить сделанное от несделанного.

### Первый запуск: одна команда

Черновик, который надо вставить в файл, а потом проиндексировать каждый каталог каждого
контекста, — это всё ещё шесть команд. `crosskit setup <каталог>` — те же самые куски, и
дорога между ними:

```text
crosskit setup ~
   │
   ├─ обходит дерево              тем же кодом, что `contexts propose`
   ├─ читает рядом                папки бесед Claude Code, папки без git, домен почты git
   ├─ собирает группы             одна группа `origin`; беседы идут за своим проектом
   ├─ спрашивает                  имена контекстов → каждую группу → остаток по одной папке
   ├─ печатает файл целиком       ту самую строку, которую запишет; без «да» не пишет ничего
   ├─ записывает                  прежний файл копируется рядом, со временем в имени
   ├─ читает записанное обратно   черновик, который не загрузился, останавливает тут
   └─ индексирует каждый контекст тем же проходом, что `index init`, и печатает итог
```

Три вещи в этой картинке стоит заметить.

**Имена контекстов вводит человек.** Система не знает сторон — ни «рабочего», ни «личного»:
у одного это два контекста, у другого — «клиент А», «клиент Б» и «своё». Что она знает — что
держится вместе и почему, и спрашивает о группе один раз, а не о каждом проекте (ADR 0042).
Беседа и папка без git своего вопроса не получают: они идут за проектом. Папка бесед
проверяется, а не раскодируется: путь проекта кодируется правилом Claude Code и сверяется с
первым `cwd` внутри.

**Показанное и записанное — одна строка.** Файл рендерится один раз из ответов, печатается и
записывается без второго рендеринга: команда, которая показала одно, а записала другое,
просила бы согласия на то, чего никто не видел.

**Машина с контекстами — отказ.** `setup` — первый запуск и только он. Конфигурация, где
уже объявлен хотя бы один контекст, останавливает команду до того, как открыта хоть одна
база. Причина — та же, что во всём разделе: контекст — граница конфиденциальности, и
команда, которая сдвинула бы её (добавив правило рядом или записав поверх) на основании
того, что обход угадал по дереву, сдвинула бы то, какие файлы читаются вместе. Тот, кто
границу провёл, её и правит.

**Остаток спрашивается по одной папке.** Что не вошло ни в одну группу, предлагается после
групп, и ответ `n` касается одной папки, а не всего остатка: в первом прогоне владельца «всё или
ничего» оставило вне контекстов две рабочие папки на 290 и 1 754 файла (этап 39b). Каталоги,
которые закрыла сама macOS, называются одной строкой, а не сотней; индексация печатает по
строке на корень; каталог сессии внутри папки бесед — подагенты, вывод инструментов — в
индекс не идёт, а `memory/` идёт.

Контекст, который не проиндексировался, не забирает остальные: они — отдельные базы над
отдельными частями диска. Итог называет упавший и заканчивается ненулевым кодом.

### Что сейчас в каждом контексте, не тронув ни одного

`crosskit status` печатает все контексты сразу и не пишет ничего. Не он один: `search`,
`ask` и `doctor` — тот же класс, и с ADR 0034 ни одна из четырёх не открывает граф на
запись. Это не обещание дисциплины, а следствие того, как устроено открытие базы:

```text
открыть базу «как обычно»  →  создаст базу контекста, который никто не индексировал
                              мигрирует базу, написанную старой сборкой
                              при закрытии свернёт журнал в базу
                              а на базе после убитого прохода — иногда умрёт по сигналу
```

Все три — записи, а четвёртое — смерть процесса ровно на том состоянии, которое отчёту
важнее всего назвать. От этапа 14 до этапа 28 правило действовало для одного
`status`, а `search` рядом применял недостающие миграции при каждом запуске — замечено на
дереве владельца и записано в ADR 0034. Поэтому читающая команда сначала смотрит на **два файла**, до всякого открытия:

```text
                    журнал рядом с базой      блокировку записи на файле базы
                    (*.lbug.wal)              (кто её держит — спрашивают, не беря)
                    ──────────────────        ───────────────────────────────
простаивает              нет                       свободна
watcher между            нет                       держит watcher
проходами
проход пишет             есть                       держит этот проход
проход убит              есть                       свободна        ← остановленный проход
```

Нижняя строка — вся суть. Движок сворачивает журнал в базу, когда её закрывает; значит
журнал, рядом с которым нет живого писателя, оставил процесс, который базу не закрыл. Это и
есть нечистая остановка, и она названа **без открытия** базы, которую движок может не
пережить.

Открывается только то, у чего журнала нет, и только на чтение — открытием, которое не
создаёт и не мигрирует. Цена названа прямо: `status` не видит того, что писатель принял, но
ещё не сбросил на диск контрольной точкой, и не чинит схему — база со схемой не этой сборки
становится строкой отчёта, а не миграцией. Строка называет команду, которая чинит:
`crosskit migrate` проходит по всем контекстам за один запуск. Отчёт говорит, что делать,
и не делает сам.

То же правило и у поискового индекса: обычное открытие создало бы пустой индекс там, где его
нет, и потом отчиталось бы «пусто» про индекс, который пуст из-за самого вопроса. У `status`
своя дверь — открыть и не создавать.

Ни одно состояние контекста не роняет команду: сломанный контекст — это находка, а отчёт,
остановившийся на первом сломанном, спрятал бы остальные. Подробности — ADR 0020.

## 7. Сверка, эпохи и наблюдение за диском

Индексация — не разовое действие. Диск живёт, и граф должен за ним поспевать.

```text
index init       первичное индексирование
index reconcile  сверка: пройти заново и привести граф в соответствие
index watch      непрерывный режим
```

**Сверка** помечает исчезнувшее, а не удаляет: путь получает статус `missing`, вся
история остаётся. Если файл исчез с одного пути, но тот же объект найден по другому — это
классифицируется как перемещение.

Чтобы параллельные проходы не мешали друг другу, у графа есть **эпоха** — счётчик
проходов. Каждая запись о встрече файла штампуется текущей эпохой, и проход хоронит
только то, что не видел никто из тех, кто начал не раньше него. Часы при этом не
используются вовсе: порядок определяется счётчиком, а не временем.

**watcher** — наблюдатель за файловой системой. Он не пишет в граф: событие только
поднимает флажок «что-то поменялось», а всю работу делает обычная сверка. Причина в том,
что события файловой системы теряются, дублируются и приходят пачками, и доверять им как
источнику истины нельзя.

Отдельная история — честность режима. Оказалось, что в некоторых средах поток событий
macOS молча не работает: подписка успешна, событий нет никогда. Теперь при старте
выполняется проверка доставки, и если подтверждения нет, программа прямо говорит, что
работает по таймеру, а не по событиям.

**Наблюдает он за контекстом целиком**, за всеми его корнями сразу — одним потоком на много
путей, а не десятью потоками. Разница померена: один поток на десять путей стоит трёх
дополнительных потоков процесса, десять отдельных — десяти. И вторая, которой не ждали:
добавление путей по одному заставляло библиотеку пересобирать поток целиком, и подписка на
десяти корнях под нагрузкой срывалась. Все пути ставятся одним действием — 0.21 с на десяти
корнях против 0.23 с на одном.

Корень, который под наблюдение не встал, **не уносит остальные**: он назван, девять других
работают, в строке итога стоит «Watching: 9 of 10 root(s)».

**Сколько стоит старт, решает не только код.** macOS, подписывая процесс на события, смотрит
на каталог, из которого запущена программа. Тестовые программы запускались из
`target/debug/deps`, где отладочная сборка копила служебные файлы: к октябрю — 867 тысяч. На
таком каталоге система отвечала 10–16 секунд вместо долей миллисекунды, и тесты наблюдателя
падали, хотя продукт был цел: настоящий `index watch` из `target/release` стартует за 0.1 с.
Сборка больше этих файлов не создаёт, а тест, не дождавшийся старта, сам называет причину
(этап W). И старт теперь ограничен: подписка, не ответившая за 30 с, оставляет контекст на
таймере с причиной `StartTimedOut`, а опоздавший поток событий сам себя закрывает (ADR 0049).

И здесь важно, чего при этом **не** теряется:

```text
поток событий по корню замолчал ─► теряется ЗАДЕРЖКА: изменение
                                    заметят не сразу, а на ближайшем проходе

                                 ─► НЕ теряется покрытие: проход по таймеру
                                    всё равно идёт по всем корням контекста
```

Это и есть ответ на вопрос, который задавать надо было: честной проверки доставки **по
отдельному корню** не существует — она потребовала бы создавать события внутри наблюдаемого
дерева, то есть портить то, что наблюдаешь. И её отсутствие терпимо ровно потому, что
события ускоряют, а не заменяют. Регистрация пути при этом доказывает меньше, чем кажется:
на macOS каталог с нулевыми правами FSEvents принимает молча, отказ приходит только на путь,
которого нет.

### Кто держит базу, пока watcher работает

База контекста — один файл, и писать в него может только один процесс. Читать — сколько
угодно: замок берёт писатель, читатель не берёт никакого.

```text
   index watch — пишет                 search, doctor — только читают
   ┌───────────────────┐               ┌─────────────────────────┐
   │ держит замок базы │               │ замка не берут вообще   │
   └─────────┬─────────┘               └───────────┬─────────────┘
             │ батч за батчем                      │ снимок на момент запроса
             ▼                                     ▼
   ┌──────────────────────────────────────────────────────────────┐
   │   graph-work.lbug   +   журнал graph-work.lbug.wal рядом     │
   └──────────────────────────────────────────────────────────────┘
```

Поэтому искать во время наблюдения можно: `search` и `doctor` сначала пробуют открыть базу
как обычно, а получив отказ — открывают её только на чтение. Ответ при этом — снимок на
момент запроса: следующий запрос увидит то, что watcher успел записать между ними. Вторая
**пишущая** команда по-прежнему отвергается.

Чего это не даёт: пока проход прямо сейчас пишет, читателю бывает нечего прочитать, и
команда честно отказывает вместо ответа. Между проходами — а это почти всё время watcher'а
— она отвечает.

### Служба: наблюдатель без терминала

`index watch` живёт, пока открыт терминал. `crosskit service install` ставит агент launchd,
и тот же наблюдатель запускается при входе в систему — для **всех** контекстов в одном
процессе, по потоку на контекст.

```text
   вход в систему ─► launchd ─► …/Crosskit/bin/crosskit service run
                                   │
                    ┌──────────────┼──────────────┐
                    ▼                             ▼
            поток контекста work          поток контекста personal
            (тот же WatchService,         (замок своей базы,
             что у index watch)            свой поток событий)
                    │                             │
                    └───────► журнал service.log ◄┘   строки index watch с временем
                    └───────► status.json  ◄──────┘   фаза, режим, последний проход
                                   ▲
                    crosskit service status — читает файлы, баз не открывает
```

Три вещи здесь не очевидны.

**Программа — копия.** Служба работает не на `target/release/crosskit`, который
`cargo build` переписывает на месте, а на копии в каталоге данных. Копия меняется только по
`install` и `restart`, и `status` говорит, если запущенная сборка старее той, которой его
спросили.

**Отказ одного контекста — его отказ.** Контекст, базу которого держит терминальный
`index watch`, ждёт и пробует раз в минуту; паника в его потоке ловится и становится такой же
повторной попыткой. Остальные контексты этого не замечают — как корни внутри контекста
(выше).

**Читатель спрашивает службу.** До ADR 0050 писатель держал базу, и в моменты записи читатель
не открывал её вовсе (`busy`: 3,2 % запросов без правок, 27 % с правками на копии `work`).
Теперь служба отвечает на чтение сама — по сокету в своём каталоге, теми же строками, что
печатает CLI, из графов, которые уже держит:

```text
   панель ─┐                         ┌─► поток контекста work: пишет проходами
           ├─► crosskit.sock ─► служба
   CLI --json ┘   одна строка JSON      └─► ответ из того же графа, в том же процессе
                 туда и обратно
```

Одно правило выучено падением: читать в процессе писателя можно рядом с открытой транзакцией
записи, но **не в тот миг, когда движок двигает страницы** — при коммите и контрольной точке.
Служба падала дважды (SIGSEGV в движке), пока на эти два мига читатели не стали ждать по
замку. С ним: 0 `busy` из 4 723 запросов, падений нет.

**Проход — только по изменённому.** Раньше событие было флажком «что-то поменялось», и проход
обходил все 22 корня `work` — 2,5–3 минуты ради одного файла. Теперь путь события говорит,
где искать: проход обходит каталог, в котором была правка (при удалении — ближайший уцелевший
предок; при переезде — оба). Каталог, до которого полный обход не дошёл бы — исключённый
политикой, сгенерированный — не обходится. Решают пути только *где* смотреть; что в графе,
по-прежнему решает обход. А весь контекст обходится при старте, при любом признаке потерянных
событий и раз в 30 минут. Правка находится в поиске через 1,2 с (p50). Корень, которого нет,
больше не перепроходится повтором раз в минуту.

### Что стоит выключенный ноутбук

Принятый батч попадает не в саму базу, а в журнал рядом с ней. В базу движок переносит
журнал на **контрольной точке**: когда журнал перерастает примерно 16 МиБ и когда базу
закрывают.

```text
   проход пишет: батч → батч → батч → …          база: 4 КиБ, всё в журнале
   закрытие базы или журнал > 16 МиБ  ─────────► контрольная точка: журнал → база
```

Пока контрольной точки не было, вся работа прохода живёт в журнале. Процесс, убитый на
середине — Ctrl-C на индексации, OOM-killer, потеря питания, — теряет эту работу в любом
случае. А если проход писал новое содержимое (первая индексация, сверка после правок),
движок потом не может дочитать оставленный журнал, и тогда **контекст не открывается
ничем**: ни поиском, ни перестроением.

Раньше здесь начинался тупик: команда падала текстом движка (а на Linux — половину раз
вообще молча, сигналом), и что делать, знал только README. Теперь беда названа и у неё есть
одна команда:

```text
crosskit index recover        журнал уезжает в сторону под именем со временем, ничего не удаляется
crosskit index reconcile …    дерево читается заново, граф наполняется
crosskit index rebuild --search   индекс пишется из графа
```

Почему это честно стоит времени, а не данных: граф целиком выводится из файлов на диске.
Потеряно то, что успел записать убитый проход, — и это один проход по дереву, а не чьи-то
документы.

Чтобы терять меньше, watcher теперь складывает каждый проход в базу до того, как объявит
его завершённым. Убитый между проходами — не теряет ничего и открывается; убитый посреди
прохода — теряет этот проход, и это по-прежнему требует восстановления.

Проход, который только отмечал, что файлы на месте, базу так не ломает: она открывается,
просто без того, что он успел записать.

Измерения и решения — ADR 0014 и ADR 0015; команды — в README, раздел «Нечистая
остановка».

## 8. Очередь заданий и исполнитель

Каждая новая версия файла кладёт в очередь запись «это надо проанализировать» — в той же
транзакции, что и сама версия. Значит задание не может потеряться и не может появиться
без своей версии.

```text
                    ┌──── исполнитель пропал (истёк срок аренды) ────┐
                    ▼                                                │
  queued ──захват──► claimed ──результат──► done                     │
    ▲  ▲                │                                            │
    │  └────────────────┴────────────────────────────────────────────┘
    │                   │
    │              отказ обработчика
    │                   ▼
    └── попытки есть ─ failed ─ попытки кончились ─► dead
```

- **захват** — «взял в работу»; второй исполнитель это задание уже не получит;
- **аренда** — срок, на который задание считается взятым. Процесс умер — аренда истекла,
  задание вернулось в очередь. Решает срок, а не признак «жив ли процесс», поэтому
  механизм переживает убийство процесса и перезагрузку;
- **dead** — три раза не вышло: больше не пробуем, причина записана категорией. Часть
  причин не ждёт трёх раз: если ответ пришёл и не подходит, второй такой же вопрос даст тот
  же ответ. А вот если ответ **не удалось прочитать** — это не про ответ, и попытка
  тратится как обычная: `dead` не отменяется ни уборкой очереди, ни новой сверкой, ни
  переиндексацией файла, поэтому хоронят только наверняка (ADR 0033).

Часы здесь влияют только на скорость возврата, но не на сохранность: если задание
случайно сделают дважды, второго результата не появится — дубль отвергает схема базы.

Числа сейчас: аренда 5 минут, предел 3 попытки, захват страницей по 100, возврат
страницей по 500.

### В каком порядке берут

Очередь разбирается порциями, поэтому порядок решает, что вы увидите сегодня, а что через
неделю. Правило одно: **раньше берётся задание той ревизии, которая раньше наблюдалась**.

Разница видна там, где работу попросили задним числом. Одобрили маску — и в очередь разом
попали задания для файлов, лежащих в дереве давно. Их строки самые новые, а работа —
самая старая:

```text
  когда наблюдалась ревизия     когда появилась строка в очереди

  1 января  старый .py    ──┐        3 марта  (одобрили маску)   ─┐
  1 марта   документ A    ──┤        1 марта  (обычный проход)   ─┤
  2 марта   документ B    ──┤        2 марта  (обычный проход)   ─┤
  4 марта   новый .py     ──┘        3 марта  (одобрили маску)   ─┘
            ▼                                  ▼
  берут: старый .py, A, B, новый .py     было бы: A, B, старый .py, новый .py
```

Очередь отражает возраст работы, а не случайность того, когда вы дописали правило. Файл,
пролежавший в дереве с января, законно старше документа, увиденного вчера, — и идёт раньше
него. Подробности и измерения — ADR 0030.

### Очередь, которую больше никто не просит

Проверка политики стоит **в момент захвата**: правила меняются между проходами, и захват
обязан спрашивать. Но `--limit` ограничивает **захваченное**, а платит только
**выполненное**. Задание, которое больше никому не нужно, не стоит ничего — и при этом
занимает место в лимите, который заведён ради денег:

```text
   очередь, набранная до того, как исключения узнали машину

   run --limit 20 ──► взял 20 ──┬─► 3 разобрано   ◄── за это платят
                                └─► 17 снято      ◄── бесплатно, но лимит потрачен
                                                      и до документов так не дойти

   jobs withdraw  ──► прошёл всю очередь страницами, один раз ──► снял всё лишнее
   run --limit 20 ──► взял 20 ──┬─► 20 разобрано
                                └─► 0 снято
```

`crosskit index jobs withdraw` задаёт тот же вопрос один раз и по всей очереди. Он не
зовёт модель и не читает ни одного файла — только смотрит, допускает ли политика ещё
хоть один путь, по которому лежит файл ревизии, и покрывает ли его правило анализа. Поэтому
он работает без движка и без ключа.

Снятое задание не потеряно. Состояние то же самое `skipped`, единственное обратимое: за ним
не стоит ни попытки, ни вызова, ни результата, — и проход, снова увидевший этот путь, кладёт
задание обратно в очередь.

Watcher уборку **не делает сам**. Полный обход очереди после каждого прохода — это десятки
сканов таблицы заданий, каждый проход, все часы, что watcher живёт, ради беды, которая
чинится один раз. Он называет число снятых в своей строке и один раз за сессию говорит, чем
это чинится. Подробности — ADR 0031.

### Кто нажимает кнопку

Задания кто-то должен взять. Долгое время это был человек: `crosskit index jobs run`.
Watcher держал дерево сверенным, очередь росла, и утром человек запускал разбор руками.

Теперь watcher умеет это сам — но только если ему сказали:

```toml
[watch]
analyze = true
analyze_limit = 20
```

Почему не по умолчанию: в контексте, разрешившем выход содержимого, разбор очереди — это
вызовы модели, то есть деньги. Watcher, оставленный на ночь, не должен тратить их, не
спросив. Ключа два, потому что вопроса два: можно ли тратить вообще и сколько очереди берёт
один проход. «Можно» без «сколько» — ошибка загрузки, а не удобное умолчание: умолчание
здесь было бы решением программы о том, во сколько обходится один чужой проход.

```text
   ┌──────────── один проход watcher'а ────────────┐
   │                                               │
   │  сверка дерева ──► контрольная точка ──► отчёт о проходе
   │        │                                      │
   │        └── завершилась? ── нет ──────────────► ничего не разбираем
   │                  │                            (ревизий нет — заданий нет)
   │                 да                            │
   │                  ▼                            │
   │        разбор очереди, не больше N заданий ──► отчёт о разборе
   └───────────────────────────────────────────────┘

   финальный проход при Ctrl-C ──► очередь не трогается вовсе
```

Три вещи, которые здесь легко сделать неправильно:

- **Остановка.** Человек, нажавший Ctrl-C, не просит сначала потратить деньги, поэтому
  финальный проход очередь не разбирает. Сигнал, пришедший **посреди** разбора, берётся,
  когда разбор закончится, — и именно поэтому разбор ограничен числом заданий: это предел не
  только трат, но и того, сколько watcher продолжает работать после просьбы остановиться. К
  моменту выхода ни одно задание не остаётся «взятым»: каждое либо сделано, либо вернулось.
  А если процесс не остановили, а убили, — взятое вернёт аренда, как и всегда.
- **Разрешение.** Правила из следующего раздела действуют целиком. Запрещающий контекст
  работает детерминированным обработчиком; ключа нет — причина сказана один раз при старте,
  и очередь не тронута вовсе. Решается это один раз на сессию: watcher, перечитывающий своё
  разрешение каждый проход, мог бы сменить то, что отправляет, посреди ночи.
- **Отказ.** Если очередь не удалось разобрать, наблюдение от этого не ломается: проход
  остаётся завершённым, watcher говорит, что анализ не удался, и продолжает. Анализ — работа
  рядом с наблюдением, а не вместо него.

В отчёте прохода появляются пять чисел: взято, выполнено, не удалось, снято, осталось в
очереди. «Снято» — это доля лимита, которая ничего не купила; когда она не ноль, watcher один
раз за сессию называет `crosskit index jobs withdraw` (предыдущий раздел). Путей и текста в
отчёте по-прежнему нет.

**Здесь нашлась чужая беда.** Померили под жёстким лимитом в 1 ГиБ: watcher, которому
разрешили взять сразу 20 000 заданий, убивало ядро примерно на семитысячном. Но то же делала и
старая команда `index jobs run --limit 20000` в своём процессе — значит дело было не в
watcher'е. Разбор этого стал следующим этапом; что оказалось причиной и что с ней сделали —
в конце раздела «AI-анализ».

## 9. AI-анализ и «пропуск»

Здесь самое интересное решение проекта: граница сделана **не проверкой, а отсутствием
значения**.

```text
у контекста есть свойство: можно ли выпускать содержимое наружу
                           умолчание — НЕЛЬЗЯ

разрешено ─► выдаётся «пропуск» — значение, которое невозможно
             изготовить нигде, кроме одного места в доменном слое

пропуск требуется по значению тремя вещами:
   • функцией, которая достаёт текст кусков из графа
   • обработчиком, который говорит с моделью
   • исходящим запросом
```

В запрещающем контексте пропуска не существует — значит эти три объекта **нельзя
создать**. Не «вызов вернул отказ», а собрать вызов не из чего. Проверяется поведением:
тест подставляет заведомо неверный ключ и запускает анализ в запрещающем контексте; если
бы запрос собрался, он ушёл бы в сеть и был бы отвергнут.

```text
контекст запретил              → считаем по кускам локально, ключ не нужен
контекст разрешил + ключ есть  → модель называет тему документа
контекст разрешил, ключа нет   → причина сказана один раз, очередь не тронута
```

Задача модели скромная: одна короткая метка темы на версию, строго по схеме, не длиннее
120 символов. Потолок — не опрятность, а контроль приватности: метка без потолка была бы
способом протащить содержимое файла в граф под другим именем.

Цена посчитана на очереди из 10 000 версий (оценка по байтам, не по измеренным токенам):

| модель | порядок стоимости |
| --- | --- |
| Opus 5 | ~$266 |
| Sonnet 5 | ~$106 |
| Haiku 4.5 | ~$31 |

Умолчанием выбрана дешёвая модель: первый запуск на настоящем дереве не должен стоить
четверть тысячи долларов ради строчки текста. Качество на этой задаче ещё не сравнивалось
живыми вызовами — это записанный долг, и сравнение стоит меньше доллара.

### Почему работник не растёт

Была беда, которую десять этапов никто не мерил: процесс, обрабатывающий задания, ел память
тем больше, чем больше заданий сделал. Под жёстким лимитом в гигабайт он умирал примерно на
семитысячном. Для продукта, который обещает работать без присмотра, это значит, что первый
настоящий прогон на большом дереве придётся перезапускать десяток раз.

Мерили в три шага.

```text
1. наша сторона или не наша?
   наши аллокации: 0.13 МиБ на 1 000 заданий и 0.13 МиБ на 20 000 — не наша
   RSS:            293 МиБ        и 1 450 МиБ                    — растёт

2. за данные или за работу?
   те же 10 000 заданий по 1 000 на процесс: 287…332 МиБ, без тренда
   десятый процесс работает над графом в десять раз больше первого
   и стоит столько же                        — значит за работу

3. что именно в работе?
   20 000 транзакций, каждая пишет один узел:          86 МиБ
   20 000 транзакций, каждая пишет узел и связь:      639 МиБ
   то же самое, с контрольной точкой каждые 1 000:    177 МиБ
```

Оказалось: дорого обходится запись **связи**, и движок держит её цену до **контрольной
точки** — момента, когда журнал складывается в саму базу. Починка — одна строчка смысла:
работник просит сложить журнал каждую тысячу сделанных заданий. После неё 20 000 заданий в
одном процессе проходят под тем же гигабайтом, занимая 336 МиБ вместо того, чтобы быть
убитыми.

Попутно нашлась и вторая, отдельная вещь. Движок выбирает размер своего кэша страниц, глядя
на память **машины**, — а в контейнере машина и разрешённая процессу память это разные числа:
при лимите в гигабайт он видел двадцать и целился в кэш на шестнадцать. Причиной смерти это
не было (проверено: с одним этим прогон всё равно умирал), но теперь Crosskit спрашивает
лимит у ядра и называет потолок, который в него влезает. Пользу это принесло в другом месте:
корпус в десять тысяч файлов теперь индексируется под 640 МиБ, где раньше нужно было 704.

## 10. Поиск

Поиск есть, он работает внутри контекста, и устроен он так: **индекс — не хранилище, а
указатель**. В графе лежит правда; индекс только знает, в каком куске текста встречается
какое слово.

```text
запрос «обход индекса»
        │
        ▼
┌───────────────┐   какие куски совпали, и в каких файлах — куски
│    индекс     │   одного файла складываются в одну строку прямо
│  своя папка   │   здесь (только термины и идентификаторы —
│  на контекст  │    ни путей, ни текста, ни статусов)
└───────┬───────┘
        │ по одному идентификатору куска на файл: лучший из совпавших
        ▼
┌───────────────┐   где лежит файл сейчас, есть ли он ещё,
│     граф      │   и какой у куска текст
└───────┬───────┘
        │
        ▼
   строка выдачи: [present] путь · фрагмент · на чём совпало · сколько мест ещё
```

**Одна строка — один файл.** Складывает индекс, а не то, что после него: страница из пяти
кусков, свёрнутая снаружи, осталась бы страницей из трёх файлов. Файл стоит своего лучшего
совпадения, а каждое следующее стоит всё меньше, поэтому ни один документ не занимает
страницу тем, что он длинный (ADR 0038).

**У беседы есть собственное имя, и оно весит отдельно.** Имя — это одна строка на файл против
десятков тысяч кусков тела, и обычное ранжирование её не замечает: то же слово стоит 0.24 в
имени и 11.04 в теле, потому что длина поля делится на среднюю по **всем** документам, а имени
у большинства нет вовсе. Множитель 40 на этом поле — поправка к этой арифметике, а не
утверждение «имя важнее тела»: отношение шкал померено как 46–48, и всё от 30 до 50 даёт
одинаковый результат.

Чем приводить имя к основе — выяснилось измерением, и не тем, что ожидали:

```text
морфология (стеммер)   разборали → разбора, а имя даёт разбор — НЕ сошлось
первые пять букв       разбо = разбо                          — сошлось

морфология             форму → форм = формы                   — сошлось
первые пять букв       форму ≠ формы                          — НЕ сошлось
```

Опечатки убивают стеммер, склонение убивает префикс. На настоящем наборе вопросов префикс
оказался лучше — и поле осталось одно, префиксное, потому что морфологическое сверх него не
давало ничего.

Что это дало на пятнадцати вопросах к настоящему корпусу бесед: **правильная беседа стоит
первой в двенадцати случаях из пятнадцати и попадает в первую пятёрку во всех пятнадцати**,
и пятёрка — это пять разных файлов. Было: первой в девяти, в пятёрке в одиннадцати, разных
файлов 2.4.

Почему путь и текст не хранятся в индексе, хотя так было бы быстрее: потому что тогда их
пришлось бы обновлять. Файл переехал, политика перестала допускать каталог, текст
изменился — и индекс сообщал бы вчерашнюю правду с уверенным видом. Так он не может: того,
что он не хранит, он не может показать.

### Чего именно нет в индексе

**Прежних версий.** В индексе документы только текущей версии файла; появилась новая —
документы прежней исчезают. Поэтому размер индекса растёт от числа файлов, а не от числа
правок. На корпусе из 10 407 файлов граф хранил 11 500 кусков текста, а индекс — 11 000:
разница ровно та, что в графе осталась история.

**Но исчезнувшие файлы в нём остаются.** Если файла больше нет на диске, его содержимое
никуда из графа не делось, и находить его иногда нужно. По умолчанию такие файлы в выдаче
не показываются — внизу написано, сколько их скрыто, — а с флагом `--include-missing`
показываются с пометкой `[missing]`. «Файла нет на диске» и «такого никогда не было» — не
одно и то же.

### Языки пакетами

**Стеммер** приводит слово к основе, чтобы «файлов» находилось по запросу «файл». Обычный
индекс несёт один стеммер на всех, а корпус здесь многоязычный — и именно на этом сорвались
оба прежних варианта (раздел 14, этап 7): один индекс давал полноту 0.96 по одному языку и
0.21–0.28 по второму.

Здесь язык — **файл данных**, а не ветка в коде. Пакет говорит, как язык называется, какой
версии его правила, какими буквами он пишет, какие из этих букв есть только у него, и как
он снимает окончания. Русский и английский описаны такими же файлами, как казахский; чтобы
добавить язык, добавляют файл.

```text
        кітаптар                    индексы                   сервerный
           │                           │                          │
   есть буква қ/ә/ң —          букв-улик нет: написать      две письменности:
   только казахский            мог и русский, и казахский   никто
           ▼                           ▼                          ▼
        кітап                   индекс  +  индек            сервerный
                                (оба прочтения, одна позиция)
```

| что написано | какие правила | что попадает в индекс |
| --- | --- | --- |
| `reconcile`, `café` — только латиница | английские | `reconcil`, `café` |
| `кітаптар`, `мүмкіндік` — есть буква только казахского | казахские | `кітап`, `мүмкіндік` |
| `индексы`, `елдер` — буквы, которые пишут оба | и русские, и казахские | оба прочтения на одной позиции |
| `сервerный`, `2026` — смесь или не буквы | никаких | слово как есть |

Третья строка — цена честности: программа не знает, на каком языке написано слово из общих
букв, и вместо того чтобы угадать, кладёт в индекс оба прочтения. Документ тогда находится и
русским читателем, и казахским. Стоит это лишних терминов — на текстах этого репозитория
индекс вырос с 0.39 до 0.47 от размера текста, — а полнота и точность по русскому и
английскому остались прежними.

Вопрос при этом расширять нельзя, и это выяснилось измерением: несколько терминов в одной
позиции разбор вопроса читает как фразу, а фраза из двух прочтений одного слова не находит
ничего — полнота по русскому падала с 0.95 до 0.39. Поэтому вопрос задаётся по разу на
прочтение, а ответы объединяются.

Какие языки есть в корпусе, говорит конфигурация, а не догадка:

```toml
[search]
languages = ["ru", "en", "kk"]
```

Язык, которого в сборке нет, — ошибка загрузки, а не молчаливый пропуск. Иначе корпус
индексировался бы правилами, которых никто не просил, и никто бы об этом не узнал. Казахский
сборка несёт, но по умолчанию не объявляет: объявить его — значит сменить правила, которыми
написан индекс, и перестроить его.

### Две беды, которые не видно по выдаче

Плохой поиск выглядит как хороший: результаты есть, и они правдоподобны. Поэтому обе беды
названы отдельной строкой в `doctor`, а лечение у них одно — перестроить индекс.

```text
Search index: 10450 documents against 10450 chunks of current versions (in step with the graph)
Search index written by: fields=chunk_id,file_id,source_language,text,conversation_name_prefix;suffixes=1;tokenizer=simple-lowercase/1+prefix-5/1;normalizations=ru/1,en/1
```

**Индекс отстал** — документов меньше, чем кусков текста: часть текста в него не попала.
Это лечит и обычная сверка: каждый проход читает каждый разрешённый файл и пишет его
документы заново, поэтому проход, не дописавший индекс, — обычное отставание, а не поломка.
**Индекс написан другими правилами** — текст в нём есть, но записан в форме, до которой
нынешний запрос не дотягивается: слова, приведённые к основе другим анализатором, или поле,
по которому фильтрует запрос, которого у половины документов нет. Второе без самоописания
было бы невидимо вовсе — счётчики при нём сходятся, — и лечит его именно перестроение:
проход переписывает документы только тех файлов, которые прочитал.

Поэтому во второй строке перечислено всё, чем индекс написан: его поля, версия таблицы
суффиксов, по которой заполнено поле языка файла, и правила текста. Индекс, у которого
другой набор полей, этой сборкой не открывается вовсе, и отказ говорит ровно это, а не
«каталог недоступен». И ещё одно: проход, дописывающий индекс, написанный другой сборкой,
не переклеивает на него свой ярлык — иначе одного добавленного файла хватило бы, чтобы
индекс начал называть себя свежим (ADR 0035).

Перестроение читает граф и ничего в него не пишет, поэтому безопасно всегда; новый индекс
становится видимым одним шагом в конце, поэтому прерванное перестроение оставляет прежний,
а не пустой.

### Что это стоит

Всё измерено на корпусе 10 407 файлов (14.4 МБ индексируемого текста) и на текстах самого
репозитория, там где нужен настоящий словарь.

| величина | значение |
| --- | --- |
| холодная индексация без поиска | 28.84 с |
| она же с поиском | 28.45 с (в пределах разброса между прогонами) |
| индекс на диске | 3.1 МиБ, 0.22× текста |
| запрос к индексу (настоящий текст) | медиана 0.22 мс, p90 0.26 мс |
| целая страница ответа | медиана 5.0 мс, из них 4.2 мс — чтение графа |
| целая команда `crosskit search` | медиана 91 мс: почти всё — старт процесса и открытие базы |
| перестроение всего индекса | 1.0 с |
| полнота / точность | русский 0.95 / 0.93, английский 1.00 / 0.99 — одновременно |

Одно число из этой таблицы стоило отдельного измерения. Сначала индексация с поиском
занимала 35.5 с вместо 28.8 — на четверть дороже. Разложили: сама работа с текстом стоила
0.5 с, а 5.6 с уходило на то, что индекс делали видимым после каждой пачки файлов. Теперь
пачки копятся, а видимым всё становится один раз в конце прохода — и цена поиска ушла в
шум. Заодно выяснилось, что индекс, оставленный «кусками», отвечает на запрос за 785 мкс
вместо 221: собранный в конце индекс быстрее в три с половиной раза.


### Период: «на прошлой неделе»

`ask` и `search` понимают время в самой фразе — «на прошлой неделе», «вчера», «в сентябре» —
и флагами `--since`/`--until`. Дни из фразы вычисляет программа, а не модель, и печатает их
до ответа:

```text
Period: 21–27 Sep 2026 (last week, Mon–Sun, local time)
Looked for: договоры           ← слова периода не ищутся
```

**В период файл попадает только через событие со своим временем**: реплику или касание
беседой (ADR 0041). Время, когда проход прочитал ревизию, событием не считается — иначе
«прошлая неделя» означала бы «то, что индексировали на прошлой неделе». Под каждой строкой
печатается событие, которое её туда поставило.

Устроено это внутри, без перестройки индекса: граф отдаёт события периода, а индекс
сворачивает только их (кандидат Б, ADR 0043). Другой кандидат — отбирать после выдачи —
измерен и отклонён: на пустом периоде он обходил всю выдачу, а файлы, чей лучший кусок из
другой недели, терял.

**Чего период не видит, он говорит строкой `Not shown: …`.** Беседа, которая выросла за
предел содержимого, в графе остаётся старой ревизией, и её новые реплики периоду неизвестны;
куски, которые не удалось поставить ни к одной реплике, — тоже. Обе вещи считаются и
печатаются, и модель в `ask` получает ту же строку: «не нашлось» и «не могли найти» — разные
ответы.

### Чего поиск пока не умеет: рамка вопроса

Из запроса убираются слова периода — и только они. Всё остальное ищется как слова, в том числе
**рамка вопроса**: «в каком чате мы…», «где мы…», «через». Поиск складывает очки по всем
словам, а совпадения с любым одним уже хватает, чтобы попасть в выдачу:

```text
«в каком чате мы разобрали договоров через модель»
   к основе:  в · как · чат · мы · разобра · договор · через · модел
                ─────── рамка ───────          смысл           рамка

   3-е место: беседа, где совпало только «чата, как»
   правильная беседа: первая по запросу «договоры модель чтение», в выдаче выше — нет
```

Каждое слово рамки весит мало, но в беседах они встречаются везде, и короткий кусок, где
«чат» и «как» стоят плотно, обгоняет длинный, где «договор» и «модель» сказаны по разу.
`ask` берёт восемь лучших строк того же поиска, поэтому ошибается вместе с ним.

Беда измерена давно — этапы 29 и 31 назвали рамку причиной, по которой ломалось расширение
вопроса, — но из продукта её не убрали. Лечение — то же, что у периода: закрытый список рамок
данными, рамка не уходит в запрос, а становится фильтром («в каком чате» — только беседы), и
строка `Looked for:` показывает, что искалось на самом деле. Это следующий этап (41).

## 11. Вопрос: петля замыкается

Поиск отвечает списком мест. Вопрос — это когда отвечают словами, и по своим же файлам:

```text
   вопрос ──► индекс: что похоже ──► граф: что там написано и можно ли это показывать
                                            │
                                            ▼
                                    выдержки, пронумерованные 1..N, в пределах бюджета
                                            │
                                            ▼
                                        модель: ответ + номера использованных
                                            │
                                            ▼
                    ответ, а под ним пути — взятые из нашего же списка по номерам
```

Три вещи в этой схеме важнее остальных.

**Спросить можно не везде.** Вопрос модели — это содержимое, уходящее с машины. Контекст,
который этого не разрешал, получает отказ и строчку, которая его изменит. Половинчатого
ответа тут нет намеренно: всё, что можно сделать без модели, — это обычный поиск, и выдавать
его за ответ было бы обманом.

**Модель не знает, как называются файлы.** Ей дают номера и текст — ни путей, ни имён. Она
ссылается на номера, а путь под ответом печатает программа, найдя этот номер в своём списке
отправленного. Модель, сославшаяся на то, чего ей не давали, назовёт номер вне диапазона, и
такой ответ отвергается целиком.

**Сколько уходит — решает владелец.** Два числа: сколько выдержек и сколько в них байт. Что
ушло и каков был предел, команда печатает вместе с ответом.

Повторный тот же вопрос по тем же источникам ничего не стоит: ответ лежит рядом с базой.

Почему это сделано раньше поиска по смыслу: неизвестно было, какого качества извлечения
хватает для настоящих вопросов. Поиск по словам уже есть и стоит ноль — сначала замкнуть
петлю и посмотреть, где она рвётся. Процедура измерения — `docs/ask-quality-run.md`.

**Посмотрели, и это окупилось.** Петля порвалась не там, где ждали: не в том, что поиск не
понимает смысла, а в том, что он искал не по тому. Девяносто семь процентов индексируемых
байт беседы были машинным выводом, имя беседы поиск не использовал вовсе, а строкой выдачи
был фрагмент, поэтому одна длинная беседа занимала всю страницу. Чинили три этапа и ни разу
не позвали модель. Что из этого вышло — в разделе 15.

## 12. Панель и граф

### Панель спрашивает службу, а без неё — процесс

Панель (`apps/panel/`) — нативное окно macOS, которое ищет по ⌥Space из любого приложения. Базы
она не открывает и конфигурацию не читает: всё, что она знает о данных, приходит одним объектом
от процесса `crosskit … --json` (ADR 0044).

```text
буква в строке ──► crosskit --context work search «…» --json ──► один объект схемы 1
                         (новый процесс на страницу)                  │
                                                                      ▼
                                                     строки, счётчики, «не показано»
```

Схема у машинного ответа одна, с номером: панель сверяет номер первым и ответ другого номера
не читает вовсе. Отказ — тоже объект, с категорией из закрытого списка (`busy`,
`not-indexed`, `not-found`…), а предложение для человека уходит в stderr, как всегда. Без флага
`--json` текст команды прежний байт в байт.

Сначала панель спрашивает сокет фоновой службы (ADR 0050): та держит базы и отвечает тем же
объектом, без процесса, без открытия графа и без `busy`. Процесс — когда службы нет или она
контекст сейчас не держит. Мост через процесс был решён числом (p95 151 мс от строки до кадра
на 120 тысячах документов, ADR 0044), и две названные им причины демона — цена процесса и
`busy` рядом с проходом — служба и сняла: на копии `work` 0 `busy` из 4 723 запросов.

### Граф: окрестность беседы и файла

⇥ на строке выдачи показывает, как она связана с остальным:

```text
 Беседа и файлы, которые она меняла или вы называли. Правее — другие беседы тех же файлов.

  ◆ payments-api ┄┄┄ ┌──────────────────────┐  правила ×12 · вы назвали   ■ contract.rs ── ┌─────────────────┐
                     │ Договоры (фокус)     │──────────────────────────────                │ Сверка договоров │
                     └──────────────────────┘── создала ─────────────────── ⬚ черновик.md └─────────────────┘
                                             ┈┈ читала ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈ ⬚ registry.rs   вне контекста
```

**Шаг — это переход «беседа ↔ файл».** Два шага от беседы доходят до других бесед тех же
файлов — то, ради чего граф и смотрят. Глубина — не больше двух, узлов — не больше ста. Если
второй шаг ничего не нашёл, над графом так и написано: «У этих файлов других бесед нет».

**Линия говорит, что беседа сделала с файлом**: правила, создала, читала, сколько раз, и назвали
ли вы его сами. «Только читала» — точками, «вы назвали» — цветом акцента. Реплик на холсте нет:
номер реплики — в карточке файла, и там же сказано, что он **определён по времени**. Связи
«реплика → касание» в графе нет — касание помнит беседу и момент, — поэтому реплика находится
как последняя, сказанная не позже первого касания. Ядро помечает такое ребро `by_time`, и
экран не подаёт это чтение фактом.

**Файл — один узел.** Касание хранит путь строкой (ADR 0037). Есть в этом контексте место с таким
путём — это файл, на него можно встать фокусом; нет — тот же узел в состоянии «вне контекста»:
путь виден, перехода нет. Другой контекст — другая база, и граф её не открывает (ADR 0008).
Путь, записанный инструментом относительно (`docs/…`), читается от корня проекта беседы: на
дереве владельца он рисовался вторым узлом того же файла.

**Проект — один узел.** Это корень контекста из конфигурации: узла «проект» в графе нет. Папка,
где Claude Code хранит беседы проекта (`~/.claude/projects/<код пути>`), — часть того проекта,
чьим путём она названа; имя проекта — последний сегмент его корня, а не код папки.

**Что граф не показал, он считает.** По каждому виду — сколько найдено и сколько показано
(«обрезано · показано 56 из 149»). «Просто попалось» — прочитано один раз, никто не назвал —
свёрнуто в число, как в `touches`. Тема рисуется, только если разметка её нашла. Ближний шаг
берёт не больше двух третей узлов, чтобы дальнему осталось место.

**Рисует библиотека, а не свой код** — Cytoscape.js с раскладкой dagre слева направо, внутри
веб-вида панели (ADR 0046). Веб-вид запечатан: страница — только из приложения, сети у неё нет,
данные приходят значением, а не кодом, клавиатуру он не берёт. Цена названа: ≈ 35 мс на вид и
≈ 235 МБ памяти, пока панель запущена. Клик по беседе или файлу — новый фокус; ⏎ открывает файл
или копирует `claude --resume`; esc возвращает к выдаче с тем же выбором. Без панели то же самое
печатает `crosskit graph --focus <id>` деревом (ADR 0045).

## 13. Слой знаний: факт с цитатой

До этого этапа граф знал файлы, ревизии, куски, беседы и касания — **доказательства**. Понятий
работы в нём не было: «Контрагент», «БИН», «Пакет документов» жили только в тексте. Теперь у
контекста есть второй граф поверх первого:

```text
     Пакет документов ──belongs-to──► Контрагент ──identified-by──► БИН
            │                              ▲
            │ stated in                    │ «Контрагент уникален по БИН»
            ▼                              │  registry.md, часть 1
     кусок packages.md               кусок registry.md
```

**Откуда берётся.** Тот же вызов модели, что даёт файлу тему, теперь отвечает ещё и списком
сущностей (имя, тип, описание) и связей (субъект, предикат, объект, описание, вес) — по образцу
GraphRAG, который показал владелец. Ревизия уходит модели пронумерованными частями, и у каждой
связи модель называет часть и **дословную цитату**. Это та же очередь, те же правила «что
разбирается», те же бюджеты и тот же пропуск содержимого (раздел 9): контекст, который не
разрешил отправлять содержимое, знаний не получает вовсе. Отдельного механизма нет.

**Каждая связь доказуема.** Связь сохраняется, только если программа находит цитату в тексте
названной части и цитата называет оба её конца — иначе «БИН» доказывал бы что угодно про БИН. На
первом настоящем прогоне это второе правило отвергло большую часть фактов: модель выводила
«раздел — часть — документа» из строения файла, а цитировала одну строку. Нужную папку разбирают
прямо — `index jobs run --under <каталог>`, — иначе первыми идут старейшие ревизии. С тех пор
правило сказано и самой модели. Беседы папки одобряются точно, по одной, с ценой до записи, а
задание длиннее сорока кусков без явного «да» не уходит. Прощаются только пробелы и переводы строк; пересказ, выпавшая разметка,
другие кавычки — уже слова модели, и такая связь отвергается и считается. Связь без цитаты,
связь с концом, которого нет среди сущностей ответа, связь с типом не из словаря не попадают в
граф вовсе. Длины ограничены — имя, описание, цитата, число элементов, — чтобы описание не стало
каналом для целого файла; лишнее отвергается целиком, а не обрезается.

**Сущность — это ключ.** «Контрагент», «контрагенты», «Контрагентов» — одна сущность: ключ — это
имя, сведённое к основам слов тем же анализатором, что пишет индекс поиска. Связь указывает на
сущность ребром, а не строкой. Чего ключ не склеивает: перевод (`counterparty` и «Контрагент»),
сокращение, синоним, часть и целое имени («Карточка» и «Карточка контрагента»). Такие пары — две
сущности, и карта показывает обе.

**Новая ревизия заменяет факты файла целиком.** Знание файла — это знание его текущей ревизии.
Запись фактов идёт в одной транзакции с результатом задания и сначала удаляет всё, что файл
говорил раньше; факты заменённой ревизии не показываются сразу и снимаются ближайшим прогоном
очереди. Контексты не смешиваются: база у каждого своя (раздел 6).

**Что видно.** `crosskit knowledge` — числа: сущности, факты, доля отвергнутых по цитате, цена и
прогноз всей очереди. `knowledge show <имя>` — сущность, все её связи, цитата и источник каждой:
путь файла или беседа с номером реплики. В панели ⌘M — **карта знаний**: весь граф силовой
раскладкой, цвет — тип, размер — число связей, набранное имя подсвечивает сущность и её соседей,
клик по связи показывает цитату и источник, ⏎ открывает файл. Типы сущностей и предикаты —
закрытые списки в конфигурации `[knowledge]`; встроенные выведены из образца владельца и
пробного прогона на выдуманном корпусе (ADR 0048).

**Чего слой не умеет — честно.**

- Прогона на корпусе владельца не было: его разбор — первое, что предстоит. До него неизвестно,
  сколько фактов даст рабочий документ и сколько цитат модель перепишет своими словами. На
  выдуманном корпусе из восьми документов отвергнуто 2 из 178 предложенных связей.
- Карта держит **не больше 400 сущностей** — самые связанные. Силовая раскладка растёт с
  квадратом карты: 400 сущностей — около секунды, 800 — четыре, 1 200 — девять. Всё остальное
  видно в терминале.
- Противоречий не ищет: предикат `contradicts` — это то, что модель прочла в одном документе,
  а не сравнение двух.
- Беседы по умолчанию не разбираются — правило анализа берёт документы `.md` и `.txt`; беседе
  нужна одобренная маска, а длинная беседа не проходит бюджет одного задания.
- Цена: каждый вызов несёт около 25 тысяч токенов собственных инструкций инструмента, сколько бы
  ни было в документе. По ставкам, снятым на выдуманном корпусе, очередь `work` (1 729 заданий,
  25,6 МБ) стоила бы ≈ $430 по прейскуранту и шла бы около 18 часов — у подписки это квота, а не
  счёт, и ставки уточнит первый настоящий прогон.

## 14. Как в этом проекте принимаются решения

Метод сложился по ходу и стоит дороже любой отдельной функции:

```text
1. измерить, а не предположить
2. диагностика отдельным этапом, без правок кода
3. узкая починка ровно того, что измерение назвало
4. повторить измерение на исправленном коде
5. отрицательный результат — тоже результат, он закрывает ветку
```

История блока про производительность, целиком построенная так:

| этап | что проверяли | результат |
| --- | --- | --- |
| 2G | базовый замер | 472 с на 10 407 файлах |
| 2H | группировка транзакций | 1.15× — мало, причина не в этом |
| 2I | запись наборами | 8.3× быстрее, но память выросла втрое |
| 2J | откуда память | три запроса связей планируются сканами |
| 2K | починка этих запросов | 1135 → 371 МБ, рост от истории убран |
| 2L | размер пачки виноват? | нет: восьмикратное изменение ничего не даёт |
| 2M | запросы текущего состояния? | нет, но нашёлся выигрыш по времени |
| 2N | применили выигрыш | 10.9 → 1.9 с на операции |
| 2O–2P | настройки движка? | фиксировать нельзя: ломает крупные файлы |
| 2Q–2R | цена одного большого файла | 2 618 → 481 МБ страничной записью |
| 2S | цена чтения | потоковый разбор, −39 МБ, время ×16 |
| 2T–2U | сам критерий | заменён: пик памяти мерил ноутбук, а не код |

Последний вывод стоит выделить: одинаковый код давал 502 МБ в один день и 690 МБ в
другой, потому что система под нехваткой памяти сжимает страницы и они перестают
считаться. Поэтому критерий приёмки теперь не «пик не выше N мегабайт», а «сценарий
целиком проходит в контейнере с жёстким лимитом памяти» плюс число аллокаций нашей
стороны, которое повторяется побайтово.

Итоги блока: полный цикл на 10 407 файлах проходит на машине с 1 ГБ памяти; холодная
индексация ускорилась примерно в двенадцать раз; сверка по базе с длинной историей — в
четырнадцать.

### До какого дерева это вообще работает

Все числа памяти продукта были сняты на одном корпусе в десять тысяч файлов. Вопрос «а что
будет на ста тысячах» никто не задавал — и когда задали, ответ оказался не про память.

```text
холостая сверка (ничего на диске не менялось):
   10 000 файлов ──►  41 с
   25 000 файлов ──► 328 с
   50 000 файлов ──► 2 087 с   ← тридцать пять минут на то, чтобы убедиться,
                                  что ничего не изменилось
```

Вдвое больше файлов — вшестеро больше времени. Так растёт не работа, а что-то другое.
Нашли это одним опытом: взяли пять **одинаковых** пачек по десять тысяч файлов и сложили их
в один граф, одну за другой. Каждая пачка — ровно та же работа.

```text
пачка 1 ──►  28 с
пачка 2 ──►  60 с
пачка 3 ──► 112 с
пачка 4 ──► 180 с
пачка 5 ──► 269 с   ← та же работа, что и первая, в девять с половиной раз дороже
```

Значит платили не за работу, а за то, что уже лежит в графе. Причина оказалась в том, **как
заданы вопросы к базе**. У каждой записи есть ключ — как номер страницы в книге. Шесть
запросов на пути записи спрашивали базу так, что она вместо «открой страницу 412» пролистывала
книгу целиком. Чем толще книга, тем дольше каждый такой вопрос, а вопросов — по одному на файл.

Самое обидное: правило «не заставляй базу листать» в проекте уже было, его вывели десять
этапов назад. Просто применили тогда к одному месту из пяти. А в одном месте формулировка
усыпила: «за это платят только записи, которые уже были в базе» — звучит как редкость, а на
деле холостая сверка перечитывает **все** файлы, поэтому платили за каждый, всегда.

```text
после того, как вопросы переписали на ключи:

холостая сверка 50 000 файлов ──► 140 с вместо 2 087 с   (в 15 раз быстрее)
сто тысяч файлов, с нуля      ──► 7 минут
те же пять пачек, последняя   ──► 44 с вместо 269 с
```

Полностью одинаковыми пачки не стали и не станут: чем больше книга, тем чуть дороже открыть в
ней нужную страницу — это свойство любой базы. Но теперь десятикратный граф стоит втрое, а не
вдесятеро: цена растёт логарифмически, а не в лоб.

Сколько это просит памяти — проверено под жёстким лимитом, где процессу больше просто не
дают:

```text
   25 000 файлов ──► хватает гигабайта
   50 000 файлов ──► нужно полтора
  100 000 файлов ──► нужно два
```

Каждая строка ограничена с двух сторон: на ступень ниже ядро процесс убивает. Это не
пропорция и не обещание для любого дерева — корпус здесь синтетический, а настоящая папка с
другим набором файлов будет стоить иначе. Смысл строк в другом: сто тысяч файлов — это
обычная машина, а не сервер.

**Насколько иначе — теперь известно, и разница почти втрое:**

```text
синтетика,        25 000 файлов ──► 1 024 МиБ
дерево владельца, 26 125 файлов ──► 2 732 МиБ
```

Одинаковое число файлов, втрое разная цена. Что именно её объясняет, **не установлено**:
синтетика даёт 1.05 куска текста на файл, настоящее дерево — 4.03; в нём есть корень из
почти трёх тысяч документов на 690 МБ; и корней там десять, а не один. Какая из трёх разниц
отвечает за множитель — никто не мерил. Синтетическую таблицу это не отменяет: она честна
про то, что мерила. Она просто не про ваш каталог.

### Работа, которой не должно было быть

У прошлого этапа остался хвост: память самого Crosskit росла с числом файлов в одном проходе
— 32 МБ на десяти тысячах, 117 на ста. Подозрение пало на поисковый индекс, и оно
подтвердилось, но причина оказалась не та, которую ждали.

Разобрали по частям. Индекс делает с каждым файлом две вещи: **удаляет** его старые куски
текста и **добавляет** новые. Померили порознь:

```text
добавление ──► 13 → 27 → 27 → 27 → 27 МБ   выходит на полку и дальше не растёт
удаление   ──► 15 → 27 → 40 → 52 → 65 МБ   растёт ровной линией, без конца
```

Добавление само сбрасывает написанное на диск. А удаления копятся до конца прохода — по
1 240 байт на каждый файл. Проверили, нельзя ли сделать запись дешевле: взяли имя файла в
двенадцать раз короче. Стоимость упала на 2%. Значит платим не за имя, а за саму пометку «это
потом удалить», и её размер — не наш.

И тут стало видно главное. Проход читает **каждый** файл, который обходит. Если файл не
менялся, его версия осталась прежней — но она по-прежнему «текущая», а индекс переписывал всё,
что видел текущим. То есть **каждая проверка неизменившейся папки стирала и писала индекс
заново, целиком**. Память копилась не потому, что мы редко сбрасываем написанное, а потому что
делали работу, которой вообще не должно быть.

Починка — два правила, оба про «не делай лишнего»:

```text
файл не менялся            ──► индекс не трогаем вовсе
файл видим впервые         ──► добавляем, но не удаляем: удалять нечего
```

```text
после починки, память Crosskit за проход:

   холостая проверка 10 000 файлов ──►  1.2 МБ вместо 32
   холостая проверка 50 000 файлов ──►  1.2 МБ вместо 81
   индексация с нуля, любой размер ──►  20 МБ, и больше не растёт
```

Цена: проход стал на 3–4% медленнее, а проверка папки, где поменялось сразу много файлов, — на
11%. Причина честная: чтобы узнать, менялся ли файл, надо лишний раз спросить у базы, что она
считает текущим. Спрашиваем сто раз на десять тысяч файлов.

Заодно чуть не потеряли полезное свойство: если индекс когда-то отстал, его чинила обычная
проверка папки, а не только явная команда «перестроить». Об этом сказал старый тест, а не
человек. Свойство сохранили: проход один раз спрашивает, всё ли на месте, и если нет — пишет
всё, как раньше.

Отдельно стоит сказать, чего этот этап **не** сделал. Была догадка, что поможет то же
лекарство, что вылечило исполнителя заданий на прошлом этапе, — почаще сбрасывать журнал на
диск. Проверили: не помогает и не могло. То лекарство ограничивает, сколько движок копит между
сбросами; здесь же пятая пачка платила за сорок тысяч файлов, уже лежащих в графе, и никакая
частота сбросов этого не трогает. Гипотезу опровергли числом — это тоже результат.

### Пятнадцать этапов над седьмой частью дерева

Самая дорогая находка проекта не в производительности и не в качестве поиска. Она в том, что
пятнадцать этапов подряд программа отвечала **«проиндексировано»**, имея в графе семь
процентов того дерева, ради которого её писали.

```text
крупнейший рабочий контекст владельца:

  379 678 файлов на диске
      │  −93.1 %   исключения: имена 315 991 + маркеры 37 562 = 353 553, без остатка
      ▼            это правильно, и это ровно то, ради чего исключения заводили
   26 125 допущено политикой
      │  −84.7 %   ВОСЕМЬ КОРНЕЙ ИЗ ДЕСЯТИ НЕ ОБХОДИЛИСЬ НИ РАЗУ
      ▼
    3 998 в графе
```

Нашлось не проверкой и не тестом: ревьюер, читая отчёт совсем о другом, заметил, что у
контекста с одним репозиторием покрытие сто процентов, а у контекста с десятью — процент, и
спросил, почему. Всё остальное — отдельный этап, который **ничего не чинил**, а только
считал, корень за корнем, чем продуктовой же политикой.

**Отказов было три, и первый — самый безобидный.**

```text
1. обход списка корней останавливался на первом,
   который не прочитался                             ← ошибка

2. сообщение говорило «контекст не проиндексирован»,
   хотя два корня из десяти в графе лежали            ← ложь

3. `status` говорил «indexed» и не называл корни      ← вот почему
                                                        это прожило
                                                        пятнадцать этапов
```

Первый — это ошибка, которую делают. Второй и третий — это причина, по которой её никто не
видел. Если бы сообщение сказало «два корня из десяти», владелец узнал бы в первый же день.
Если бы `status` печатал корни, это было бы видно каждый день с тех пор.

И причина первого отказа записана в самом коде, комментарием, который писал её автор:

> «первый отказ почти всегда — это база контекста, и следующий каталог встретит её же»

Утверждение о частоте, которым закрыли вопрос о единственном случае. Оно даже не ложно в
общем: база и правда отказывает чаще прочего. Просто в том случае, который произошёл, база
работала — два корня в неё легли, — а отказал третий корень, и «следующий встретит то же
самое» не выполнилось восемь раз подряд.

**Чему это учит, помимо самой починки.** Метод из начала раздела ловит то, что измеряют.
Здесь пятнадцать этапов мерили скорость, память и качество выдачи — и все эти числа были
верны. Никто не мерил **покрытие**, потому что программа отвечала на него сама, и ответ
звучал убедительно. Отчёт, который врёт, дороже ошибки, про которую он врёт.

## 15. Что впереди

```text
сделано  ─► языковые пакеты: язык добавляется файлом данных, казахский первым
сделано  ─► вопрос по своему дереву: `ask` — поиск, выдержки, ответ с источниками
сделано  ─► черновик контекстов по уликам дерева: `contexts propose`
сделано  ─► watcher разбирает очередь сам, ограниченно и только с разрешения
сделано  ─► проход стоит дерева, а не графа: сто тысяч файлов индексируются
сделано  ─► индекс пишется только там, где что-то изменилось
сделано  ─► у файла есть язык программирования, выведенный из имени
сделано  ─► беседа разбирается как беседа: имя, реплики, касания файлов
сделано  ─► строка выдачи — файл, а не фрагмент
сделано  ─► обходят контекст целиком, и `status` называет каждый корень
сделано  ─► `setup` спрашивает о группах; беседы идут за своим проектом
сделано  ─► «на прошлой неделе» вычисляется, а не угадывается; `Not shown` вместо молчания
сделано  ─► панель ищет в настоящих контекстах — через процесс, без демона
сделано  ─► граф в панели: что беседа правила, что вы назвали, кто ещё трогал те же файлы
сделано  ─► продукт называется Crosskit (до 2 октября — Crosscode); данные переехали командой
сделано  ─► тесты наблюдателя снова говорят о коде, а не о каталоге сборки
сделано  ─► слой знаний: сущности и факты с цитатой, найденной в источнике; карта в панели
```

### Про смысловой слой — честно

В плане он стоял как «знания и противоречия»: сущности, связи между ними, противоречащие
утверждения. **Знания построены, противоречий нет** (раздел 13). До этого измерили один дешёвый
приём рядом со слоем, и он не окупился: взять слова из реплик, посчитать, какие встречаются
рядом, и расширять вопрос ближайшими соседями. Модель в нём не участвовала вовсе.

```text
без графа связей  ──► 0.73
с графом связей   ──► 0.73     граф не добавил ничего
```

Причина названа и она конкретная, а не «не сработало»: вопрос «в каком чате…?» наполовину
состоит из служебных слов, и у слова «в» ближайшие соседи — «не», «и», «это». Шесть слов
вопроса превращаются в тридцать шесть, половина из них — мусор, и настоящие связи в нём
тонут. То, что обычное ранжирование умеет наказывать, граф размножает.

И выяснилось попутно: **для этого вида вопроса смысловой слой не понадобился вовсе.** Всё
улучшение дали три другие вещи — выброс машинного вывода из индекса, имя беседы отдельным
полем и строка выдачи как файл. Слой знаний отвечает на другой вопрос — «как связаны понятия
моей работы и откуда это известно», — и поиск он не меняет.

### Чего нет и что это блокирует

```text
   агенту ИИ нечем спросить ──────► сокет службы уже отвечает на поиск, граф и карту
                                     (ADR 0050); нужен клиент для агента
   панель спрашивает службу ──────► процессом — только без неё
```

Панель спрашивает службу по её сокету, а без службы — процессом, как раньше (раздел 12). Агенту
ИИ свой клиент пока не написан, хотя служба уже отвечает тем же протоколом.

Ближе всего, по порядку:

```text
этап 41   рамка вопроса не ищется, а становится фильтром        раздел 10
потом     «всё про X» полным перечнем из графа, а не восемью лучшими строками
          разбор очереди `work` слоем знаний и словарь типов по нему    раздел 13
```

### Две починки, которые ничего не добавляют

Обе найдены измерением, обе сегодня не проявляются, и у каждой сказано, когда вы её
заметите.

**Один нечитаемый корень из десяти останавливает разметку тем для всего контекста.** Разметка
запускается только после обхода, который завершился целиком. Пока обход был одним каталогом,
это было верно: не дочитали — не знаем, что на диске. Теперь обход — это десять каталогов, и
«не завершился» значит «девять из десяти в порядке». Проверку никто не переписал.
*Заметите:* очередь перестанет уменьшаться — через дни или недели, и ничто об этом не скажет.
*Плюс:* такой корень заставляет обходить дерево втрое чаще нужного, это +23 минуты
процессорного ядра в час.

**Записи «файл наблюдался тогда-то» копятся без предела.** Команды, которая их чистит, нет.
Место на диске от этого не растёт — файл базы выходит на полку, это померено, — растёт число
строк. *Заметите:* неизвестно. Когда это начнёт мешать, **не измерено**, и первое дело здесь
— померить, а не чинить.

### Отложено сознательно

По контекстам: общий контекст для справочников и книг, тени между контекстами,
автоматическая классификация новых файлов.

По коду: разбор синтаксиса (tree-sitter), который дал бы границы определений и роль каждого
вхождения. Измерено, чего это стоит: сегодня ответ на вопрос «где определено и где
используется» обходится примерно в 13 700 токенов, потому что приходится читать файлы
целиком; с границами он стоил бы около 250. Решение отложено владельцем.

## Словарь

| термин | значение |
| --- | --- |
| граф, узел, связь | способ хранения: вещи и отношения между ними |
| чанк | кусок текста — единица поиска и анализа; размер задаёт разборщик: у текста ~4 КБ, у беседы это одна реплика |
| профиль извлечения | каким разборщиком читается файл; выбирается по его имени, и его версия входит в происхождение каждого куска |
| беседа, реплика | транскрипт сессии с ИИ, разобранный на то, что в нём сказано; всё остальное в нём — вывод инструментов и обвязка |
| касание файла | запись «эта беседа читала, писала или правила вот этот путь»; берётся из структурного поля транскрипта, а не из догадки |
| отпечаток (hash) | короткая строка, однозначно описывающая содержимое |
| транзакция | «всё или ничего» при записи |
| inode | внутренний номер файла в файловой системе |
| время рождения | момент создания файла, отдельный от времени изменения |
| контекст | изолированный мир данных со своей базой |
| корень контекста | один каталог из списка, которым объявлен контекст; у одного контекста их бывает десять, и обход идёт по всем |
| пропуск (permit) | значение, которое нельзя создать без права; его отсутствие делает запрещённое действие несобираемым |
| выдержка | кусок текста из своего файла, отправляемый модели под номером; путь остаётся на машине |
| сентинел | уникальная строка-маркер в тестах: нашлась не там — граница дырявая |
| эпоха | счётчик проходов сверки; заменяет часы при определении порядка |
| tombstone | пометка «путь исчез» без удаления истории |
| захват / аренда | «задание взято» и срок, после которого оно вернётся в очередь |
| план запроса | как база решила выполнить запрос: точечно по ключу или перебором таблицы |
| скан | перебор всей таблицы; цена растёт вместе с объёмом данных |
| peak RSS | пик оперативной памяти процесса |
| buffer pool | кэш страниц базы в памяти |
| FTS | полнотекстовый поиск |
| инвертированный индекс | словарь «слово → где встречается» |
| стеммер | приведение слова к основе, чтобы находились все формы |
| языковой пакет | файл данных с правилами одного языка: алфавит, буквы-улики, окончания по слоям |
| буква-улика | буква, которой нет у других объявленных языков той же письменности; выдаёт язык слова |
| нормализация | именованное правило приведения к основе: язык, версия правила и буквы, которые оно заявляет |
| отпечаток анализатора | запись в индексе о том, какими правилами он написан; несовпадение значит, что слова в нём хранятся не в той форме, которую ищет запрос |
| keyset-пагинация | «дай, что идёт после этого результата» вместо «пропусти N»: страница не зависит от того, сколько страниц прочитано до неё |
| свёртка по документу | несколько совпавших кусков одного файла — одна строка выдачи; оценка строки складывается из них так, что длина не выигрывает |
| журнал (WAL) | файл рядом с базой, куда движок пишет принятые изменения до того, как сложит их в саму базу |
| контрольная точка | момент, когда журнал переносится в базу; до неё записанное живёт только в журнале |
| полнота / точность | доля найденного из нужного / доля верного среди найденного |
| группа `origin` | первый сегмент пути в адресе remote (`acme` в `…/acme/team/repo.git`); по ней `setup` собирает проекты в группы |
| папка бесед | каталог, где Claude Code хранит беседы одного рабочего каталога (`~/.claude/projects/<код пути>`); корень контекста того проекта, к которому относится |
| период | промежуток дней из фразы («на прошлой неделе») или флагов `--since`/`--until`; в него попадает только то, у чего есть событие с временем |
| рамка вопроса | служебная часть вопроса («в каком чате мы…»), которая говорит, что искать, но сама искомым не является |
| панель | окно macOS по ⌥Space: выдача поиска и граф; данные берёт процессом `crosskit … --json` |
| окрестность (граф панели) | беседы, файлы и проект вокруг выбранной строки, на один-два шага «беседа ↔ файл», не больше ста узлов |
| демон | долгоживущий фоновый процесс, через который приложения говорили бы с ядром; не построен |
| сущность | понятие работы, которое называют файлы и беседы: «Контрагент», «БИН»; одна на ключ |
| ключ сущности | имя, сведённое к основам слов анализатором поиска: «Контрагенты» и «контрагент» — один ключ |
| факт, связь | «субъект — предикат — объект» между двумя сущностями, с частью источника и цитатой |
| цитата | слова источника, которые программа нашла в названной части; не нашла — факта нет |
| словарь типов | закрытые списки типов сущностей и предикатов из `[knowledge]`; модель выбирает только из них |
| карта знаний | весь граф знаний контекста в панели по ⌘M; не больше 400 самых связанных сущностей |
