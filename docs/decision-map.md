# Карта решений: задача вместо чата

Статус: черновик концепции, 2026-10-29. Это ещё не ADR. Он появится после разбора настоящих
бесед, и раздел 10 говорит, что этот разбор должен показать.

## 1. Проблема

Работа с агентом сегодня — это чат. За месяц одной задачи в нём набираются сотни реплик,
тысячи вызовов инструментов и несколько веток решений, перемешанных во времени. Чтобы понять,
**почему** задача пошла именно так, что было отвергнуто и что осталось без ответа, человек
перечитывает переписку. Список чатов и канбан этого не решают: они упорядочивают задачи между
собой, а беспорядок — внутри одной задачи.

Предложение: **показывать задачу как карту решений**. Корень — вход задачи, ветви — варианты
на развилках, основная линия — выбранный путь, красные метки — то, что требовало внимания и
осталось без ответа. Переписка не исчезает: она становится подробностью под узлом, а не главным
экраном.

## 2. Термины

| термин | что значит |
| --- | --- |
| **Вход** | начало задачи: формулировка, с которой она пришла (из чата, канбана или Asana) |
| **HEAD** | место, где задача находится сейчас: последний узел активной ветки. Не путать со входом — ветки будут настоящими git-ветками, и в git HEAD значит именно это |
| **Развилка** | точка, где выбирали подход: «как сделать X?». Узел карты |
| **Ветка** | один вариант на развилке. У ветки есть состояние (раздел 3) |
| **Основная линия** | цепочка выбранных веток от входа до HEAD |
| **Отрезок** | кусок переписки между двумя узлами. Открывается по клику, по умолчанию свёрнут |
| **Риск** | вопрос, предупреждение или непроверенное действие, на которое в своё время не ответили. Метка на основной линии |
| **Карта проекта** | решения задач, поднятые на уровень проекта: то, что должна знать любая следующая задача |

## 3. Как это выглядит

Пример выдуманный (`payments-api`):

```
 ● ВХОД: «Двойная скидка в корзине»
 │
 ◆ Как убрать двойное применение?
 ├── ✗ A  флаг «уже применено» в заказе
 │        отклонено: ломает частичный возврат            [цитата, реплика 41]
 ├── ○ B  считать только в order.rs
 │        отложено: нужен рефакторинг расчёта цены
 └── ✓ C  убрать расчёт из cart.rs                      ← основная линия
     │    почему: корзина только показывает цену         [цитата, реплика 57]
     │    код: ветка task/discount-c · −6 +41 · тесты 3/3 ✓
     │
     ├─🔴 частичный возврат не пересчитывает скидку      [цитата, реплика 63]
     ├─🟠 интеграционные тесты не запускались (нет доступа к БД)
     │
     ◆ Как показывать скидку до заказа?
     ├── ◐ предпросмотр через API заказа                 ← HEAD (Codex, шаг 4)
     └── ? спросить у продакта                           ждёт решения
```

Состояния ветки:

| знак | состояние | что обязательно хранится |
| --- | --- | --- |
| ✓ | выбрана | причина выбора и цитата |
| ✗ | отклонена | **причина отказа** и цитата |
| ○ | отложена | условие, при котором вернуться |
| ◐ | исследуется | движок, беседа, шаг |
| ? | ждёт решения человека | вопрос и варианты |
| ✓ᵃ | решена агентом по умолчанию: человек не ответил, агент выбрал сам | вопрос, выбор агента, как отменить |
| ⊘ | брошена: на вопрос ответили другим или сменили тему | реплика, после которой её бросили |

Последние два состояния добавлены после разбора настоящей беседы (раздел 10). Без них решение
агента выглядит как решение человека, а брошенный вопрос — как вопрос, который ещё ждёт ответа.

Отклонённая ветка с причиной ценнее выбранной: агенты раз за разом предлагают уже отвергнутое.
Если причины отказа попадают в каждый новый ход, это повторение исчезает.

## 4. Правила

1. **Не всякий выбор — развилка.** Развилка — это решение, которое меняет направление кода или
   данных или которое дорого откатить. Иначе карта станет таким же шумом, как чат.
2. **Узел доказан цитатой.** Причина выбора, причина отказа и риск хранятся вместе с дословной
   цитатой из реплики. Цитату находит программа, как у фактов слоя знаний (ADR 0048). Без цитаты
   узла нет.
3. **Красным горит только то, на что никто не ответил.** Осознанно принятый риск становится
   серым и хранит причину, кто его принял и когда. Иначе через неделю на красное перестанут
   смотреть.
4. **Риск тянется вниз по основной линии**, пока его не закроют: решение на следующей развилке
   принималось с этим риском, и это видно.
5. **Переписка не прячется навсегда.** Каждый узел ведёт к своему отрезку, а отрезок — к
   репликам.
6. **Задача шире беседы.** Одну задачу ведут несколько бесед, иногда разные агенты
   параллельно в тех же репозиториях. Карта собирается из всех бесед задачи.
7. **Карта строится из исходного журнала, а не из сводок сжатия контекста.** Сводка уже
   пересказывает беседу, теряет решения и ломает порядок реплик во времени.
8. **Секреты маскируются.** Пароли и токены, вставленные в переписку, в карту не попадают.
9. **Длинная задача делится на главы.** По умолчанию видны основная линия, нерешённые
   развилки и риски 🔴 и 🟠; остальное раскрывается внутри главы.

## 5. Риски: уровни и жизненный цикл

| уровень | что сюда попадает |
| --- | --- |
| 🔴 критичный | деньги, потеря или порча данных, миграции и правки на проде, безопасность |
| 🟠 высокий | непроверенное поведение: проверка не запускалась или упала, команду отклонили, песочница не пустила |
| 🟡 средний | вопрос агента без ответа, допущение («предполагаю, что…») |
| ⚪ инфо | TODO и FIXME в диффе, мелкие замечания |

```
 открыт (цвет уровня) ──► принят (серый: кто, когда, почему)
        │
        ├──────────────► закрыт (ссылка: коммит, тест, решение)
        └──────────────► неактуален (ветка, где он возник, отклонена)
```

Задачу с открытым критичным риском нельзя молча перевести в «Готово». Риск сначала закрывают
или принимают с причиной.

**Повтор поднимает уровень.** Если агент напоминает о том же в третий раз, а ответа нет, метка
поднимается на уровень и показывает число напоминаний и возраст. Это сильнейший признак
забытого риска: в разобранной беседе одно напоминание повторялось шесть раз за месяц.

**Находка вне задачи** — риск, который к задаче не относится, но обнаружен по ходу (например,
сломанная соседняя система). Он не тянется по основной линии, а лежит в отдельной полосе, из
которой заводится новая задача.

## 6. Откуда берутся узлы

| источник | что даёт | точность |
| --- | --- | --- |
| человек: «попробуй иначе», «а если через API?» | развилку с форком от текущего узла | факт |
| агент предлагает варианты (план, вопрос с вариантами) | развилку | факт |
| событие движка: проверка (тест, сборка) упала или не запускалась; команду отклонили, и обхода не было | риск 🟠 | факт |
| дифф: добавлен TODO или FIXME | риск ⚪ | факт |
| вопрос агента, на который следующая реплика человека не отвечает | риск 🟡 | модель + цитата |
| оговорка агента: «не проверял», «предполагаю», «однако» | риск по смыслу | модель + цитата |
| разбор уже прошедшей беседы | развилки и риски задним числом | модель + цитата |

Фактические источники делаются сразу. Источники «модель + цитата» включаются только после замера
на настоящих беседах (раздел 10). Лишняя красная метка стоит дорого: она приучает не смотреть на
красное.

Ненулевой код выхода сам по себе риском не считается. В разобранной беседе из 56 ошибок
инструментов значимыми оказались две-три. Остальные — код выхода 1 при полезном выводе или
отказ, который тут же обошли.

## 7. Задача собирается из бесед

Задача почти никогда не равна одной беседе. Обычный путь выглядит так:

```
 беседа 1 (Claude Code) ── контекст заполнен ──► беседа 2 (Claude Code, по handoff-файлу)
                                                    │
                          лимит подписки кончился ──┘──► беседа 3 (Codex, по тому же handoff)
                                                    │
                     параллельно: QA-беседа в тех же репозиториях, пакетные исполнители
```

Поэтому единица карты — **задача**, а беседа — один из её источников. Переход между беседами
— это ребро «продолжение» на основной линии, с причиной, если её видно: заполнен контекст,
кончился лимит, другая платформа.

**Что считается беседой.** Пользовательская беседа Claude Code или Codex. Служебные сессии
отдельными беседами не показываются: автоматический ревьюер команд, субагенты, пакетные
исполнители по одному протоколу. Пакет из десяти одинаковых сессий — это один узел «пакетная
работа» внутри задачи.

**Задача — не каталог и не беседа целиком.**
- Одна задача идёт в нескольких каталогах и репозиториях.
- В одном каталоге живут разные задачи.
- В одной беседе бывают куски разных задач: побочная находка, переключение на соседнюю тему.

Поэтому к задаче относятся **отрезки** бесед, а не беседы целиком.

**Признаки связи, от сильных к слабым:**

| признак | откуда | сила |
| --- | --- | --- |
| беседа B читает файл, который написала беседа A (handoff, план, отчёт) | вызовы инструментов в журналах обеих | факт |
| явная ссылка: на папку или номер задачи, на другую беседу по названию | текст реплик | факт |
| одна и та же ссылка на трекер (Asana) | текст реплик | факт |
| одна и та же git-ветка | метаданные беседы | сильный |
| одни и те же файлы | касания, которые Crosskit уже пишет (ADR 0041) | сильный |
| беседа B началась вскоре после конца A в том же каталоге | время и каталог | слабый |
| похожая тема | модель | слабый, только подсказка |

**Установка.** Crosskit сканирует все проекты и беседы обеих платформ: Claude Code — с диска,
Codex — через app-server (`thread/list` с фильтром по каталогу). Затем он предлагает задачи на
подтверждение, например: «нашёл 14 задач; в задаче X — 31 беседа в Codex и Claude Code за
2,5 месяца». Человек подтверждает, сливает и делит задачи. Молча задачи не собираются.

**Цена.** Сшивка по признакам из таблицы дешёвая: это чтение журналов без модели, и её можно
делать для всей истории при установке. Карта решений внутри задачи требует модели и стоит
дорого: разметка одной месячной беседы заняла около 460 тысяч токенов. Поэтому модель строит
карту лениво — для задачи, которую человек открыл или подтвердил. Дальше она достраивает карту
по новым отрезкам и не перечитывает старое.

## 8. Ветки настоящие, а не на словах

- **Разговор.** Ветка — это форк беседы от точки развилки: `thread/fork` у Codex app-server и
  форк сессии у Claude Code (флаг headless-режима надо проверить).
- **Код.** Исследуемая ветка живёт в своём git worktree. «Сравнить A и C» — два настоящих диффа,
  «выбрать C» — принять её worktree.
- **Знания.** Карта — подграф графа знаний: задача, развилки, ветки и риски — узлы, цитаты —
  связи с репликами, которые уже есть в слое доказательств. В новый ход агента подмешиваются
  основная линия, причины отказов и открытые риски (`additionalContext` у Codex).

## 9. Снаружи — канбан

Карточка — это вход задачи, колонки — состояние, на карточке мини-карта основной линии и счётчик
рисков. Задача попадает в «Ждёт решения» ровно тогда, когда её HEAD стоит на развилке со знаком
«?».

```
 Входящие      В работе           Ждёт решения          Готово
 ┌─────────┐   ┌──────────────┐   ┌───────────────────┐   ┌──────────┐
 │ Логи    │   │ Terraform    │   │ Двойная скидка    │   │ Push iOS │
 │         │   │ ●─◆─✓─◐      │   │ ●─◆─✓─◆?  ⚠ 1🔴   │   │ ●─◆─✓─✓  │
 └─────────┘   └──────────────┘   └───────────────────┘   └──────────┘
```

Внешние трекеры, начиная с Asana, — адаптеры в `infrastructure`. Первый шаг: импорт задачи как
входа и отправка итога обратно комментарием («выбрано C, потому что…», открытые критичные риски).
Двусторонняя синхронизация статусов — отдельный этап.

## 10. Что должен показать разбор настоящих бесед

До ADR карта проверяется на длинных беседах владельца: сначала их размечает модель по правилам
разделов 4–6, затем владелец правит разметку руками. Разбор показывает:

- сколько развилок и рисков получается в настоящей беседе и читается ли карта такого размера;
- годится ли критерий развилки из правила 1 или он пропускает важное и тащит мелочь;
- какая доля красных меток после правки владельца оказывается лишней — это решает, можно ли
  доверить модели источники «модель + цитата»;
- хватает ли пяти состояний ветки и четырёх уровней риска.

Разбор настоящей беседы содержит её реплики и поэтому живёт вне репозитория. Здесь
остаются только числа и выводы, с псевдонимом беседы.

### Первый разбор: беседа `quarry-ledger`, 29 октября 2026

`quarry-ledger` — псевдоним рабочей беседы владельца: чистка данных реестра и выкатка в прод.
Числа настоящие. Разметку сделала модель по правилам разделов 4–6, пятью частями по времени.
Части сведены вручную, все ключевые цитаты найдены в тексте дословно. Ручная правка владельцем
ещё не сделана, поэтому доля лишних меток пока неизвестна.

| | |
| --- | --- |
| срок и объём | 30 дней, 36 МБ, 369 реплик после очистки, 1 217 вызовов инструментов |
| сжатий контекста | 5 |
| развилок | 40 по частям, ≈35 после сведения; на основной линии ≈15 |
| нерешённых развилок на конец | 5, одну из них спрашивали 4 раза |
| рисков | 89 по частям, ≈68 после сведения |
| открытых 🔴 на конец | 3, из них 1 — находка вне задачи |
| самый частый повтор | одно и то же напоминание 6 раз за месяц |

Что разбор изменил в концепции:

- **Пяти состояний ветки мало.** Добавлены ✓ᵃ (решено агентом по умолчанию) и ⊘ (брошено).
  Самый частый случай — одна реплика человека закрывает одну развилку из пяти, а остальные
  молча бросаются.
- **Повтор поднимает уровень риска**, а у находок вне задачи своя полоса (раздел 5).
- **Ошибки инструментов — слабый источник**: значимы две-три из 56 (раздел 6).
- **Новые правила 6–9**: задача шире беседы, журнал вместо сводок, маскирование секретов,
  главы. Беседа делится на шесть глав; основная линия в ≈15 узлов читается, а все ≈100 узлов
  на одном экране — нет.
- **Беседа — лишь часть задачи** (раздел 7). `quarry-ledger` — одна из бесед задачи `quarry`.
  Предварительная перепись по ключевым словам и первым репликам, без ручной проверки. Её
  первый вариант ошибся: «около 25 сессий Codex» оказались в основном не работой в Codex.
  После проверки заголовков сессий:
  - **около 35 бесед Claude Code с середины августа по конец октября**, в двух рабочих
    каталогах;
  - из них около 23 бесед августа–сентября существуют **только как копии в Codex**. Codex
    Desktop импортировал историю Claude Code, а Claude Code удалил оригиналы: самый старый его
    файл на машине на месяц моложе начала задачи. Копия хранит только текст реплик, без вызовов
    инструментов;
  - **собственная работа в Codex — одна сессия** с 16 субагентами-исполнителями, которые шли по
    одному протоколу, и 16 сессиями автоматического ревьюера команд.

  Одни ключевые слова дают шум, потому что тема упоминается и в инструкциях проекта. Состав
  задачи можно установить только по признакам связи из раздела 7.

  Ошибка переписи сама стала выводом. Платформу беседы определяет её происхождение, а не место
  хранения: импортированная копия — беседа Claude Code, и в задаче она не должна появиться
  дважды.

Проверка владельцем, 29 октября 2026:

- **Список бесед-кандидатов задачи подтверждён** без правок.
- **Карта беседы подтверждена с одной правкой.** Находка вне задачи (сломанная соседняя
  система) попала в таблицы развилок и рисков самой задачи, хотя на основной линии её не было.
  Ошибка не в самой находке, а в том, к чему её отнесли. Вывод: до того как узел попадёт в
  задачу, программа явно проверяет, относится ли он к задаче. Если нет, узел уходит в полосу
  находок.

Доли лишних меток по этой проверке посчитать нельзя: владелец не размечал каждую метку, а
подтвердил карту целиком. Для числа нужна поштучная разметка хотя бы одной главы.

**Сшивка бесед в задачу замерена** (ADR 0051, последний раздел):
- задача затравки на сильных признаках — 5 бесед, по оценке разработчика без чужих;
- полнота — 9 из ≈35 бесед. Главная причина пропусков — копии бесед Claude Code в хранилище Codex:
  у них нет инструментов, имени и настоящего времени;
- без четырёх поправок правила сшивка склеивала 60 бесед из разных задач.

## 11. Чего карта не делает

- **Не сливает ветки сама.** Выбор ветки и принятие её кода — решение человека.
- **Не заменяет переписку.** Карта — это оглавление переписки, а не её пересказ вместо неё.
- **Не решает за человека, что риск принят.** Серым метку делает только человек и только с
  причиной.
